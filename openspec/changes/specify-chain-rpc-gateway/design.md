## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

- *Native provider provisioning and operations*, line 644: "The standalone RPC gateway has its own inbound bearer and persistent journal, distinct from engine/admin credentials."
- *Listener and secret boundaries*, line 656: "Reference topology places Caddy TLS ingress in front of provider public HTTP (`127.0.0.1:9419`), relay HTTP (`127.0.0.1:8081`), and the bounded authenticated chain RPC gateway (`127.0.0.1:8547`)."
- Line 667: "The bounded RPC gateway exposes an exact `eth_*` method allowlist, not arbitrary node administration."
- *Shared signing-wallet directory*, line 474: Unix secrets must not be group- or world-accessible, native Windows uses owner-protected storage, "Provider signing, admin, engine, and RPC credentials are separate protected files", and bearer tokens never go on command lines.
- *Configuration and state*, line 459: `network.rpc_bearer_file` is an optional protected RPC bearer file; "never put a token in the URL".
- *Settlement and recovery risks*, line 512: native `eth_*` RPC replaces the historical `chiral_*` contract, and the 64 KiB and 8 MiB bounds.
- *A.1 Global rules*, line 808: bearer files never enter the webview; the GUI passes file paths to native commands.
- `CLAUDE.md`: "Operator routes require their protected bearer and reject browser `Origin` requests", and wallet, engine and operator secrets "use protected files, not command-line arguments".

The change was prompted by item 7 of `docs/apas-worker/comparison-2026-11-18.md`: the gateway accepted every request without a bearer when bound to loopback, although line 656 puts public TLS ingress in front of exactly that loopback port, and the generated Caddyfile forwards the public RPC domain's `/api/chain/rpc` to it.

## Decisions

1. **One small capability, `chain-rpc-gateway`.** The standalone gateway is a separate binary with its own listener, credential, allowlist and probes. Its transport bounds already live in `inference-funding-settlement`, which this capability references instead of restating.
2. **The bearer is required on every bind address, with no development exception.** Line 656 puts public TLS ingress in front of the loopback port, so "loopback" says nothing about who can reach it. Any other local process or user on the host can reach a loopback port too. An exception would need a flag that, once copied into a service file, silently serves the chain RPC unauthenticated behind ingress. No caller needs one: provisioning already requires `rpc_token_file` in calibration mode as well, every documented command passes `--bearer-file`, and tests create a 32-character file in one line. The previous rule (bearer required only for a non-loopback bind) is removed.
3. **The bearer file reuses the provider's protected-secret reader.** `provider_config::read_secret` opens without following a symbolic link (`O_NOFOLLOW` on Unix, reparse-point open on Windows), requires a regular file of 1 to 4,096 bytes owned by the effective user with no group or other access (owner-only ACL on Windows), trims surrounding whitespace, and refuses an empty value or one containing whitespace or control characters. The gateway adds two rules: at least 32 characters, and visible ASCII only. Non-ASCII bytes cannot be sent in an `Authorization` header by the Rust client (`HeaderValue::from_str`), so such a bearer could never authenticate; refusing it at startup is better than a gateway that refuses everyone.
4. **The minimum is 32 characters.** The book states no length. Provisioning already refuses a shorter `rpc_token_file` ("RPC bearer must contain at least 32 characters") and the gateway already refused a shorter bearer when one was given. The spec makes that floor normative for every bind address. Question 2 asks the author to state it.
5. **Distinct from the upstream bearer, the one distinctness the gateway can check.** Line 644 says the bearer is distinct from engine and admin credentials. The gateway never reads those files, which live in the provider configuration, so it cannot compare against them; provisioning generates the admin and engine tokens with `secrets.token_urlsafe(48)`, so a collision with the operator's RPC token is negligible. The gateway does read its upstream bearer, and equality there matters most: a client holding it could call the upstream node directly and bypass the allowlist. The gateway therefore reads the upstream file as `rpc_client` sends it (protected open, at most 4,096 bytes, trimmed) and refuses to start when the two are equal. If the upstream file cannot be read, the gateway now stops with that error; before, it stopped at the identity check because `rpc_client` could not send the bearer, so no working configuration is refused. The comparison is constant-time, although at startup no attacker observes timing.
6. **Origin refusal is 401 for any value.** The current code refuses any request carrying `Origin`, including `null`, with the same 401 as a missing bearer. The spec keeps that: a browser page must never use the gateway, and a 401 reveals nothing about whether the bearer was right. Native clients (`rpc_client`, the CLI, the daemon and the relay) never send `Origin`.
7. **Authentication precedes the body.** The bearer layer wraps only the RPC route and reads headers only, so a refused request is not buffered or parsed, consumes no rate or concurrency budget, and reaches no upstream. `/healthz` and `/readyz` are merged outside that layer and remain unauthenticated (requirement 7).
8. **`Cache-Control: no-store` on every RPC-route response, refusals included.** Authorized responses already carried it. The 401 refusal did not; it now does, so that no intermediary caches anything on that route. The probes carry no secret and are not covered.
9. **`net_version` is removed from the allowlist.** Line 667 says the allowlist is an exact `eth_*` list, and line 512 says native `eth_*` RPC replaced the older contract. No Chiral client calls `net_version`: `ChainClient` identifies the network with `eth_chainId` and the genesis block, and no script, page or SDK example names it. A third-party library such as ethers v5 may fall back to `net_version` only when `eth_chainId` fails, and such a library cannot use the gateway anyway, because the gateway requires a bearer and refuses browser origins. Keeping it would have needed an author decision; removing it aligns the code with the book. The Verus companion (`verified/method_allowlist.rs` and its README) is aligned by hand; Verus is not installed (report entry of 2026-11-15), so its proof was not re-run.
10. **Parameter shapes are normative; budgets are not.** The method table in requirement 4 is the contract that `validate` enforces and the existing tests assert, and an exact allowlist is only meaningful with fixed shapes. The numbers below are not stated by the book and are recorded as current implementation values.
11. **Current implementation values (not normative).** Batch bound 8 members. Read concurrency 32 and submission concurrency 4 (`Semaphore::try_acquire_many`, never queued). Read rate 64 per second with a burst of 128; submission rate 2 per second with a burst of 4. JSON-RPC error codes: -32003 authentication or `Origin` refusal; -32600 invalid envelope, shape, method or batch size; -32700 invalid JSON; -32005 rate, capacity and aggregate-size refusals; and, per member, -32602 rejected, -32001 pending and -32002 unavailable, each with a fixed message. A startup refusal is printed by Rust's `main` as `Error: "<reason>"` on stderr with exit status 1; a missing `--bearer-file` is a `clap` usage error with exit status 2.

## Code differences

1. **A loopback gateway accepted every request without a bearer** (requirements 1 and 2; book lines 644 and 656). `--bearer-file` was optional and required only for a non-loopback bind (`chiral_rpc_gateway.rs:61–65` before this change), and `auth` authorized every request when no bearer was configured (`map_or(true, …)` at line 41). With the reference Caddyfile, a public `POST https://<rpc_domain>/api/chain/rpc` without credentials then reached the allowlist and the upstream node. Fixed by task 2.1.
2. **A non-ASCII bearer was accepted** (requirement 1). It passed the 32-byte check but could never match a header that a client can send, so the gateway refused everyone. Fixed by task 2.1.
3. **An inbound bearer equal to the upstream bearer was accepted** (requirement 1; book line 644). Fixed by task 2.1.
4. **The 401 refusal had no `Cache-Control: no-store`** (requirement 2). Only authorized responses carried it. Fixed by task 2.2.
5. **`net_version` was on the allowlist** (requirement 4; book line 667). Fixed by task 2.3 (decision 9).
6. **Preflight did not check that the gateway requires its bearer** (requirement 8). It checked only `/healthz` and `/readyz`, so a gateway serving unauthenticated passed. Fixed by task 2.4.
7. **Provisioning did not refuse identical inbound and upstream bearer files** (requirement 8). Such a deployment would fail at gateway start (task 2.1); provisioning now refuses it first. Fixed by task 2.5.

## Observations outside this capability

- `relay_server` merges the same `chain_rpc_api::router` into its HTTP listener without any bearer or `Origin` check (`relay_server.rs:232`). The reference Caddyfile forwards only the catalog, rating, policy and health paths of the relay domain, so that route is reachable on `127.0.0.1:8081` only, but the reasoning of decision 2 applies to it as well. Open question 1.
- The `Authorization` scheme is matched case-sensitively (`Bearer `), although HTTP authentication schemes are case-insensitive. Every Chiral client sends `Bearer`. The spec does not require either behaviour, and nothing was changed.
- `docs/provider-qualification.md` line 225 now also says that preflight requires a 401 from an unauthenticated RPC request. `docker-compose.yml`, the `Dockerfile` and the guide's native command already pass `--bearer-file`, so none of them needed a change; `README.md` does not start the gateway.

## Open questions for the whitepaper author

1. **Should the relay keep its unauthenticated `/api/chain/rpc` route?** `CLAUDE.md` says the relay serves "bounded chain RPC access", while line 656 calls only the standalone gateway "authenticated". Options: (a) remove the route from the relay, since provider and relay already call the standalone gateway; (b) require a protected bearer and refuse `Origin` there as well; (c) keep it as a loopback-only convenience. Proposed default (what this change does): this capability covers only the standalone gateway and leaves the relay unchanged until answered. Nonblocking: no task waits on the answer.
2. **May lines 644 and 667 state the bearer rule and the method list?** Proposed wording for line 644: "The standalone RPC gateway requires its own protected inbound bearer file on every bind address, including loopback (at least 32 visible ASCII characters, distinct from its upstream RPC bearer and from engine/admin credentials), and keeps its own persistent journal." For line 667: "The bounded RPC gateway exposes exactly `eth_chainId`, `eth_blockNumber`, `eth_gasPrice`, `eth_syncing`, `eth_getBalance`, `eth_getTransactionCount`, `eth_getBlockByNumber`, `eth_getTransactionReceipt`, `eth_estimateGas` and `eth_sendRawTransaction`, with fixed parameter shapes, not arbitrary node administration." This also confirms that `net_version` stays excluded (decision 9). Nonblocking: the spec adopts this reading.

## Risks

- An operator who ran the gateway on loopback without `--bearer-file` (contrary to every documented command) now gets a startup refusal. The provider and relay of such a deployment must then be given the same bearer through `network.rpc_bearer_file`. This is intended, but release notes should mention it.
- A deployment whose inbound and upstream bearer files hold the same token now fails at gateway start until the operator issues a separate inbound token. Provisioning refuses such input (task 2.5); an existing deployment provisioned before that check needs a new inbound token.
- Removing `net_version` breaks any external tool that called it through the gateway. Such a tool needed the bearer and no `Origin`, so it was an operator tool, not a browser wallet; `eth_chainId` gives the same chain identity.
- All executable evidence is local: a loopback upstream fixture and the gateway process. No live chain, Caddy ingress or Windows ACL run is involved. Task 4.1 records the missing deployment evidence; it never counts as public-release approval.
