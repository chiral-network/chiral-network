## Decisions

1. **One capability, `inference-generation-performance`.** Qualification and runtime classification share one class definition, one envelope and one timing rule, so they are specified together. The waiver arithmetic, the binding of the admitted report and evidence-only renewal stay in the capabilities that already own them.
2. **The withdrawal rule is stated exactly as the book states it.** Line 573 reads "three misses in the last up-to-20 observations, or two misses once the window reaches 20". The window for a key is its most recent min(n, 20) counted observations. The latch is set when the window holds at least three misses, or when it holds exactly 20 observations and at least two misses. The sentence is not ambiguous, and the code implements it literally (`billing_store.rs:1302–1310`: `misses>=3 OR (count=20 AND misses>=2)` over the last 20 rows by `sequence`). One consequence is easy to miss, so it has its own scenario: two misses among the first 19 observations do not latch, but the 20th observation latches even when it is a success. The rule then matches the 95% qualification threshold, since at most one miss in 20 is 95%.
3. **Provider-incomplete execution is a miss with a waiver.** Line 571 says that provider-incomplete execution "cannot masquerade as success" and that eligible misses settle with `inference_waiver`. Attainment is binary: an in-envelope request that is not a client interruption either attained or did not. Treating provider-incomplete execution as merely excluded would let a provider turn a slow request into a failure or timeout and so avoid withdrawal. The code already classifies it as missed, waived and counted (`performance.rs:304`). Author question 1 asks how failures caused by the request itself should count.
4. **A client interruption is recorded whenever the gateway can observe it.** Line 571 says that client interruption does not erase an already measured miss, and that "interruption before a measured miss is not an automatic waiver". A non-streaming client that closes its connection, and a client that disconnects before the engine responds, are client interruptions. Only an interruption that the gateway cannot attribute, such as a task panic or a runtime shutdown, is provider-incomplete. The current code differs (code difference 1).
5. **A consumer that stops reading is a client interruption, and its stall time is excluded.** While the bounded downstream buffer is full, the gateway stops reading the engine stream. Token arrival times observed after that reflect the consumer, not the engine. The gateway therefore subtracts the blocked time and, unless a miss was already measured, records the request as `client_interrupted` (`inference_gateway.rs:945–955`, `performance.rs:293` and `302`). This keeps transport and consumer slowness out of provider misses, as `p2p-provider-transport` requires.
6. **The requested maximum is the output limit the gateway reserves.** The book says "requested maximum, not eventual output" (line 552). When the client sets neither `max_tokens` nor `max_completion_tokens`, the gateway reserves min(model maximum, 256) (`inference_backend.rs:466`). That default is the request's maximum, so such a request is inside the envelope when its prompt fits.
7. **Nonpositive timing is never attainment, for TTFT as well as decode.** Line 558 says "Nonpositive or missing timing is not evidence of attainment". The requirement applies this to TTFT and the decode interval in both runtime classification and qualification. The current code treats a 0 µs TTFT as attained (code difference 2). The case is unlikely in practice, because TTFT includes private tokenization, but the rule is stated without exception.
8. **Every qualification prompt is a boundary prompt.** Line 566 says to exercise unique prepared prompts "at the 128/512/1,024/2,048-token boundaries (within eight tokens below each target)", and the provider guide (line 419) says the same. The buckets are therefore 120–128, 504–512, 1,016–1,024 and 2,040–2,048 tokens, inclusive. The runner generates only such prompts (`qualify-provider.py:270–307` and `495`). Native validation also accepts samples outside every bucket, and counts them toward the 100 samples per mode (code difference 3).
9. **Current implementation values (not normative constants).** Each may change without a spec change if the requirements still hold:
   - Outcome classification strings: `eligible` (attained or measured miss), `short_output_ttft_only`, `client_interrupted`, `provider_incomplete` (since task 2.1 this also covers an `interrupted` status the gateway cannot attribute, which was formerly `interrupted_unknown_origin`), `outside_workload`, plus `pending` while reserved and `unqualified` for unprofiled agreements (`performance.rs:300–306`, `billing_store.rs:1062–1067`, `inference_gateway.rs:370–375`). Terminal statuses come from `terminal_status`: `completed`, `cancelled`, `disconnected`, `timed_out`, `failed`, and `interrupted` from `Drop` (`inference_gateway.rs:401–405` and `723–731`).
   - Overload refusals: 429 `provider_saturated` (body readers), 429 `model_saturated` (model slots) and 429 `rate_limit` (arrival envelope). The arrival limiter is a token bucket per deployed model, shared by all accounts, with a burst of `max_concurrency` requests and a refill of `arrival_milli_rps` / 1,000 requests per second (`inference_gateway.rs:535–547`).
   - The bounded downstream buffer for a streaming client holds 4 events (`inference_gateway.rs:636`).
   - Evidence is at most 64 MiB. Native validation accepts 100–10,000 samples per sweep. The runner samples memory every 0.2 seconds and uses a 120-second HTTP timeout.
   - The engine is asked for sampled-token IDs through `n_probs` (at least 1 for chat), `return_tokens: true` and, for completions, `verbose: true` (`inference_backend.rs:487–500`).
   - A latched model's offers disappear at the next offer refresh, nominally every 30 seconds, and offers expire 120 seconds after issue (`app.rs:351–354`, `376`, `391–395` and `421`).
   - A latched report's requests are refused with 503 `model_unqualified` (`inference_gateway.rs:519–525` and `568–574`, `billing_store.rs:1003–1011`), and its quotes cannot obtain new funding acknowledgements (`contracts.rs:385–394`).

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **An interruption the gateway does not attribute is waived and counted as a provider miss, and client disconnects reach that path** (requirements 11 and 12, book line 571). `Settlement::drop` settles an unsettled request as `interrupted` (inference_gateway.rs:401–405). `outcome` classifies `interrupted` as `interrupted_unknown_origin`, with attainment missed and remedy `inference_waiver` (performance.rs:303), and `settle_request` counts it as a miss in the withdrawal window (billing_store.rs:1292–1310). Two client actions reach this path:
   - A non-streaming client runs `stream_inner` inside the HTTP handler with no sender, so a client disconnect is not observed (inference_gateway.rs:667–676 and 875).
   - Before streaming starts, `engine.dispatch` is awaited inside the handler for both response modes (619–624).

   When a client closes its connection, the HTTP/1 server (hyper 1.8.1, `mid_message_detect_eof`: "found unexpected EOF on busy connection") fails the connection and drops the handler future, which drops the `Settlement`. The code comment at inference_gateway.rs:321–323 names "socket teardown" among the `Drop` causes. A client that disconnects before a measured miss therefore gets an automatic waiver, and three such disconnects within the window latch withdrawal of the provider's report for every consumer. The test `exclusions_do_not_erase_a_previously_observed_miss` asserts the current behavior (performance.rs:413–415). Task 2.1. Fixed 2026-11-17 by task 2.1.
2. **A 0 µs TTFT counts as attainment** (requirements 4 and 9, book line 558). The native qualification predicate checks only `r.ttft_us <= TTFT_US` (performance.rs:249), and so does the runner's `passes` (qualify-provider.py:440). The runtime `outcome` treats `ttft_us == Some(0)` as an attained TTFT (performance.rs:291–306). Decode already requires a positive interval. Task 2.2.
3. **Native validation accepts qualification samples outside every prompt boundary** (requirement 8, book line 566). `validate_evidence` counts every sample of an endpoint/mode toward the 100-sample minimum and the 95% mode threshold, and checks only that each of the four buckets has at least 20 samples (performance.rs:252–266). A sample with, for example, a 300-token prompt is accepted. The runner never produces one (qualify-provider.py:495), so this affects only evidence the runner did not write. Task 2.3.

No other difference from the whitepaper was found. The envelope, the token clock, internal streaming and stripping, overload refusal, evidence binding, sweep coverage, joint attainment, the arrival check, the memory checks, the short-output exclusion and the withdrawal arithmetic and its durability match the requirements.

## Observations outside this capability

- Native validation cannot tell whether a `device_used` memory series for a Vulkan profile came from a trustworthy counter. Only the runner fails closed for Vulkan (qualify-provider.py:202). This matches line 99, which assigns the rejection to the runner, and the evidence remains an operator declaration, not attestation.
- `validate_evidence` returns per-sweep summaries, which `qualification_probe` discards (inference_backend.rs:695–697). The evidence file keeps every raw sample, so nothing is lost. Exposing the summaries to operators would be a separate change.

## Open questions for the whitepaper author

1. **Failures caused by the request itself.** Line 571 says that provider-incomplete execution "cannot masquerade as success", and decision 3 counts it as a miss with a waiver. The code classifies every in-envelope request that ends without normal completion, other than an observed client interruption, as provider-incomplete (performance.rs:304). That includes a request that the engine refuses after admission because of a consumer-supplied option that the gateway's validation admitted, for example a structured-output schema the engine cannot compile. If consumers can trigger such failures, a funded consumer can latch withdrawal with three cheap requests whose usage is unknown and therefore cost nothing. Should a failure attributable to the request count as a provider miss, be excluded like a client interruption, or be prevented by stricter validation before reservation? Proposed default (what the spec adopts): it counts as provider-incomplete. The gateway admitted the request, and the provider can validate options before reservation. Nonblocking: no task waits on the answer.

## Risks

- Every executable evidence above is synthetic: unit fixtures, a fixture engine that returns fixed SSE, and runner tests with mocked commands. No qualification run, live engine token clock or GPU memory series has been recorded for this contract. Task 4.1 tracks live qualification evidence. It must come from an authorized private deployment, and it is not public-release approval.
- The token clock requires one sampled-token ID per output event, and observed IDs equal to final usage. Qualification samples always end at exactly 256 tokens with finish reason `length`. No recorded evidence shows that the pinned engine (`cd959bae`) keeps that agreement for requests that end at an end-of-generation token or a stop sequence, or that use tools or structured output. If it does not, such requests would be recorded as provider-incomplete misses. A consumer could then trigger them on purpose, with a prompt or stop sequence that ends generation at once, and latch withdrawal with three cheap, waived requests. Task 4.2 requires that evidence before any qualified class is published.
- The implementation values in decision 9 are not normative. Changing one needs no spec change, but this design should be updated to match.
- Requirements reference capabilities from pending changes. Task 4.4 sets the archive order.
