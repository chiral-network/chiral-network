## Decisions

1. **Four new capabilities, no modified ones.** Acquisition, runtime, chat and the workbench shell have different trust boundaries and different later consumers (M2 uses the runtime; M4 uses the library and runtime). The workbench capability holds the cross-cutting shell rules (local-mode independence, navigation, status bar, Settings, native boundary) so the other three stay focused. Closing, logout and Quit behavior for the new state is stated inside these capabilities instead of modifying `desktop-window-lifecycle`, whose Quit requirement M4 is expected to extend; this avoids two pending changes rewriting the same requirement.
2. **One artifact contract, proven by byte parity.** The desktop reimplements `scripts/provision-model.py` natively in Rust (no Python at runtime) and is accepted only if it produces byte-identical `chiral-artifact-sha256.json` and `chiral-model.json` for the same inputs and makes the same accept/reject decisions on the provisioner's fixture corpus. Canonical bytes come from `protocol.rs::canonical_json`; parity tests must cover non-ASCII strings because the Python writer uses `ensure_ascii=False`. The desktop is stricter in one respect: it requires the repository's LFS SHA-256 for every selected GGUF, as the book's transfer rule states, whereas the script also accepts a git blob SHA-1 for non-LFS files. GGUF files are LFS-stored on Hugging Face in practice, and the produced artifact has the same form either way. Repositories without a declared license, and identifiers not of the `organization/name` form, are refused because the script refuses them.
3. **Install-time fields are chosen before download and fixed afterwards.** As the book's *Selection* and *Load and eject* rules state, the user chooses the task, per-slot context, maximum output and chat template that the provisioner fixes; the per-slot context is not a load setting, and another context is another installation with a new artifact identity (and, for a paid generation share, new qualification; a free share is published after readiness probes instead, as `specify-desktop-share-online` specifies under book *Author decisions* item 1). The values are chosen against the repository's declared metadata and rechecked against the verified GGUF; a contradiction stops the installation for a new choice rather than silently changing a value, matching the provisioner's refusal. Choosing the default template records `chat_template_name` null, because the provisioner records null when `--chat-template-name` is omitted and the manifest bytes (hence identity) would otherwise differ. Proposed prefill values (open question 2): task from the declared pooling metadata, context = min(declared native context, 32,768) and maximum output = min(context − 1, 4,096); the dialog flags values below the qualification minimums.
4. **Storage layout refines the book's.** Because one commit can yield several installations (different quantizations, templates or limits), and an artifact root may contain only its inventoried files, each installation lives at `<app data>/models/<organization>/<name>/<commit>/<artifact identity>/`, where the identity is the SHA-256 of the canonical manifest (the existing `artifact_manifest_sha256`). This stays within the book's `models/<repo>/<commit>/` prefix. Runtimes live at `runtimes/<runtime identity>/` (the existing `runtime_sha256`); an inventoried runtime directory cannot hold anything else, so per-load engine key files live in a separate `<app data>/engine/` directory. Downloads stage in `<app data>/downloads/` on the same volume so installation is an atomic rename. Native preferences (token path, chat-history preference and whether its first-run disclosure was shown, removed bundled runtimes) live in a settings file under app data. `local-server/` and `network/` belong to M2 and M4. `<app data>` is Tauri's `app_local_data_dir` on every platform: on macOS and Linux it is the same directory as `app_data_dir`, and on Windows it is the per-user local (non-roaming) directory under `%LOCALAPPDATA%`, so tens of gigabytes of models, runtimes and staging never land in a roaming or redirected profile. The layout plus a GGUF path of up to 512 characters (the provisioner's `safe_path` bound) can exceed Windows' 260-character path limit; a Windows selection with such a path must either install, load and chat successfully or be refused before anything is staged, and the verification plan exercises it. Owner-only permissions cover the directories and files this change creates, not files that WebView2, WebKit or other software keep under the same root.
5. **Templates are selected, never edited.** The user selects the default embedded template or a named one; when the GGUF has named templates but no default, a name is required, exactly when the provisioner requires `--chat-template-name`. The template file is the GGUF's bytes; `chat_template_sha256` covers the effective source the pinned Jinja lexer reads.
6. **Pin first, then fetch by commit.** The download resolves the ref to a full commit, re-reads the metadata at that commit (license, file list, LFS digests and sizes), and requests every file by commit. The license shown for acknowledgement is the one at the pinned commit, matching how the script reads the card data at `--revision`.
7. **A constrained native transfer client.** Fixed origins (`https://huggingface.co` for the API and resolve requests) and the book's `safe_http_client` discipline applied per hop: each host, including every redirect target, is resolved once under a five-second deadline, refused if the answer set is empty, exceeds 32 answers or contains any address failing `offer_registry.rs::public_ip`, and connected to only at those pinned addresses. Redirects are followed by the native client one hop at a time (never by the HTTP library's redirect policy, which would resolve and connect again unchecked), at most 5 per request, only to `https` on port 443 and only to `huggingface.co` or the compiled download-host allowlist. Five hops leave margin over Hugging Face's resolve-to-storage redirect chain (a resolve redirect to an LFS or Xet storage host, possibly preceded by a same-origin redirect for a renamed repository); the limit is confirmed with the host allowlist against current infrastructure. JSON responses (search, metadata, model card) reuse the consumer client's 8 MiB response bound. There are no environment proxies (as with the existing outbound clients), and the token goes only on requests to the Hugging Face origin. Resumption uses HTTP range requests on staged bytes; the full-file SHA-256 is the backstop, so a resumed transfer never skips verification. The exact host allowlist is an implementation input to be confirmed against Hugging Face's current download infrastructure (for example its LFS CDN and Xet bridge hosts) and recorded with the code.
8. **Runtimes only from the compiled allowlist.** The desktop compiles the same official asset table as `scripts/provision-runtime.py`. A bundled runtime is the same pinned archive shipped with the installer and goes through the same hash check and extraction, so there is no second, unverifiable install path. Because the book offers bundling as an alternative to an explicit request, a bundled archive is installed at first launch without any network request; the prohibition is on *downloading* a runtime without an explicit request, not on installing the bundled one. A runtime the user removes is not silently reinstalled; Settings offers reinstalling it from the bundled archive. A GitHub runtime download uses the same per-hop client rules as Hugging Face (decision 7) with `github.com` and a compiled GitHub release-host allowlist. Runtimes can be removed explicitly, refused while a loaded engine uses them; M4 adds the refusal while a share or qualification run uses one, which its *An active share pins its model and runtime* requirement already assumes. Which backends each installer bundles is a packaging decision outside this change. Verification before every launch reuses checks equivalent to `engine_runtime.rs::validate_inventory`; missing native dependencies are reported, never supplied by downloading or environment injection.
9. **Fit: an estimate before, an observation after.** The estimate adds weight bytes, the KV cache (layers × per-slot context × concurrency × K/V widths × cache-type size, from GGUF metadata) and a stated runtime allowance. In Discover it uses the chosen install context and the intended concurrency against total memory minus headroom; at load it uses the installed context and the chosen concurrency against currently observed free memory minus headroom, which already accounts for other loaded models and processes. For CPU-only execution, system RAM is shared memory, so the estimate uses the 4,096 MiB unified headroom; the managed engine has no CPU memory observer, so CPU loads rely on the pre-load estimate and report observed memory without a post-load refusal. Accelerated loads reuse the managed engine's post-health device observation. The runtime allowance constant is an implementation input shown with each estimate.
10. **One private engine child per loaded model.** The local engine manager reuses `engine_runtime.rs` command construction (minimal environment, logging and web UI off, no context shift or prompt cache, explicit devices) with an OS-selected loopback port and a fresh per-load key file, so a desktop load never collides with a provider's fixed private port and never adopts another process. The desktop's engine client follows the book's private-engine rule (proxies and redirects disabled) and connects only to literal `127.0.0.1`, as `engine_runtime.rs::await_health` already does, so prompts and the per-load key cannot be diverted to an environment proxy. Several models may be loaded at once, each passing its own fit check, subject to the load refusals and acknowledgements M4 adds while a share is active or a qualification run is in progress. No automatic restart or replay, matching the provider lifecycle rule for managed child failure. An installation that backs an active share or an in-progress qualification run is never loaded by the desktop (the book: "the model is never loaded twice"); M4 owns how it is served.
11. **Untrusted models are disclosed, not vetted.** The book replaces the operator assumption of trusted installations with untrusted GGUF inputs and requires a disclosure before loading a model from an unvetted repository, but defines no vetting. Until it does, every repository is unvetted and the load dialog always carries the disclosure; the user's explicit Load in that dialog is the consent. Bounded GGUF parsing reduces, but does not remove, parser risk inside the engine.
12. **Local chat through the native boundary.** A native command builds the chat request and streams engine events over a Tauri channel, mirroring `inference_stream`. Usage comes from the engine's reported counts (streamed usage), never from text length. With `--no-context-shift` the engine refuses only a prompt that alone fills the slot; otherwise it generates until the slot or the output limit is reached and stops with finish reason `length`. The desktop therefore pre-checks overflow itself exactly as the provider gateway does (`inference_backend.rs`: `/apply-template`, then `/tokenize`, then prompt tokens + maximum output tokens against `context_length`) and refuses before generation, and it labels a `length` stop as stopped at the length limit instead of completed. It never trims history behind the user's back.
13. **Network threads reuse the consumer path unchanged.** Existing `inference_stream`, `inference_cancel` and `request_status` operations, the Playground status labels (including the separate dispatch-error label) and Reconcile action, the Playground's 1,000,000-character display limit that requests cancellation, exact wei display and no automatic paid retry. Funding stays in the Marketplace and Usage pages, where the A.1.6 disclosure already lives. Moving a thread's content to a provider requires explicit consent so that "local use never sends prompts off the machine" holds even when local and network sources share one view.
14. **History is native, disclosed and controllable.** History is on by default (book *Author decisions* item 3, the familiar local-client behavior). Because that default stores conversations without a prior choice, the Chat page shows a one-time first-run disclosure before the first thread is stored, with a Turn off action, and records natively that it was shown; the persistent history disclosure on the Chat page remains. Threads are stored by the native process under `chats/` with owner-only permissions, never in webview storage. Turning history off stops writes without deleting what exists; clearing is a separate confirmed action. Storage is protected but not encrypted by Chiral, and the page says so. Network threads store their network identity and consumer wallet address, and are listed only when both match the loaded profile and the thread's account exists in its account store, so session scoping (A.1.8) hides them under a different network, a different wallet on the same network, or another `data_dir` without deleting them. Network identity alone would leak one wallet's prompts, account IDs and request IDs to another profile on the same network, since consumer accounts and credentials are scoped per `data_dir`.
15. **Session and window lifecycle.** Closing keeps engines, downloads and streams running (A.1.10). A.7 scopes A.1.3 and A.1.8 to network actions, so logout and profile changes cancel network-thread streams and clear network data but leave local-model chats streaming, local models loaded and history intact. Local streams are therefore tracked separately from the consumer session's stream set, which the native `logout` path cancels as a whole today. Every application exit the native runtime observes stops engines and leaves downloads resumable: a confirmed Quit (after `logout` succeeds, before the window is destroyed), an operating-system quit command that bypasses the modal (A.2: Cmd+Q on macOS) when `desktop-window-lifecycle` does not intercept it, and operating-system logout or shutdown. M4 makes `desktop-window-lifecycle` intercept such quit requests while a share is active or a qualification run is in progress and route them to the Quit confirmation, so the desktop then exits only through a confirmed Quit and keeps running if the user declines; the Cmd+Q scenario therefore assumes no active share and no qualification run. macOS has no parent-death signal or job object, so an implementation that stopped engines only on the confirmed-Quit path would leave `llama-server` children holding memory and a keyed loopback listener after Cmd+Q; Linux parent-death and the Windows kill-on-close job remain backstops for abrupt termination. The Quit confirmation text is unchanged.
16. **Navigation follows A.7.** Chat, Discover and My models come first; Marketplace, Playground, Usage & API keys, Account, Network and the external-daemon Provider page are grouped under Network; Wallet stays; Settings and Diagnostics sit at the end; Local server and Share items wait for M2 and M4; the fallback route is unchanged pending open question 4. A.7 draws the rail (Sidebar) layout only; for the Top bar the Network group becomes one Network menu, and the Top bar's existing More-folding and width rules (A.2, `MAX_VISIBLE` in `src/lib/navigation.ts`) apply to the resulting top-level items without reordering them, so the order and grouping are testable in both layouts.
17. **Only custom-command permissions.** New native commands receive allow-permissions; no shell, filesystem, HTTP, dialog or opener plugin is granted. Reveal location takes an installation identity, never a path or URL from the webview, because a native `reveal(path)` handed to `open` or `xdg-open` would let the webview open or launch arbitrary files and URLs. It reveals the installation selected within its parent directory (Finder `open -R`, Explorer `/select,`, the parent directory elsewhere) rather than opening the directory itself, because a file manager can write `.DS_Store` or similar files into a directory it opens and both inventory validators reject any file outside the inventory. Such a failure names each unexpected path so the user can remove the stray file instead of re-downloading gigabytes; the desktop still never repairs an installation itself.
18. **The token file holds only a Hugging Face token.** `provider_config::read_secret` accepts any whitespace-free token, so a wallet key (64 hex characters) or a provider admin, engine or RPC bearer file would pass the generic rules and be sent to `https://huggingface.co` as a bearer if the user picked the wrong path. The desktop therefore also requires the Hugging Face user-token form (`hf_` followed by at least 30 ASCII letters or digits) and refuses paths under the engine key directory or the loaded consumer profile's `data_dir`, or equal to its RPC bearer file, both when saved and before each use (a profile can be loaded after the token path is saved). Refusal leaves Hugging Face requests unauthenticated; it never falls back to another secret.

## Non-goals and limitations

- **Other milestones:** the local API server (M2), libp2p transport, path labels and relay disclosure (M3), and sharing, in-app qualification, the provider daemon, sleep prevention and share-related library, eject, logout, status-bar, tray and Quit behavior (M4).
- **OS confinement of the engine:** the book makes confinement that denies the engine access to the wallet, provider, local-server and token secrets a release-gate item; this change does not specify a mechanism (open question 3) and cannot be presented as available before that gate closes.
- **Consumer state layout:** moving the consumer `data_dir` into `<app data>/network/` is not part of M1; profiles are still loaded by path in Settings.
- **Importing externally provisioned model directories** into the library: not stated by the book, and it would require a trust decision about arbitrary paths. Operators keep using the script path.
- **Relocating storage** or choosing a custom models directory: Settings shows locations read-only; moving immutable artifacts and protected state needs its own design.
- **Non-GGUF formats, multimodal projectors, LoRA adapters, image/audio, Responses API and tool execution:** outside the book's release scope; the managed launch disables multimodal projectors.
- **Completions-only and embedding models in Chat:** they can be installed and loaded but are not chat sources; their use arrives with the local API server (M2).
- **Changing context at load:** fixed by the installation per the book; another context is another installation.
- **Proxy support** for Hugging Face or GitHub downloads, consistent with the existing outbound clients.
- **Deduplicating files** across installations: inventories forbid links, so two installations of the same bytes take twice the space.
- **Update checks or notifications** for newer revisions.
- **Repositories without a declared license and non-LFS GGUF files:** refused (decision 2).
- **Intel Macs:** the managed runtime observes Metal only on Apple Silicon and the allowlist has no macOS CPU package, so no backend is available there.
- **CPU post-load memory refusal:** CPU loads rely on the estimate (decision 9).
- **Installer packaging and signing**, including which runtime each installer bundles: separate release gates.
- **Encrypting or securely erasing chat history:** history is protected by file permissions only, as disclosed.
- **Accepting Hugging Face gating terms in-app.**
- **Platform hardware qualification:** no OS/backend becomes qualified through this change.
- **Version enforcement is unchanged:** the existing required-update modal (A.2 version gate) still blocks the whole GUI, local pages included; making local mode usable under a required update would be a separate decision.

## Open questions

1. **Chat history default — decided.** Decided 2026-11-16 (book *Author decisions* item 3): history is on by default, stored only in local protected storage, and can be turned off and cleared. `desktop-local-chat` (*Chat history is local, protected and under user control*) now makes the on default normative with a first-run disclosure shown before any thread is stored (decision 14), and task 2.10.2 is no longer blocked.
