**Code observed while drafting**
- `chiral_daemon` binds its public and administration listeners, starts accepting, and refreshes and publishes offers immediately. On SIGTERM or Ctrl-C it drains, waits up to 75 seconds for the listeners to finish, then stops the engines and the DHT. It requires `--version-policy` only when the configuration is not in development mode.
- Every 30-second maintenance refresh reconciles funding and fees and calls the fee remitter, which submits batches at `FEE_MIN_REMIT_WEI = 10^15` or `FEE_MAX_AGE_SECS = 86,400`; `drain` does not stop it (`app.rs`, `contracts.rs`, `billing_store.rs`).
- In development with an unprofiled model, offers are stored locally and not published to the DHT. A free model's offer always carries `min_funding_wei = "0"`.
- Prices are read from configuration at startup. The daemon has no administration action that changes a running model's prices, and none that stops and relaunches the managed engine while the daemon keeps running; `drain` closes admission and withdraws offers, refusing funding with HTTP 503 `provider_draining` (`app.rs`, `contracts.rs`).
- `GET /api/ratings/:wallet` returns `elo`, `base_elo` and `vote_count`, where `vote_count` counts eligible votes over the 180-day window; no field counts votes over the last 14 days (`rating_api.rs`, `reputation.rs`).
- `ProviderConfig::validate`:
  - requires a nonzero loopback administration port distinct from the public port;
  - requires `fee_bps == 50`;
  - validates `public_endpoint` with the HTTPS-origin rules, so a libp2p-only offer needs milestone 3;
  - rejects generation without a serving profile outside development, whatever its prices, so a free share needs the exception of decision 29;
  - forbids mixing profiled and unprofiled models;
  - requires disjoint devices for simultaneous qualified models.
- The provider gateway serves an account only when a configured model accepts the account's agreed model for execution (`ProviderState::qualified_model`). `ModelSpec::accepts_execution` (`protocol.rs`) requires both serving profiles to be absent or both present with the same terms, so an account agreed under a serving profile is never served by an unprofiled model, and the reverse. It does not compare prices.
- The gateway charges the arrival envelope only when the account's model has a serving profile; an unprofiled model is limited by its concurrency slots alone (`inference_gateway.rs`).
- The daemon's readiness probe for every configured model, profiled or not, checks the private engine, tokenizer and template identity and runs real inference on each advertised endpoint with usage accounting, before the model is published (`inference_backend.rs`, `probe_model` and `qualification_probe`).
- `src/lib/components/ServingProfile.svelte` describes every missing serving profile as "this embedding or local calibration profile".
- The gateway's per-account rate limit is 120 attempts in each fixed 60-second window. The contract router has 64 control slots and the inference gateway 64 body-reader slots (`contracts.rs`, `inference_gateway.rs`).
- `DhtConfig` has `listen`, `bootstrap` and `identity_file`. `scripts/provision-provider.py` writes a DHT `listen` of `/ip4/0.0.0.0/tcp/<port>` for a published deployment and `/ip4/127.0.0.1/tcp/<port>` for calibration.

- `version::policy_public_key` resolves the `CHIRAL_POLICY_PUBLIC_KEY` override from the environment on first use.

- `scripts/provision-provider.py --calibration` binds the calibration HTTP listener on the same `127.0.0.1:9419` as the published deployment, with a loopback DHT listener, no bootstrap, and a Caddyfile that only answers 503.
- `scripts/qualify-provider.py` sends one paid echo probe (only when `completions` is advertised), then per path one warm-up per mode, then for each concurrency c a sweep of `c × ceil(max(modes × N, c) / c)` requests rotated round-robin over the gateway keys, with the warm-ups and echo probe on the first key.

## Decisions

1. **The book's step order, with reachability checked twice.** The wizard keeps choose, identity, reachability, qualification, pricing, publish. Reachability is checked before any qualification money is approved, so an unreachable machine does not spend a budget. That first check cannot use the calibration daemon, which is loopback-only, unannounced and has its own identity, and it cannot use the published deployment, which native configuration refuses to start without a qualified profile. It therefore runs in a dedicated reachability-check mode (decision 20) under the identity that will publish. The check runs again with the published deployment, started drained, immediately before publishing, because that is the process that will serve. A free or embedding share spends no budget, but it still completes the reachability-step check before its later steps, so every share follows one step order and an unreachable machine learns so before readiness and publishing. Both checks are libp2p checks (decision 33), so neither can run, and no share can pass step 3, until milestone 3 is implemented. Under the launch window (decision 37), step 4 approves the budget of a run that happens later, while the share is published (decision 38), so the reachability-step check still precedes any approval. The automatic run needs no new reachability-check-mode run, because the published deployment keeps running through it; the in-place promotion repeats the final check before resuming (decision 39).
2. **A calibration deployment, then a published deployment.** Native configuration rejects unqualified priced generation outside development. Calibration runs in development mode with nonzero terms, so it never relies on the free-generation exception (decision 29). A share that was published without an approved budget has no calibration deployment. The guide qualifies through a loopback, unpublished `--calibration` deployment with `serving: null`, then promotes into a separate deployment with empty state.
   - The desktop does the same. The calibration deployment runs in development mode on loopback with no DHT bootstrap and no libp2p serving, so its offers are not published. It has its own persisted DHT identity and ledger directory: one calibration deployment per network identity and provider wallet, reused across attempts. It shares the provider wallet's recorded `data_dir` base and journal.
   - Development mode does not exempt it from a verified signed policy (decision 25), and all its listeners stay on literal loopback.
   - Calibration agreements never become published agreements.
   - Revised for decision 38: the calibration deployment no longer runs only while the published deployment is stopped. It runs while the published deployment is in its qualification pause, still running but with its engine stopped, so the model is still never loaded twice. Its listeners therefore use ports distinct from every published-deployment listener (decision 23). A passing run's ModelSpec is promoted into the existing published deployment, not into a fresh one (decision 39), as the earlier upgrade already did.
   - Calibration accounts and fee obligations are preserved and listed with the share's liabilities. While the calibration daemon runs it remits automatically at the book's thresholds (decision 28). Forced remittance of the remainder is an explicit action that runs the calibration deployment on loopback.
3. **Start without publishing.** The daemon publishes as soon as it is ready. A new daemon option starts it drained, so the desktop publishes by calling the existing `resume` administration action, and only after the final reachability check, readiness, gas check and disclosure acceptance. Publication is confirmed through `/admin/offers`. Started drained, a libp2p-serving daemon still publishes its addresses through identify and its DHT records, as milestone 3 requires, and holds its relay reservation. What it does not publish is offers: its published-offer list is empty and its manifest replies carry none.
4. **A native qualification runner with evidence-contract parity.** Desktop users do not have a Python provisioning environment, and milestone 1 makes the same choice for `provision-model.py`. The desktop therefore implements the runner natively. It must produce the same `chiral-performance-evidence-v2` evidence and the same qualified ModelSpec as `scripts/qualify-provider.py` for the same measurements. The native deployment revalidation remains the gate.
5. **A paying wallet distinct from the provider wallet.** Guide §6 requires the measurement consumer wallet to differ from the provider wallet. The book's "one wallet may act as both consumer and provider" concerns the desktop's network-consumer role and provider role, not the measurement payer. The loaded consumer wallet may pay when it is not the provider wallet. Otherwise the user selects or creates another paying wallet, which gets a `data_dir` base dedicated to qualification payments, as the guide's separate consumer profile does.
6. **Calibration rates and publication prices.** Revised for book *Author decisions* items 8 and 11 (open question 8, decided). The serving profile and evidence do not bind prices. Guide §6 and §8 have calibration use the intended prices and require prices to match at promotion, and this decision's interim rule followed them by making a qualified share's publication rates equal its calibration rates. Auto-price now moves a qualified share's price among 0, 25, 50, 75 and 100% of a target with no new qualification, and the book requires for a nonzero price only "a valid qualification". Publication prices are therefore independent of the calibration rates, and the interim rule is withdrawn, together with its scenario *Publication rates follow the calibration rates*. The calibration rates remain the measurement deployment's own terms. Lower calibration rates lower the qualification funding and its fee, and the user chooses them in step 4. The runner refuses a free calibration agreement, so calibration still needs a positive minimum funding and at least one nonzero rate, both shown inside the budget. This departs from the guide's promotion rule for desktop shares only; the guide still governs `chiral_daemon` operators.
7. **Budget computation follows the runner exactly.** The requirement *Paid generation shares require in-app qualification within an approved budget* states the formula; this decision explains it.
   - The sweep count comes from `scripts/qualify-provider.py`: for each concurrency c it is `c × ceil(max(2E × N, c) / c)` paid requests across the 2E gateway modes. This is the total per sweep, not per mode. The guide's phrase "rounds `max(modes × N, concurrency)`" describes the same expression.
   - Warm-ups are sent once per mode per path before the sweeps, not per concurrency. The 2E gateway warm-ups and the echo probe (sent only when `completions` is advertised) are paid and go to the first key. Private-engine samples and warm-ups are unpaid, so the budget excludes them.
   - Each paid request is reserved at its maximum cost, `ceil((2,048 × input + 256 × output) / 1,000)` wei. This is an upper bound: the echo probe requests one output token, and failed or unknown-usage requests settle lower.
   - The guide asks for headroom under the 120 attempts per account per minute but gives no number. The gateway counts attempts in fixed 60-second windows. In one window the runner offers at most about 60 × A / 1,000 requests plus a burst of c, a sweep boundary can add another burst, and round-robin can give one agreement one extra request. The first agreement also carries the W warm-ups and the probe. K = max(1, ceil((ceil(60 × A / 1,000) + 2C) / (118 − 2E))) keeps every agreement within the limit under those bounds. The constant is this change's choice and must be revisited if the runner's schedule changes.
   - Opening funding is grossed up so that net credit after the 0.5% fee covers the agreement's reservations, and is never below the calibration minimum. Each agreement is opened once; there are no planned top-ups.
   - Gas is an estimate per funding transaction, kept outside the exact total.
   - The approved total is a hard cap on funding.
8. **One managed daemon, one shared model per share in this change.** The lifecycle is driven by configuration, so adding a model means restarting the daemon, which interrupts the current share. Simultaneous qualified models also need disjoint devices. The requirements are written per share so a later change can allow more.
9. **Loopback listeners, a dialable DHT listener, and a complete `libp2p_serving` block.** Administration, engine and the provider HTTP listener all bind literal loopback. A desktop share advertises no HTTPS origin (decision 33), so no ingress forwards to the provider HTTP listener; the desktop does no TLS, DNS or port setup. The reference ports (9419, 9421, 8000) are defaults the user can change. An occupied port is an error, never permission to adopt the process holding it.
   - The DHT listener of the published deployment, and of the reachability-check daemon under the same identity, binds a non-loopback interface on a default port the user can change. The reference provisioning does the same outside calibration (`/ip4/0.0.0.0/tcp/<port>`). Direct dials, hole punching and AutoNAT need it. Only the calibration deployment keeps a loopback DHT listener (decision 2).
   - Milestone 3 makes the `libp2p_serving` block mandatory for libp2p serving and leaves its values to the operator (its decision 18). The desktop is the operator here, so for every share it writes the whole block into both daemons' configurations, with a `null` `public_endpoint`. `relays` is the provider profile's list, which the wizard requires to hold 1–32 entries. The field names below are those milestone 3's decision 18 proposes for implementation; if that change renames them, the desktop follows.
   - **Implementation input, not an author decision:** the desktop sets each stream-server limit by the following rule, where C is the share's maximum concurrency:
     - `max_streams_per_peer` = C + 2: one stream per concurrent request from one consumer, plus a request-status read and a cancel;
     - `max_streams` = C + 64: every admitted request, plus the router's 64 control slots;
     - `request_head_timeout_secs` = 10;
     - `max_header_bytes` = 16,384 (16 KiB);
     - `idle_timeout_secs` = 30;
     - `max_requests_per_stream` = 1, because milestone 3's native consumers open one stream per request.

     The Share page shows the resulting values before publishing. They are not offer terms, so they bind no agreement. Implementation may revise this rule against milestone 3's stream-server release gate; a revision updates this decision and needs no author decision.
10. **Context is fixed by the installed ModelSpec.** The book's step 1 states that per-slot context is fixed by the installed artifact, and *Local chat* → *Load and eject* that a different context is a separate install with a new artifact identity and, for sharing, a new qualification. Under *Author decisions* item 1 that qualification applies to a paid generation share; a free share of the new install passes new readiness probes instead (decision 29). The guide forbids changing installed limits, and the launcher allocates per-slot context equal to the ModelSpec context. This matches milestone 1's decision 3: installed limits are immutable maxima, a local load may use less, and a share uses exactly the installed ModelSpec. The wizard shows the context and never edits it.
11. **Local use goes through an operator-only admission route.** The book requires local chat and every local-API-server route mapped to a shared model to go to the daemon. There they acquire the same per-model slot and qualified arrival budget before dispatch, without an account charge and never calling the engine directly. The mechanism chosen here is an operator route on the daemon's loopback administration listener, authenticated by the administrator token. It takes the same slot and arrival budget and applies the same validation and bounds. It never appears on the public listener or a libp2p stream.
    - A share whose model has no serving profile (a free share before any promotion) has no qualified arrival budget: the arrival rate is a serving-profile field, and the gateway charges the arrival envelope only for profiled models. Local requests to such a share take only a slot, and an "arrival budget exhausted" refusal never occurs for it. After promotion, a free share has the arrival budget at every price (decision 39).
    - Local requests have no prepaid account, fee or reputation, and are excluded from the paid performance window and waivers. Those remedies are defined over paid agreements' admitted reports.
    - Milestone 1 delegates a shared installation's local generation here through carve-outs in its own requirements, so the chat-side behavior (sending without a local load, admission refusal reasons, Stop through the daemon, relayed usage) is stated in this change's requirement, not by modifying milestone 1. Local use of an installation under qualification is refused, because it would disturb the measurement.
    - This requires a daemon change.
12. **Logout and profile switching are refused while sharing or qualifying.** This is the book's rule (*Share online*; A.7 scoping of A.1.3 and A.1.8): the user stops sharing first, so a share never ends without the drain and liability display. While qualifying, the refusal points to *Stop qualification* (decision 27), because no share exists yet. Quit is the only action that stops shares and runs as a side effect, and it lists them first.
13. **No automatic start and no automatic restart.** Share mode never starts without explicit consent, and the lifecycle table forbids automatic engine restart and requires reconciliation before a restart. A share that was active at the last exit is shown as stopped, with its last observed liabilities.
14. **A graceful stop reuses the daemon's own shutdown path.** *Stop sharing* calls `drain` first, so admission closes and offers are withdrawn at once. It then waits for in-flight requests, which the user may cut short, and then signals shutdown. The daemon's own 75-second settle bound still applies.
    - On Windows the supervisor must deliver the console control event the daemon waits for, or an equivalent. Delivering it is an implementation task.
    - Application quit requests are intercepted while sharing (decision 26). Only terminations the desktop cannot intercept run the stop from the native exit handler without the liability display.
15. **Native sleep prevention for idle system sleep only.** Each platform uses its own interface:
    - macOS: an IOKit `PreventUserIdleSystemSleep` assertion;
    - Windows: `SetThreadExecutionState` with the system-required and continuous flags, without away mode;
    - Linux: a logind inhibitor with `what=idle` and `mode=block` only. A `sleep` lock in block mode stops unprivileged users from suspending, so it is never taken. A `sleep` lock in delay mode is permitted only to finish bookkeeping before suspend. If a desktop environment's idle suspend ignores logind's idle inhibitor, that is recorded as a platform limitation; the desktop does not take a broader lock to compensate.

    None of these needs a webview permission. Consent is a locally stored native setting, and its default and prompt follow decision 31.
16. **Sharing state appears in the status bar and the tray.** Milestone 1's status bar explicitly leaves sharing state and transport to this change, which adds them on every page. The tray tooltip requirement in `desktop-window-lifecycle` is changed, not duplicated, because its current text fixes the tooltip.
17. **libp2p reachability builds on milestone 3's observation.** Milestone 3 has the provider report its AutoNAT classification, held relay reservations and advertised addresses on its loopback administration status, and leaves the wizard's verification to this change. The libp2p check is therefore:
    - that observation;
    - plus a dial through the relay of the advertised relayed (or confirmed direct) address. The dial comes from a native libp2p client whose peer ID is not the provider's: the loaded consumer node, or an ephemeral identity when no consumer profile is loaded;
    - plus a requirement that the Noise-authenticated peer ID equals the deployment's.

    The circuit leaves the machine through the relay, so it proves the relayed path. It does not prove hole punching from every consumer's network, and the dashboard says so. Before publication the provider has no valid signed offer, so the book provides only a coordination-sized reservation for this check. The check therefore proves reachability, not serving-grade relay capacity.
18. **Sharing hands the engine to the daemon.** The book states that the desktop ejects its own engine for the model, the daemon launches the managed runtime with the qualified settings, the daemon never uses the desktop's engine as an external endpoint, and the model is never loaded twice. This change keeps a confirmation before the eject because it ends any local chat in progress. While the model is shared, it cannot be ejected from the local engine until sharing stops. During a qualification run the published daemon stops its own engine before the calibration daemon launches one, and launches it again after a run that did not pass (decision 38), so the model is still loaded once at a time.
19. **The untrusted-artifact disclosure happens before the first share.** The book requires the GGUF risk to be disclosed before sharing a model from an unvetted repository. Sharing puts the provider signing key and administrator token within the reach of an exploited engine. The wizard therefore discloses before the first share of each installation, and treats every repository as unvetted unless milestone 1 defines vetting.
20. **A reachability-check mode for the pre-budget check.** A new `chiral_daemon` mode runs under the share's persisted provider DHT identity and network configuration, and holds that deployment's lock, so it can never run beside another daemon with the same peer ID. In this mode the daemon:
    - starts no engine, loads no model and mounts no inference route;
    - publishes no offer, so its manifest replies carry none, which is correct for a deployment that is not sharing;
    - runs no maintenance refresh, so it sends no chain transaction, reconciles no funding and remits no fees;
    - reports its reachability observation on its loopback administration status.

    It holds a reservation on the profile's relays, which is coordination-sized because it has no offer. It uses the same non-loopback DHT listener and `libp2p_serving` block as the published deployment (decision 9), so the check observes the configuration that will serve. The earlier HTTPS part of this mode, a loopback provider listener that answered only an identity-bound probe, is withdrawn by book *Author decisions* item 7 (open question 5). This needs a daemon change, alongside the start-drained option.
21. **One `data_dir` base per wallet, recorded.** The book requires every process signing with one wallet to use one `data_dir` base. Consumer profiles carry their own `data_dir`, and the consumer keeps its wallet key and accounts under it, so the base cannot simply be fixed to `<app data>/network/`.
    - A new deployment takes the loaded consumer profile's `data_dir` when one is loaded, and `<app data>/network/` otherwise, which is the book's storage layout.
    - The desktop records each signing wallet's base per network identity. It refuses any consumer-profile load, a first load included, or any daemon start, that would give a recorded wallet a second journal.
    - The generated configuration, tokens and provider DHT identity file stay under `<app data>/network/`. The daemon's own `data_dir` is the deployment's base, because the daemon keeps the journal and the deployment's ledger under one `data_dir`.
22. **One published deployment per network and provider wallet.** The book's lifecycle table treats model, price and admission changes as new offers and new agreement terms within a deployment that preserves the old accounts. Distinct identities per model would multiply ledgers whose fee obligations each need that deployment's daemon to run before they can be remitted. Every share with the same wallet on the same network therefore reuses one deployment. When the shared model does not serve some existing accounts under the daemon's execution-compatibility rule, the wizard lists them with their exact liability and requires acknowledgement before publishing. That rule never lets an unprofiled model serve an account agreed under a serving profile, so a free share of the same model lists the deployment's funded qualified accounts as unserved. One deployment per wallet is also what keeps a share under one wallet and peer ID through its launch window, its in-place promotion and every price change, so the launch reputation that a catalog keeps for that identity continues (decisions 37–39). The author may prefer one deployment per model or profile (open question 9).
23. **A calibration-only consumer context.** The calibration endpoint is literal-loopback HTTP, which the native consumer accepts only in development. Turning development on in the user's loaded profile would relax its origin rules for every network action. The guide instead builds a separate development consumer profile.
    - Qualification therefore uses a consumer context limited to the calibration endpoint, with no catalog or DHT, keeping the paying wallet's journal under its recorded base.
    - When the loaded consumer wallet pays, that context shares the profile's base and account state. It must then run under the loaded consumer's coordination, for example as an endpoint-scoped allowance inside the native consumer, not as a second instance on the same state directory, whose in-process mutation lock would not be shared.
    - Calibration accounts are labeled as calibration wherever accounts are listed.
    - Withdrawn by book *Author decisions* item 7: an earlier rule kept calibration listeners off the share's provider listener port, because an HTTPS share's ingress would have forwarded that port from the Internet. A desktop share has no HTTPS ingress and every calibration listener is literal loopback, so that reason no longer applies.
    - Reinstated for a different reason by decision 38: the calibration deployment now runs while the published deployment is paused but still running, so every calibration listener must use a port distinct from every published-deployment listener, simply so both can bind. The reference calibration's use of `127.0.0.1:9419`, the published deployment's default HTTP port, therefore changes for desktop shares.
24. **Competing local loads.** Milestone 1 lets any further model load that passes its own fit check. The book says local use must not silently degrade a qualified commitment, and that competing workloads can invalidate performance.
    - During qualification any local load is refused, including a load of the installation under qualification, because it would corrupt the memory and timing measurement the budget pays for. A local load of that installation would also run the model a second time beside the calibration daemon.
    - While sharing, a load on overlapping devices (always, on unified memory) requires an explicit acknowledgement each time. The acknowledgement names paid misses, waivers and the durable withdrawal latch that resume and refresh do not clear. The load is not refused outright, because the book does not claim exclusive GPU ownership and the user may accept the risk. For a free share, which has no speed class, waiver or withdrawal latch, the acknowledgement states instead that the load competes with the share's consumers for memory and compute.
25. **The bundled daemon, a verified policy for every daemon, and one policy authority.**
    - The desktop runs only the `chiral_daemon` shipped in its own installation, bundled as a Tauri sidecar (`externalBin`) and spawned natively, not through a webview shell permission. It refuses a different version, because that binary receives the signing-key path and administrator token and must share the desktop's policy and wire contract.
    - Guide §3 requires the signed policy in calibration too, so no desktop-managed daemon uses development mode to skip `--version-policy`.
    - The runtime resolves the `CHIRAL_POLICY_PUBLIC_KEY` override from the environment. The minimal child environment would drop it, so the desktop and the daemon could trust different authorities. The variable, which holds a public key, is therefore passed explicitly when the desktop's own authority comes from it, and is absent otherwise.
26. **Application quit requests are intercepted while sharing or qualifying.** The book requires that a share never end without the drain and liability display, and that Quit's confirmation list active shares before stopping them. A.2 notes that Cmd+Q bypasses the modal today.
    - While a share or run is active, an interceptable application quit request (in Tauri, a preventable exit request such as Cmd+Q or the macOS application menu's Quit) is prevented and opens the same confirmation.
    - Operating-system shutdown, restart or session end, and termination signals, are never blocked. For them only, the native exit handler drains and stops the daemons without the display.
    - Once a confirmed quit has stopped everything, the exit request that follows the window's destruction is not prevented. When nothing is shared or qualifying, quit requests behave as today.
27. **Stop qualification.** A run needs its own stop, because before publication there is no share for *Stop sharing* to act on. *Stop qualification* follows the guide's interruption rules: stop new dispatch, let in-flight paid requests finish or reach their deadline (or stop now), keep the journal and ledgers for reconciliation, and stop the calibration daemon gracefully. A stopped run never emits a qualified ModelSpec, and its output identity is never reused. Logout refusal while qualifying points to it, and confirmed Quit performs it before `logout`. Revised for decision 38: since the run now happens while the share is published, "before publication" no longer holds; *Stop qualification* stays separate from *Stop sharing* because it ends only the run, and then ends the published deployment's pause so the share serves free again. A scheduled run that has not started is cancelled instead, which lapses its approval without spending.
28. **Automatic fee remittance is disclosed, not disabled.** The daemon's maintenance refresh, which a drain does not stop, remits fee batches at the book's default aggregation thresholds. Disabling it would leave provider fee obligations unremitted, against the book's default. The change instead discloses automatic remittance in the provider-identity step, the qualification budget statement, the publish disclosure and the dashboard. Only forced remittance (`fees/remit`) is an explicit user choice, consistent with the guide's rule that `fees/remit` stays out of qualification automation.
29. **Free shares skip qualification (book *Author decisions* item 1).** The book allows a generation share whose input price, output price and minimum funding are all zero to publish without the speed qualification, after the daemon's readiness probes, with no speed class or waiver and the label *Unqualified — no speed guarantee* wherever consumers see it. Paid shares still require qualification, and setting any nonzero price requires qualification first.
    - **Where the choice is made.** Revised again for the replacement book *Author decisions* items 8–11 (decisions 37–42). Every new share, generation or embedding, is first published free, and a new generation share is first published without a serving profile, whether or not a budget is approved. Step 4 no longer chooses between a free path and a paid path: it either approves the budget of the run that happens later while the share serves (decision 38) or shares without qualification. A nonzero price comes later, from Auto-price or manual pricing, by repricing in place (decision 42), and only once the share has a valid qualification. The earlier choice in step 4, and *Charge for this model* (decision 35), are withdrawn.
    - **Readiness probes.** The "lighter readiness probe" the old open question asked about is the daemon's existing readiness probe: tokenizer and template identity, a capability probe of every advertised endpoint, and a real inference with usage accounting. It runs on the published deployment, started drained, and publication waits for it. No calibration deployment, paying wallet, budget, journal or evidence is involved.
    - **Native configuration.** `ProviderConfig::validate` rejects unprofiled generation outside development whatever its prices. The production rule lives in the pending `specify-inference-commercial-terms` (*Native deployment constraints cannot be bypassed by declaration validity*). This change modifies that requirement, adding only the exception: a generation model whose token rates are both zero may be configured and published with `serving: null` outside development, its offers carry `min_funding_wei = "0"` (which the daemon already emits for a free model), and it claims no speed class, capacity tier or qualification identity. Priced unprofiled generation is still rejected, private calibration still authorizes nothing, and qualified and unprofiled models still never share one process, which one model per share already ensures. Using development mode to publish a free share would relax origin and listener rules, so the desktop never does it. The modified requirement makes this change depend on archiving `specify-inference-commercial-terms` first, and on rebasing if that change's copy of the requirement is revised.
    - **Execution compatibility.** Accounts agreed under a serving profile are never served by an unprofiled model. Accounts opened under an unprofiled free share are served by a later qualified configuration of the same model only under the pre-promotion free-agreement exception (decision 45), within their allowance and with no speed promise. Free accounts carry no balance, so only the deployment's funded qualified accounts appear in the unserved-accounts acknowledgement (decision 22).
    - **Admission.** A free share whose model has no serving profile has only concurrency slots, no arrival envelope (decision 11). Its daemon has no performance-withdrawal latch to show, and no waiver applies. After promotion a free share has its serving profile, its arrival envelope and the latch (decision 39).
    - **Gas.** A free opening has zero funding, so its fee is `floor(0 × 50 / 10,000) = 0` and it creates no fee obligation. The daemon still remits any obligation the reused deployment already holds. The book's step 2 says the wallet needs CFX for fee-remittance gas and makes no exception for free shares, so the gas requirement for publishing applies to a free share as to any other, and the wizard adds that the free share's own openings create no fee obligation. Exempting a free share whose deployment holds no unremitted obligation would avoid requiring gas the daemon may never spend, but it goes beyond the book, so it is left to the author (open question 12).
    - **Backends.** A free share needs no qualifying memory counter, context of 4,096 or output of 256, so it may run on any backend milestone 1 can load, including CPU and Vulkan, as long as it passes the fit check. It still carries no speed class and is not a speed certification, and because a nonzero price needs a valid qualification, Auto-price never raises its price.
30. **Consumers see *Unqualified — no speed guarantee*.** The book requires the label wherever consumers see a free share, and A.4's *Serving profile* gives its text. No main spec or pending change defines the Marketplace or other consumer display of a missing serving profile; `specify-p2p-provider-transport` covers only transports and path on those surfaces and states that a free offer shows no speed class. This change therefore adds a requirement in `desktop-share-online` (*Unqualified generation offers are labeled for consumers*) rather than inventing a new capability. The label is derived from the signed declaration alone: a model that advertises `chat` or `completions` with `serving: null`. It does not depend on price, so a priced unprofiled offer that a misconfigured or dishonest provider signs is labeled the same way, which is true of it. Embedding-only offers keep A.4's statement that no generation-speed guarantee applies. Machine-readable CLI output already carries the signed `serving: null` and gains no derived field here; adding one would be a CLI interface change outside this milestone.
31. **Sleep prevention is automatic after preselected consent (book *Author decisions* item 4).** The wizard asks with the option *Prevent idle system sleep while sharing* preselected, and proceeding with it selected records consent. With consent, prevention is held automatically whenever a share is active, and also while a qualification run is in progress, because sleep during a run wastes the approved budget; it is released when they stop. The option appears in the qualification step before a budget is approved (for a share that qualifies) and in the publish step (for every share). Consent is revocable in Settings or on the dashboard. Lid-close and user-initiated sleep are never blocked (decision 15). The book says the wizard asks with the option preselected and makes no exception, so the option is preselected every time the wizard asks, including after a decline or revocation. A revocation stays in effect for the running share and until the user next proceeds through the wizard with the option selected. Whether a later wizard should instead remember a revocation and show the option cleared is left to the author (open question 13).
32. **Relays come from the provider profile, with no fee (book *Author decisions* item 2).** The project operates serving-capable testnet relays named in shipped profiles, and a provider may also list relays anyone else operates. The provider profile's `relays` field already carries the list, so a shipped profile may name the project relays and a user may select another profile. Relays charge no fee and add no payment, agreement or term, so the wizard shows none. Serving-grade circuit sizing and per-provider quotas are milestone 3's, and running any relay is a separately authorized deployment. The relayed path of task 2.8 therefore waits only on milestone 3's implementation and an authorized, operating serving relay, not on an author decision.
33. **Desktop shares are libp2p-only (book *Author decisions* item 7).** The share wizard offers no HTTPS origin. As the book's *Share online* step 3 explains, nothing outside the machine can yet confirm that a user-operated HTTPS origin reaches this app: open question 5 found no relay probe endpoint and no way to bind an origin's response to this daemon's identity.
    - **HTTPS providers.** A provider that wants an HTTPS origin runs `chiral_daemon` with the provider guide and its preflight. The reachability step says so, and the existing Provider page (A.5.5) keeps administering such daemons unchanged. An HTTPS option, with an external identity-bound probe, may return in a later change. HTTPS remains a valid provider transport in general: milestone 3's signed `transports` field keeps `https`, and consumers, including this desktop's consumer pages, still reach HTTPS providers.
    - **Configuration and offers.** Every desktop share's daemon configuration has a `null` `public_endpoint` and a `libp2p_serving` block (decision 9). Milestone 3 derives `transports` from configuration, so the share's offers are schema v2 offers declaring `["libp2p"]` with a `null` `endpoint`, signed with the deployment's peer ID. The wizard accepts no HTTP origin or endpoint of any kind, so it cannot select milestone 2's local API server as a share endpoint.
    - **Offer schema (book *Author decisions* item 5, milestone 3's).** Schema v1 is dropped with no acceptance window. New-schema offers are published only on `/chiral/inference/manifest/2`, and upgraded nodes stop publishing, discovering, quoting and funding v1 offers. As the book's *Wire change* now words it, this governs only new discovery, quotes and accounts: top-ups, requests and recovery of an existing account continue under its saved terms. Nothing here depends on a v1 cutoff or a v1 counterpart: a libp2p-only offer cannot be expressed in v1, which requires a non-null `endpoint`, and every offer the desktop's bundled daemon signs is schema v2. Keeping persisted v1 terms in saved accounts verifiable is milestone 3's rule; desktop deployments, which never published v1 offers, add no v1 state for it.
    - **Removed by this decision:** the HTTPS reachability option, origin validation and ingress guidance (task 2.7, withdrawn); the HTTPS part of the reachability-check mode (decision 20, task 2.5); the rule keeping calibration off the share's provider listener port (decision 23); and the HTTPS smoke test and release gate.
    - **Dependency.** Before milestone 3, HTTPS was the only path to publishing. Now every share needs milestone 3: until it is implemented, the reachability step is unavailable, so no reachability check runs, no qualification budget is requested through the wizard and no share, free or paid, is published. Tasks can be built and tested against test doubles before then. This change is archived after `specify-p2p-provider-transport` (task 1.6).
34. **The relayed-grace statement (book *Author decisions* item 6).** Milestone 3 owns the relay rule. A serving relay grants serving-grade circuits to a destination peer that has a currently valid signed offer, verified from its own authenticated manifest, or had one that expired within the last 24 hours. Clarified 2026-11-16 (book *Relays carry ciphertext, under explicit limits*): the 24 hours count from the signed `expires_at` of the most recent offer the relay itself verified for that peer, which the relay already stores in its evidence record, so the grace ends 24 hours after that `expires_at`. This replaces this decision's earlier anchor, the time of the relay's most recent verification. The same per-provider quotas apply, and milestone 3 specifies the bounded, durable evidence a relay keeps: a relay restart does not end a grace period, and only eviction from a full evidence store or a failed store can end it earlier, while the per-provider quotas limit circuits during it without ending it. The grace covers every way this machine's daemon can run without a current offer: drain, *Stop sharing* while it drains and waits, a chain-outage publication pause, and a performance-withdrawal latch.
    - The drain action (and the qualification pause, which withdraws offers as a drain does, decision 38), the dashboard while a relayed share has no current offer, and the *Stop sharing* and Quit confirmations therefore give one statement. While the daemon runs, serving relays keep carrying request status, receipts, cancellation and existing accounts until 24 hours after this machine's most recent offer verified by the relay expires. After that, consumers may lose access to them through the relay unless a direct or hole-punched path is established. A relay whose evidence store is full or has failed can end the grace earlier: milestone 3 keeps a relay's grace evidence (one bounded record per destination peer ID and network) durably, so a relay restart does not end it, but bounds the records by an operator-configured relay-wide quota and, when that quota is full, evicts the record with the earliest grace end; a store that fails fails closed for grace. This statement discloses that early end to the provider.
    - "While the daemon runs" matters because the grace keeps a relay willing to carry circuits; it does not make a stopped daemon answer. *Stop sharing* and Quit therefore also say that once the daemon has stopped, the provider is unavailable on every path until this machine shares again.
    - The end is a bound, not an exact time, because each relay counts from the most recent offer it verified, which the desktop cannot observe. A relay can verify only offers this machine's daemon published, so no relay's grace outlasts 24 hours after the `expires_at` of the last offer the daemon published. The dashboard therefore shows the `expires_at` of the last offer it observed in the daemon's published-offer list and the time 24 hours after it, labeled as the latest time the grace can end. A relay that verified only an earlier offer, or whose evidence store is full or has failed, ends it sooner. The desktop reads that list again immediately before a drain it performs. When the daemon withdraws offers on its own (a chain-outage pause or a performance latch), an offer refreshed after the desktop's last read can make the true bound later than the one shown; polling the list at least as often as the daemon refreshes offers limits that gap to one refresh interval.
    - The grace changes no money, terms or accounts. Milestone 3's circuit-budget check before paid dispatch still applies. Direct and hole-punched paths do not depend on a relay, so the statement is given only for a relayed path. Tasks 2.16 and 2.20 are no longer blocked on an author decision; their relayed parts wait on milestone 3's implementation, like every libp2p part.
35. **Superseded: free is the default share, and charging is an explicit upgrade (the earlier book *Author decisions* item 8).** Superseded in place by the replacement items 8–11 of the book's 2026-11-16 revision, which decisions 37–42 apply. This decision made every new share start free and made charging an explicit *Charge for this model* upgrade: it drained and stopped a running free share, qualified on the idle machine within a separately approved budget, and published the paid share from the same deployment. Its requirement *New shares start free* is replaced by *New shares start free in a launch window*, and its requirement *Charging for a shared model is an explicit upgrade* is removed. The replacement keeps what this decision established elsewhere: a new share inherits nothing from an earlier one as a preselected choice; *Share again* is not a new share and offers its accepted terms unchanged; a share keeps one deployment, wallet and peer ID for its whole life; free accounts leave no liability; free service never substitutes for qualification (decision 38); and nothing restarts automatically after a failure (decision 13).
36. **Superseded: free service earns no ratings, and the track record is disclosed (the earlier book *Author decisions* item 9).** Superseded in place by decision 43, which applies the replacement item 9 (launch reputation). This decision disclosed, and optionally showed on the dashboard, the uptime-only catalog track record of `specify-provider-track-record` (now `specify-provider-launch-reputation`), read from the loaded consumer profile's catalog. Decision 43 keeps its rules that free sessions still cannot vote, that catalog figures are shown beside and never blended into the payment-gated score, that the desktop never computes them, and that milestone 5 is a release dependency, not an archive-order dependency.
37. **The launch window (book *Author decisions* items 8 and 11).** The requirement *New shares start free in a launch window* applies it.
    - **Every new share is first published free.** Its rates and minimum funding are `"0"`, its offers carry the free allowance (decision 40), and a generation share has no serving profile (decision 29). There is no longer a paid path before publication: the book runs qualification "in the first quiet hour of the window", that is, on the published share (decision 38), and makes the launch window the default. The first consequence that open question 14 asked about, charging before anything is published free, therefore no longer exists.
    - **Length.** With Auto-price on, the window lasts at least 24 hours by the desktop's clock and ends only at a review whose up rule holds, so its earliest end is the 24-hour review. The desktop's own 24-hour minimum is added to the catalog's "at least 24 hours observed" because the catalog counts observation per provider identity, and a wallet with earlier shares may already have 24 hours; the book promises at least 24 hours of free service for the new share.
    - **Floor.** The floor does not apply during the window, because the book has the window free and starts Auto-price's pricing "after the window".
    - **Manual pricing has no window.** The book says that unchecking Auto-price "restores manual pricing", and that the launch reputation is "a signal, not a gate". A share in manual pricing may therefore charge as soon as it has a valid qualification, and the confirmation tells the provider that consumers see an incomplete launch reputation (decision 42).
    - **Sharing again.** *Share again* keeps the stopped share's accepted terms, including its Auto-price target, floor and step, because otherwise prepaid accounts could not be served again (decision 35's reading, kept). A share that has left its window does not re-enter it: a later step down to free is a free period in which the catalog probes again, not a new launch window.
38. **Automatic qualification in the first quiet hour (book *Share online* step 4).** The requirement *Qualification runs automatically in the share's first quiet hour* applies it, with the changes to *Paid generation shares require in-app qualification within an approved budget*, *Qualification evidence is journaled and never fabricated* and *A qualification run can be stopped explicitly*.
    - **Approval at setup.** The book runs qualification "within the budget approved at setup". The budget formula, exact funding order, distinct paying wallet and hard cap are unchanged (decisions 5 and 7). An approval authorizes exactly one run and lapses unspent when the share stops, when settings change or when the user cancels it, so no spending outlives the context in which it was approved. Another run needs a new approval, as another attempt always did. *Share without qualification* publishes the share free and unqualified, and the dashboard offers the approval later.
    - **The quiet hour, concretely.** The book does not define it. This change chooses a one-hour warm-up after the first publication, so that the share first serves and is observed as published, and a provider that stops at once spends nothing; then the first moment with no request admitted for 15 minutes and none in flight, which begins the quiet hour; and a fallback 12 hours after the first publication, so that a busy share is still qualified in time for the 24-hour review to find it so. "Hour" names when the run starts, not a limit on its length; the dashboard shows an estimated duration. These constants are this change's implementation choices, not author decisions, and a revision backed by measurement updates this decision.
    - **Pause rather than stop.** The book has free admission pause "with a retryable busy response, because other traffic on the same devices would invalidate the measurement", and the model is never loaded twice (decision 18). The published daemon therefore keeps running, with its identity, reservations, ledger, maintenance and fee remittance, but stops its engine, so that the calibration daemon can launch its own. It withdraws its offers as a drain does, for two reasons: an offer would keep inviting openings it cannot serve, and with no current offer the catalog has nothing to probe, so the pause is counted once, as unavailable samples, and not again as failed probes. Requests that still arrive, from existing accounts or cached offers, get HTTP 503 `qualification_in_progress` with `Retry-After`, the busy response the book names. It uses 503 like the existing `provider_draining`, and the code is this change's. Milestone 5's current draft classifies a probe that meets this response as busy, and one that finds no offer as unreached; both are excluded from probe success, and neither ends the free period. On a relayed path the pause leaves no current offer, so the relayed grace and its statement apply (decision 34).
    - **The measurement is unchanged.** The calibration deployment, journal, runner, evidence parity and budget cap are unchanged. Only two rules change: the calibration deployment now runs beside the paused published deployment, so its ports must differ (decision 23), and it never runs while a published engine is loaded.
    - **No maintenance exemption.** Book *Launch reputation* counts a sample unavailable when the provider offers nothing valid or is not ready, and has no maintenance exemption; a self-declared one would let a provider hide downtime. The pause therefore counts as unavailable. Its effect on the 95% ready-to-charge bar: 5% of the first 24 hours is 72 minutes, so a run of D minutes leaves 72 − D minutes for any other unavailability; a 60-minute run leaves 12 minutes. When that margin is exceeded, the window simply lasts longer: one 60-minute pause costs about 2.1% of 48 hours. The qualification step and the dashboard show the estimate and this effect.
    - **Outcomes.** A passing run is promoted (decision 39). After a failed or stopped run, the published daemon launches its engine again with its unchanged configuration and resumes after readiness, so the share stays free and is retryable, as the book requires.
    - **Planned steps are not automatic restarts.** The lifecycle table forbids an automatic engine restart after a managed-child failure. The engine stops and launches here are planned steps of a run the user approved. A daemon failure during them stops the run and is never retried automatically.
    - **Recovery continues during the pause.** Only new inference requests and new openings are refused. Request status, receipts, cancellation, account inspection and the crediting of funding acknowledged before the pause continue, because ambiguous-outcome recovery and acknowledged funding must never depend on the engine being loaded.
    - **Only unprofiled shares are qualified in place.** A run is offered only while the share's model carries no serving profile, which is also the only state in which the share is necessarily free. A profiled model, including one withdrawn by a performance-withdrawal latch, may have accounts with prepaid balances under its profile; pausing it would interrupt paid service, and a failed run's outcome, the unprofiled free configuration, would strip the profile those accounts were opened under. Re-qualifying a profiled share, for example by evidence-only renewal, is outside this change.
    - **Daemon change.** The qualification pause and its end are operator-only actions on the loopback administration listener (task 2.29).
39. **Promotion into the published deployment in place, and qualified free offers.** The requirement *A passing run is promoted into the published deployment in place* applies it.
    - **Same identity.** Decision 22 keeps one published deployment per wallet, and the earlier upgrade already published the paid share from the free share's deployment. Promotion likewise restarts that deployment with the qualified ModelSpec, keeping its wallet, peer ID, ledger and revision counter, so the launch reputation that a catalog keeps for that identity continues. The guide's promotion into a fresh deployment (decision 2) remains the procedure for `chiral_daemon` operators.
    - **A restart, not a hot swap.** The lifecycle is configuration-driven and the serving profile is an execution term, so promotion is a graceful restart while the share is already paused, followed by native revalidation, readiness, the final reachability check and resume. It needs no further prompt, because the disclosure accepted at publication describes it.
    - **The profile stays at every price, free included.** There are three reasons. First, a later step down to free must not change execution terms, or paid accounts with balances would stop being served, because an unprofiled model never serves an account agreed under a serving profile. Second, with execution terms fixed, a price change is only an offer revision (decision 42), never a restart. Third, the book's *ready to charge* includes "a valid qualification", and the provider becomes ready only at the end of a free period. Milestone 5's current draft leaves that check to the provider's own Auto-price and to consumers, who check the signed offer's serving profile; a free offer that carries the profile lets consumers see, during the launch window, the qualification the provider will charge under. The MODIFIED native-deployment requirement needs no further change: its exception covers a free model without a serving profile, and a free model with one satisfies the unmodified rule.
    - **Consequences of a qualified free offer.** Free accounts opened after the promotion are agreements under a serving profile. Their in-envelope misses settle with a waiver of a cost that is zero, and count toward the durable withdrawal latch, which then withdraws the model at every price. The dashboard says so. Decided 2026-11-16 by the author (book *Share online* step 4): free requests under the profile count toward the withdrawal latch, because the speed claim must hold under all admitted load (open question 15). Free accounts opened before the promotion are not agreements under the profile and are not performance-accounted (decision 45).
    - **Free accounts opened before the promotion.** Superseded 2026-11-16 by the author's decision (book *Share online* step 4; open question 15): they keep being served after the promotion under their allowance, with the same model and settings and no speed promise (decision 45). The earlier reading, that they were no longer served because adding a serving profile is not evidence-only renewal, is withdrawn.
    - **Failure.** If revalidation, readiness or the reachability check fails, the deployment stays drained, and the user chooses to retry the promotion or to restore the unqualified free configuration; neither happens automatically (decision 13).
40. **The free allowance (book *Author decisions* item 10).** The requirement *Free offers carry a signed free allowance* applies it. Milestone 3 owns the signed `free_allowance` field (`tokens` and `lifetime_secs`), its bounds, its enforcement per account and its display to consumers; this change chooses the values and writes them into the daemon configuration. The defaults are 20,000 tokens and 86,400 seconds, the book's defaults and milestone 3's native default. The user may change them within milestone 3's bounds, and a value outside them is refused rather than clamped, like every exact value (A.1.4). A change is a new offer revision (decision 42), and milestone 3 keeps every opened account's allowance. An allowance's lifetime runs from the account's opening on the provider's clock, including while the share is paused, drained or stopped, as milestone 3 specifies, and the Share page says so. A nonzero step publishes a `null` allowance; a return to free publishes the configured allowance again. Free accounts also count toward the commercial terms' free-opening caps of eight per payer wallet and 10,000 ledger accounts, which an ended allowance does not release under milestone 3's current text, so a busy launch window can reach the ledger cap.
41. **Auto-price (book *Author decisions* items 8 and 11).** The requirement *Auto-price sets the price from launch reputation* applies it.
    - **On by default, but not everywhere.** The checkbox is selected by default. It is unavailable without a catalog, which leaves it no inputs. It is unavailable for an embedding share, which cannot hold a valid qualification and so is never ready to charge (decision 44, revised 2026-11-17).
    - **Steps and rounding.** The book's "one step among 0, 25, 50, 75 and 100% of the target" leaves rounding open. Each rate is floor(target × s / 100), so that a step never exceeds its share of the target, computed with exact integers (A.1.4). The minimum funding stays at the target's at every nonzero step, because it bounds the smallest opening and its fee rather than pricing tokens, and it is `"0"` at step 0, as the free-opening rule requires. A target whose 25% step rounds both token rates to zero is refused, because a nonzero step with zero rates and a positive minimum is invalid; floor(r × 25 / 100) is at least 1 only when r is at least 4 wei.
    - **Floor.** The floor is one of the steps, preset to 0%. "Never below the floor" applies outside the launch window. Leaving step 0 goes to the larger of 25% and the floor. That is the only move of more than one step, because the floor is the provider's lowest acceptable price once it charges; with a floor of 0% it is one step.
    - **Review timing.** Reviews run every 6 hours from the first publication and never sooner than 6 hours after the previous one, recorded durably, so that restarts cannot speed up price changes: at most four automatic revisions a day. A review due while the daemon cannot reprice (a run, promotion, drain, repricing or not-ready state) runs when that ends.
    - **Reading the rules.** The rules are the book's, read as follows. *Ready to charge* is the catalog's launch criteria (at least 24 hours observed and 100 probes, availability at least 95%, probe success at least 98%, no billing mismatch) together with a valid qualification, which the desktop checks itself, because milestone 5's current draft has the catalog not assess qualification. "Ready at the end of its latest free period" means the catalog's current launch criteria while the share is free, and the criteria the catalog computed at the end of the latest free period while the share charges; only the catalog can report the latter, because probes stop while the provider charges. While the provider charges, its probe success, and so its service score, is the catalog's walk-back over its most recent free periods, newest first, until at least 100 counted probes are included (book *Launch reputation*, author decision 2026-11-16); the desktop reads it as reported. A billing check the catalog cannot perform is reported *unchecked*, is not a mismatch and does not block the launch criteria; the dashboard shows **Billing unchecked** (book *Launch reputation*, author decision 2026-11-16). Down takes precedence over up, because both can hold at once (a service score of 92 is compatible with 94% availability and 98% probe success), and the book has availability and paid votes "drive Auto-price down". "At least 5 votes in 14 days" counts eligible payment-gated votes whose first acceptance falls within the last 14 days. The desktop also checks a valid qualification itself before moving up and before every nonzero step, and the daemon enforces it again when repricing.
    - **Inputs from one catalog, never fabricated.** Inputs come only from the provider profile's `catalog_url` (decision 43). An input is unavailable on a failure or error, a degraded observer, a missing record or field, or figures computed more than 6 hours earlier. Holding when inputs are missing is the conservative reading. It never raises the price on missing evidence, and it never lowers it because the catalog, rather than the provider, had an outage: an unreachable observer is not evidence against the provider. A down move needs one established down condition, and an up move needs every input. Today's `GET /api/ratings/:wallet` decides the payment-gated condition in the common cases: a score of at least 45, or fewer than 5 eligible votes in its 180-day window, rules it out. Only a score below 45 with at least 5 votes needs the 14-day count, which no endpoint reports today.
    - **Facts this change needs from milestone 5.** For a wallet and peer ID: the service score, the 14-day availability, the launch criteria with each unmet criterion, whether the provider is free now, whether the launch criteria were met at the end of its latest free period, the observer status and the computation time; and the count of eligible payment-gated votes in the last 14 days. Milestone 5's current draft serves them at `GET /api/launch-reputation/:wallet/:peer_id` (`service_score_bps`, the wallet's `availability_14d`, `launch_criteria`, `free_now`, `free_periods[].launch_criteria_met_at_end`, `observer_status`, `computed_at`) and adds `votes_14d` to `GET /api/ratings/:wallet`. That change is still being revised, so this change's requirements fix no field names, and task 2.31 reads them from that change's API as finally specified. With `votes_14d` served, the payment-gated condition is always decidable; the reasoning above from the score and the 180-day count covers only a catalog that predates it.
    - **Publication and limits.** Each change is a new offer revision made by repricing in place (decision 42). Milestone 3 makes such a revision ordinary, and it alters no opened account. Auto-price never approves a budget, starts a run or spends.
    - **History.** The dashboard shows the step prices, the current step, the next review, and each review's decision with its inputs and reason. The local history, keeping every review from the last 30 days and at least the last 100 (at most 121, since reviews are at least 6 hours apart), is protected and holds no secrets, so the provider can see why its price moved and check the catalog's figures.
    - **Turning it off and on.** Unchecking keeps the current price, so nothing changes unexpectedly. Checking it again maps the current price to the highest step not above it at the next review, which still respects the 6-hour limit, so toggling cannot bypass it.
42. **Manual pricing and repricing in place.** The requirements *Manual pricing applies when Auto-price is off* and *A running share is repriced by a new signed offer revision* apply it.
    - **Repricing replaces restarts for price changes.** Earlier drafts kept repricing in place out of scope, and the upgrade drained and stopped the free share. Auto-price changes prices every 6 hours, and draining and restarting each time would interrupt service and cost availability that the launch reputation measures. Prices are not execution terms (`ModelSpec::accepts_execution` compares none), and the book's lifecycle table asks of a price change only "their appropriate new offer" with old accounts preserved. A new operator-only administration action therefore applies new token rates, minimum funding and free allowance to a running model, validated as configuration would be, records them durably and publishes a new revision at once (task 2.30). Changes of model, artifact, runtime, hardware, serving profile or admission still need a restart with a new configuration.
    - **Manual pricing.** Prices change only by the user's confirmed action. A nonzero generation price needs a valid qualification, and an embedding input price needs none. Because the launch reputation is a signal, not a gate, the desktop refuses nothing because of it, but states that consumers see an incomplete launch reputation while the catalog does not report the provider ready.
    - **Quotes.** A quote already signed keeps its terms until it expires, so a consumer part-way through an opening is never charged a price it did not accept.
43. **Launch reputation is disclosed and shown, never computed (book *Author decisions* item 9).** This decision supersedes decision 36.
    - **Disclosure.** The book's step 6 now says that reputation reflects only paying users' feedback, that free service earns no ratings, that catalogs observe this machine's availability and, while it is free, probe it and publish a service score, and that with Auto-price on, prices for new accounts change automatically. The publish disclosure adds the launch window, the automatic qualification with its pause and its availability cost, the promotion and its effect on earlier free accounts, and the free allowance.
    - **Catalog source.** The catalog moves from the loaded consumer profile's `catalog_url` (decision 36) to a new nullable `catalog_url` in the provider profile, because Auto-price needs a catalog whenever a share runs, and a share needs no consumer profile. The catalog must report the provider profile's network identity, and a shipped provider profile may name the project's catalog.
    - **Dashboard.** The display is now required when a catalog is configured, because Auto-price acts on it. It shows the figures exactly as the catalog reports them, with its origin and computation time, beside and never blended into the payment-gated score. The desktop never computes, estimates, samples or probes them itself: self-observation is exactly what the catalog's observer exists to avoid. Otherwise the dashboard says that the catalog reports no launch reputation yet, or that it is unavailable.
    - **Release dependency, not archive order.** *Status and milestones* requires milestone 5 before launch windows or Auto-price are presented as available. Every new share starts in a launch window by default, so in practice this gates presenting sharing at all (task 3.7). This change refers to milestone 5 by change name only, so the two changes can be archived in either order. Milestone 5 can track a libp2p-only provider only once milestone 3 is implemented, which every desktop share already needs.
44. **Embedding shares use manual pricing; Auto-price is unavailable for them.** Revised 2026-11-17, superseding the 2026-11-16 revision below. The book's *Launch reputation* defines *ready to charge* as "At least 24 hours observed and 100 probes, availability at least 95%, probe success at least 98%, no billing mismatch, and a valid qualification." An embedding share cannot hold a valid qualification, so it can never be ready to charge, and Auto-price, whose up rule needs readiness, could only hold it free. Auto-price is therefore unavailable for an embedding share, with that reason shown; the share has no launch window, and its input price becomes nonzero only by manual pricing, which needs no qualification for an embedding share, with a zero output price. Its first publication is still free. No Auto-price rule moves an embedding share's price. *Superseded 2026-11-17:* the 2026-11-16 revision, an assistant default that contradicted the book, read: Revised 2026-11-16 (open question 16, decided as an implementation decision the author may revisit). As first drafted, Auto-price was unavailable for embedding shares, because the ready-to-charge result required a valid qualification, which an embedding share cannot have, and the book's probes and billing-honesty check describe generation requests. Now milestone 5 (`specify-provider-launch-reputation`) defines readiness for embedding offers: the same launch criteria without qualification, from embeddings probes on `/v1/embeddings` and a billing check on input tokens. Auto-price is therefore available for an embedding share, with the same steps, reviews, inputs and down rules; its up rule needs those launch criteria and no qualification, and every step keeps a zero output rate. Manual pricing, whose nonzero input price needs no qualification, remains. Its first publication is still free. This change refers to milestone 5 by change name only, so this adds no archive-order dependency.
45. **Free accounts opened before a promotion keep being served (book *Share online* step 4, author decision 2026-11-16).** When a run passes, the share gains its qualified profile and keeps serving the free accounts opened before it under their allowance, with the same model and settings and no speed promise. Under `specify-inference-commercial-terms`, adding a serving profile is not evidence-only renewal, so a profiled model would refuse those agreements. This change therefore modifies *Existing agreements permit only evidence-only renewal of identical terms* with one exception, which is not renewal: an agreement opened in a deployment under a free generation offer with `serving: null`, zero rates and minimum funding, and a signed free allowance stays executable by the same deployment's model after a serving profile is added, when every other execution term is identical.
    - **What the exception keeps.** The agreement keeps its own terms: served only within its signed allowance, at zero cost, under the free-opening and allowance rules it had. It acquires no speed class, qualification identity, remedy or waiver, is not performance-accounted and does not count toward the withdrawal latch, because it never agreed to a profile. Accounts opened after the promotion under qualified free offers are agreements under the profile and do follow the performance rules (decision 39).
    - **What it does not change.** Removing a profile still ends service to profiled agreements; any other change of model, artifact, limits or settings still ends execution compatibility; an unprofiled agreement with a nonzero price is never served by a profiled model (none can exist outside development). The exception is keyed to the same deployment, so a different deployment identity never inherits it.
    - **Promotion.** Promotion changes only the ModelSpec's serving profile and evidence (decision 39), so it falls within the exception. A failed promotion restored to the unqualified configuration serves those accounts unchanged. The publish disclosure says so in advance, and the dashboard counts the pre-promotion free accounts still open with allowance left.
    - **Archive order.** The modification is a second MODIFIED requirement of the pending `inference-commercial-terms`, so `specify-inference-commercial-terms` still archives first (task 1.6); it relies on `specify-p2p-provider-transport`'s signed `free_allowance`, which also archives first.
    - **Retry-After for the qualification pause.** The pause's HTTP 503 `qualification_in_progress` carries `Retry-After` as an integer number of seconds from 1 to 3,600, the estimated remaining pause rounded up and clamped, because milestone 2 passes the header on only within that range and native consumers (milestone 3) treat the response as retryable and not admitted, never retrying it automatically as a paid request (implementation decisions of 2026-11-16 the author may revisit).

## Non-goals and limitations

**Not specified here**
- The libp2p transport, NAT traversal, relay limits and operation (milestone 3).
- Model download, installation, runtime installation and local chat (milestone 1).
- The local API server (milestone 2).
- Sharing several models at once, changing serving settings in place, and hot-swapping weights. To change those terms, stop sharing and share again. The old agreements keep their accepted terms. Prices, minimum funding and the free allowance, by contrast, now change in place by new offer revisions (decision 42).
- Observing, probing, computing or storing a launch reputation, and its Marketplace display (milestone 5). This change discloses it, shows what the provider's catalog reports, and reads it for Auto-price (decisions 41 and 43).
- The `free_allowance` offer field, its bounds, its enforcement and its consumer display (milestone 3). This change only chooses the values (decision 40).
- Relay deployment. Book *Author decisions* item 2 names project-operated relays, but running one is a separately authorized deployment, and its limits and quotas belong to milestone 3.
- Setting up TLS, ACME, DNS, port forwarding or router configuration; LAN or public exposure of administration or the engine.
- An HTTPS origin for a desktop share (book *Author decisions* item 7, decision 33). HTTPS providers run `chiral_daemon` with the provider guide and its preflight; an HTTPS option with an external probe may return in a later change.
- Start-at-login, background sharing after the desktop exits, or a headless desktop provider. Operators who want those use `chiral_daemon` directly.
- Desktop upgrades while sharing, and automated backups. The operator rules (drain, consistent protected backup, no restoring stale ledgers) apply unchanged, but the desktop gains no backup feature here.
- Moving a deployment or a wallet journal to another `data_dir` base.

**Never part of sharing**
- GPU rental, customer shell access, training, combining strangers' VRAM, or independent attestation of execution.
- Treating earnings as profit, or providing tax or accounting reporting.

**Unchanged**
- The existing Provider page (A.5.5) for externally operated providers.
- Milestone 1's requirements: this change relies on their share carve-outs and modifies none of them.

**Limitations**
- **Platforms:** CPU and Vulkan cannot qualify paid generation, because the runner has no qualifying memory counter for them; they can serve only free shares, which carry no speed class. Windows and macOS qualification remain open release gates. On Linux, idle-sleep prevention depends on the desktop environment honoring logind's idle inhibitor.
- **Abrupt termination:** abruptly killing the desktop on macOS can leave the daemon orphaned; it is detected at the next start, not prevented. Operating-system shutdown ends a share without the liability display.
- **Engine confinement:** the engine is not an OS sandbox, and while a model is shared it also processes requests from remote consumers. The book makes OS confinement that denies the engine the `network/` and `local-server/` directories a release-gate item. This change discloses the risk but does not provide confinement, and sharing is not presented as available while that gate is open (open question 11, task 3.7).
- **Milestone 3 dependency:** desktop shares are libp2p-only, so until milestone 3 is implemented the wizard stops at the reachability step and nothing can be published (decision 33).
- **Relayed recovery after offers lapse:** on a relayed path, a share without a current valid offer keeps serving-grade circuits until 24 hours after the signed `expires_at` of its most recent offer that the relay verified (book *Author decisions* item 6), and a relay whose evidence store is full or has failed can end that earlier, because milestone 3 bounds a relay's durable grace evidence by a relay-wide quota, and fails closed for grace when that store fails. After that, consumers may lose access to request status, receipts, cancellation and existing accounts through the relay unless a direct or hole-punched path is established. This change discloses it (decision 34) and does not change the relay rule, which is milestone 3's.
- **Budget bound:** the budget is an upper bound on reserved cost; actual spending is usually lower, and the agreement count includes a headroom chosen by this change.
- **Qualification pause:** the automatic run takes the share offline from the pause until it resumes, free after a failed run or with its serving profile after a passing one, and the pause counts as unavailable in the launch reputation, using part of the 72 minutes that 95% availability allows in the first 24 hours (decision 38).
- **Free accounts at promotion:** free accounts opened before a passing run's promotion keep being served after it within their allowance, with no speed promise and no performance remedy (decision 45; open question 15, decided 2026-11-16).
- **Auto-price depends on one catalog:** Auto-price follows one catalog's observation and holds when that catalog is unavailable; another catalog can disagree, and a provider can switch to manual pricing (decision 41).
- **Launch reputation:** launch windows and Auto-price, and therefore sharing, are not presented as available until milestone 5, the catalog's launch reputation, is implemented (book *Status and milestones*; decision 43, task 3.7).
- **Public rollout:** no public rollout is authorized. Release gate 7 (the desktop sharing lifecycle: sleep, quit, and stop sharing with outstanding liabilities) and the qualification gates remain.

## Open questions

1. **Free sharing without qualification** (book *Author decisions* item 1). Decided 2026-11-16 (book *Author decisions* item 1): allowed. A generation share whose input price, output price and minimum funding are all zero may publish with `serving: null` after the daemon's readiness probes (exact template, tokenization and capability probes plus a real inference with usage) instead of the speed qualification. It carries no speed class and no waiver, and is labeled *Unqualified — no speed guarantee* wherever consumers see it. Paid shares still require qualification, and setting any nonzero price requires qualification first. The requirement *Free and embedding shares publish after readiness without speed qualification* (which replaces *Embedding and price-zero generation shares follow the qualification rule in force*), the new *Unqualified generation offers are labeled for consumers*, the MODIFIED `inference-commercial-terms` requirement and decisions 29 and 30 apply it. Task 2.13 is no longer blocked. Book *Author decisions* item 8 later made free the default for every new share, with charging as an explicit upgrade (decision 35); its replacement, items 8–11, makes every new share start free in a launch window, priced afterwards by Auto-price or manually once qualified (decisions 37–42).
2. **Default for sleep prevention** (book *Author decisions* item 4). Decided 2026-11-16 (book *Author decisions* item 4): automatic while sharing. The share wizard asks for consent with the option preselected; with consent the app prevents idle system sleep whenever a share is active and releases it when sharing stops; consent is revocable in Settings or on the dashboard; lid-close and user-initiated sleep are never blocked. *Idle system sleep is prevented automatically while sharing, with consent* and decision 31 apply it. Task 2.19 is no longer blocked.
3. **Relay operation** (book *Author decisions* item 2), owned by milestone 3. Decided 2026-11-16 (book *Author decisions* item 2): the project operates serving-capable testnet relays named in shipped profiles, and providers may also list relays anyone else operates. Relays charge no fee and add no payment, agreement or term to the inference protocol. A serving-grade circuit on a project relay must at least carry one paid request, project relays enforce per-provider reservation, circuit and bandwidth quotas, and the exact values are fixed and measured within milestone 3. Running a relay is a deployment that needs its own authorization, cutover and monitoring. Decision 32 applies it. The relayed path of task 2.8 is no longer blocked on an author decision; it still waits on milestone 3's implementation and on an authorized, operating serving relay.
4. **Default for local chat history** (book *Author decisions* item 3), owned by milestone 1. Decided 2026-11-16 (book *Author decisions* item 3): on by default, stored only in local protected storage, and can be turned off and cleared. Local chat on a shared model follows milestone 1's history setting, so this change needs no edit for it.
5. **External HTTPS reachability probe.** The book requires verification "through a relay" but defines no relay probe endpoint, and no way to bind an HTTPS origin's response to this daemon's identity. Decided 2026-11-16 (book *Author decisions* item 7): moot for this change. Desktop shares are libp2p-only, so the share wizard offers no HTTPS origin and needs no external HTTPS probe. A provider that wants an HTTPS origin runs `chiral_daemon` with the provider guide and its preflight, and an HTTPS option with an external probe may return in a later change. Decision 33 applies it. Task 2.7 and the HTTPS part of the reachability-check mode in task 2.5 are withdrawn. The question no longer blocks anything, but HTTPS was the only path to publishing before milestone 3, so nothing can now be published until milestone 3 is implemented.
6. **Paying wallet for qualification.** This change follows guide §6: the paying wallet must differ from the provider wallet (decision 5). The author should confirm this reading of "one wallet may act as both consumer and provider". Non-blocking.
7. **Calibration identity.** This change gives the calibration deployment its own DHT identity and ledger, following the guide's promotion into a fresh deployment (decision 2). The author may instead want a state-preserving way to qualify inside the deployment that will publish. Non-blocking.
8. **Calibration prices versus publication prices.** The book's step order puts pricing after qualification, while guide §6 and §8 have calibration use the intended prices and require them to match at promotion (decision 6). Decided 2026-11-16 by book *Author decisions* items 8 and 11, as this change reads them: Auto-price moves a qualified share's price among fractions of a target with no new qualification, and a nonzero price needs only "a valid qualification", so publication prices are independent of the calibration rates. The interim rule that made them equal, and its scenario *Publication rates follow the calibration rates*, are withdrawn (decision 6). Task 2.14 is no longer blocked. The author should confirm this reading if the guide's matching rule was meant to survive for desktop shares.
9. **Deployment per wallet or per model.** This change reuses one published deployment per network and provider wallet and requires acknowledgement of accounts a new model will not serve (decision 22). The author may prefer a new identity per model or serving profile. Non-blocking.
10. **Relayed service after offers lapse** (owned by `specify-p2p-provider-transport` open question 3). Under the rule as first drafted in milestone 3, a relay-only provider without a current valid offer got only coordination-sized circuits, and serving streams never ride them. After drain, *Stop sharing*, a chain outage that pauses publication, or a performance-withdrawal latch, consumers of a relayed share could then lose access to request status, receipts, cancellation and existing accounts through the relay unless a hole-punched or direct path was established. Decided 2026-11-16 (book *Author decisions* item 6): a 24-hour grace. A serving relay grants serving-grade circuits to a destination that has a currently valid signed offer, verified from its own authenticated manifest, or had one that expired within the last 24 hours, under the same per-provider quotas. Clarified the same day (book *Relays carry ciphertext, under explicit limits*): the 24 hours count from the signed `expires_at` of the most recent offer the relay itself verified for that peer, not from the time of that verification. Milestone 3 specifies the durable evidence a relay keeps; a relay restart does not end the grace. The drain action, the dashboard while a relayed share has no current offer, and the *Stop sharing* and Quit confirmations now give the relayed-grace statement of decision 34. The statement says that relays keep carrying request status, receipts, cancellation and existing accounts until 24 hours after this machine's most recent offer verified by the relay expires, after which consumers may lose access to them through the relay unless a direct or hole-punched path is established. It adds that a relay whose evidence store is full or has failed can end the grace earlier, because milestone 3 bounds a relay's durable grace evidence by a relay-wide quota, and fails closed for grace when that store fails. The relayed-path parts of tasks 2.16 and 2.20 are no longer blocked on this question; they wait on milestone 3's implementation, like every libp2p part.
11. **Engine confinement** (owned by `specify-desktop-local-models` open question 3, *Repository vetting and engine confinement*). The book's *My models* makes OS confinement that denies the engine the `network/` and `local-server/` directories a release-gate item. Sharing is the case where this matters most, because the engine then also processes remote consumers' requests and an exploited engine could read the provider signing key and administrator token. This change discloses the risk (decision 19) and does not specify confinement. Not blocking for implementation. **Blocking** for presenting sharing as available (task 3.7).
12. **Remittance gas for a free share.** The book's step 2 requires the provider wallet to hold CFX for fee-remittance gas, and *Author decisions* item 1 waives only qualification for a free share. This change therefore requires gas for every share (decision 29). A free share's own openings create no fee obligation, so the author may prefer to let a free share publish without gas while its deployment holds no unremitted obligation. Every new share is first published free (decision 37), so the answer affects every new share; and because Auto-price can later make the share paid without a new publish step, an exemption would also need a gas check before Auto-price's first nonzero step. Non-blocking.
13. **Sleep-consent preselection after a revocation.** *Author decisions* item 4 says the wizard asks with the option preselected. This change preselects it every time (decision 31), so a user who revoked consent must clear it again in the next share's wizard. The author may prefer that a later wizard remember a decline or revocation and show the option cleared. Non-blocking.
14. **Superseded: reading of "the wizard starts every new share as free"** (the earlier book *Author decisions* item 8). Superseded in place by the replacement items 8–11 (decisions 37 and 38). The question asked the author to confirm two consequences of reading free as a default choice. The first, that *Charge for this model* could be chosen before anything was published free, no longer exists: *Charge for this model* is withdrawn, every new share is first published free, and qualification runs on the published share. The second, that *Share again* on a stopped paid share is not a new share and keeps its accepted terms, is kept as this change's reading in *New shares start free in a launch window* (decision 37), because otherwise a stopped paid share's prepaid accounts could not be served again. Nothing remains open here.
15. **Qualified free offers, and free accounts opened before promotion — decided.** Decided 2026-11-16 (author, in chat; book *Share online* step 4): after a passing run the share keeps serving the free accounts opened before promotion under their allowance, with the same model and settings and no speed promise. This change widens execution compatibility through a MODIFIED *Existing agreements permit only evidence-only renewal of identical terms* (decision 45), and the promotion requirement, publish disclosure, dashboard and tasks 1.10, 2.33 and 3.2 now follow it. The first consequence is also decided (author, in chat, 2026-11-16): free agreements opened under a serving profile follow the performance rules, so their misses count toward the durable withdrawal latch; pre-promotion free accounts are not performance-accounted. The question as first asked: after a passing run, this change keeps the share's serving profile at every price, free included (decision 39), because a step down to free must not strand paid accounts, a price change should never change execution terms, and consumers can then see during the launch window the qualification the provider will charge under. Two consequences need the author's confirmation. First, free agreements under a serving profile follow the performance rules: their misses carry a zero-cost waiver and count toward the durable withdrawal latch, so free consumers' service quality can withdraw the model. Second, accounts opened under the share's unqualified free offers before the promotion are no longer served after it, because adding a serving profile is not evidence-only renewal; they hold no balance, and their owners can open new free accounts. The alternative is to extend execution compatibility in `inference-commercial-terms` so that a model with a serving profile also serves free agreements made without one for the same model and artifact, which this change does not own. It was non-blocking, because the rule then drafted was safe and cost only the free service of those early accounts.
16. **Auto-price for embedding shares — decided.** Re-decided 2026-11-17 to follow the book: Auto-price is unavailable for embedding shares, with the reason shown, because the book's *ready to charge* requires "a valid qualification", which an embedding share cannot hold; manual pricing remains (decision 44 revised 2026-11-17; tasks 1.11, 2.12 and 2.31). *Superseded 2026-11-17:* the earlier decision, an assistant default that contradicted the book, read: Decided 2026-11-16 (implementation decision by default, which the author may revisit): milestone 5 (`specify-provider-launch-reputation`, design Decision 32 *Embeddings shares*) defines readiness for embedding offers, the same launch criteria minus qualification, with embeddings probes and an input-token billing check, and Auto-price may run for embedding shares (decision 44 revised; *Auto-price sets the price from launch reputation*, *Free and embedding shares publish after readiness without speed qualification*; tasks 1.10 and 2.31). The question as first asked: the ready-to-charge result requires a valid qualification, which an embedding share cannot have, and the book's probes and billing check describe generation requests, so the first draft made Auto-price unavailable for embedding shares, which kept manual pricing; the author might want milestone 5 to define a launch reputation and readiness for embedding offers so that Auto-price can price them.
