Current code (verified read-only):

- `protocol.rs::InferenceOffer` has a required `endpoint: String` and `OFFER_DOMAIN = "chiral-inference-offer-v1"`. `protocol.rs::Quote` decodes with `deny_unknown_fields`, has no allowance field, and is signed under `QUOTE_DOMAIN = "chiral-inference-quote-v1"`.
- `provider_config.rs::ProviderConfig` requires `public_endpoint` and `dht`.
- `dht.rs` builds a TCP/Noise/yamux swarm with `relay::Behaviour` (server only; 128 reservations, 2 per peer, 128 circuits, 4 per peer; default circuit duration and byte limits), forces Kademlia server mode (`kad.set_mode(Some(kad::Mode::Server))`), and has no AutoNAT, DCUtR or relay client. Identify listen addresses are added to Kademlia without filtering (up to eight per message). `dht.rs::ManifestResponse` decodes a page as typed `Vec<Signed<InferenceOffer>>`, so one undecodable offer fails the whole page.
- `consumer.rs` catalog discovery decodes `/api/offers` entries as `Vec<Value>` and parses each entry separately, skipping those that fail. Its HTTPS client uses a ten-second connect timeout, 30- or 120-second control deadlines, a 3,600-second inference response and stream deadline, a 120-second stream idle timeout, and an 8 MiB cumulative response bound for both streaming and non-streaming responses.
- `app.rs::public_router` builds fresh `contracts::router` and `inference_gateway::router` values on each call; `inference_gateway::router` creates each model's arrival envelope at construction. Calling it once per listener would therefore split that state.
- `scripts/provision-provider.py` always writes `public_endpoint` as `https://<provider_domain>` (or loopback HTTP in calibration), and `scripts/provider-preflight.py` probes `config['public_endpoint'] + path`.

## Decisions

1. **One router instance, a second listener.** The stream handler serves each inbound `/chiral/inference/http/1` stream as an HTTP/1.1 server connection. It uses the one `Router` the provider builds at startup, cloned for the HTTP listener and the stream listener. `public_router()` is never called per listener, because today each call constructs new contract and gateway state: a second call would split the per-account rate window, the qualified arrival envelope, the body-reader slots and the cancellation registry by transport. Because there is no copy of the routes, parity holds by construction; a test compares the reachable route sets of both listeners, and cross-listener cancel and admission tests guard the shared state. `/api/version-policy` is part of today's public router and is therefore reachable on the stream too; that is a public, unauthenticated read. Native consumers open one stream per request, so resetting a stream affects exactly one request.
2. **`Host` is not authority.** Native consumers send the provider's peer ID string as `Host`. The router does not route or authorize by host, and owner proofs bind `{provider_wallet, method, path, body_hash}` with no origin, so proofs are independent of the transport. Source controls (where present) key on the remote peer ID; otherwise every relayed consumer would share the relay's IP.
3. **Authenticate before bytes.** The peer-ID equality check runs on the established connection before the stream writes anything. Over a relay, Noise and yamux run end to end through the circuit, so the authenticated remote is the provider and never the relay.
4. **Offer schema v2 is decided by structure; the revision stream holds only v2 offers.** v2 adds `transports` and keeps `endpoint` always present, as a string or `null`, consistent with "null optional fields are part of the typed serialization". v1 rejects `transports` and v2 requires it, so the two schemas are disjoint. A payload is decoded and verified under exactly one schema and domain (`chiral-inference-offer-v1` or `chiral-inference-offer-v2`). No extra version field is needed, and a v1 signature can never authenticate a v2 payload. Structural decoding stays necessary after v1 is retired (decision 5), because saved accounts and provider ledgers keep v1 offers that must still verify. No upgraded node accepts a v1 offer for fresh use, so registries and the revision stream per `provider_wallet/deployment_id/model.id` hold only v2 offers. An upgrading provider continues its one persisted revision counter, so its v2 revisions are above every v1 revision it issued, and a retained v1 offer never shares a revision value with a v2 offer of the same provider. Transport order is signed but carries no preference, the same treatment the model's `capabilities` array already gets. Earlier drafts kept one revision stream per schema so that v1 counterparts could coexist with their v2 offers; book *Author decisions* item 5 removed the counterparts (decision 6), and with them the need for a second stream.
5. **No acceptance window; v1 is kept only for retained agreements.** Decided 2026-11-16 (book *Author decisions* item 5). v1 never shipped publicly, so v2 replaces it at once. An upgraded node refuses a v1 offer for every fresh use (discovery, registry insertion, catalog listing, selection, quote proposal and acceptance, and opening a new account) with a reason naming the retired schema, and no cutoff, configuration or received object re-enables it. What survives is the book's rule that "persisted current-schema offers, quotes and receipts in saved accounts and provider ledgers stay parseable and verifiable for the life of the account", which matches the existing split between fresh onboarding and historical recovery: recovery of an acknowledged opening and the account's requests, status, receipts, cancellation, top-ups and settlement continue under their existing contracts. The book's *Wire change* states the scope directly: retirement "governs only new discovery, quotes and accounts — top-ups, requests and recovery of an existing account continue under its saved terms". Two consequences follow:
   - *Funding* in the book's "stop publishing, discovering, quoting and funding current-schema offers" means opening a new account from a v1 offer or quote. A top-up of an existing v1 account funds that account under its saved terms, and `inference-account-topup-request` already makes top-up settlement independent of current offer publication, so top-ups continue.
   - A quote the provider issued against a v1 offer before upgrading, with no durable acknowledgement and no account, would open a new account, so the upgraded provider refuses its funding-intent registration or free opening. The consumer broadcasts only after a durable acknowledgement, so nothing has moved on chain at that point, and the refusal is handled like any refused registration. Native quotes last 300 seconds, so this case exists only around the upgrade.

   The fixed cutoff `T_v1` on signed `issued_at` that earlier drafts proposed is withdrawn by the same decision.
6. **One manifest protocol, `/2`; `/1` retired.** Decided 2026-11-16 (book *Author decisions* item 5). v2 offers are served only on `/chiral/inference/manifest/2`, with `/1`'s framing and bounds. Upgraded nodes neither serve nor query `/1`, publish no v1 offer and list none in the relay catalog. The new protocol ID is still needed without a window: un-upgraded receivers decode a whole page as typed offers (`dht.rs::ManifestResponse`), so v2 offers served on `/1` would make them drop whole pages, whereas a missing `/1` makes them fail negotiation cleanly. Private testnet nodes upgrade together, so there is no mixed-version discovery: a candidate without `/2` contributes no offers and withdraws none, and a v1 entry on a catalog page (for example from an un-upgraded relay) is skipped on its own. The signed version policy (recommended or required update) remains the tool for stragglers. The same decision withdraws the dual-protocol window, withdrawal scoped per schema, the v1 counterparts that upgraded HTTPS-capable providers would have kept on `/1`, the preference for a v2 offer over a current counterpart, and the relay registry's two entries per namespace.
7. **Wire-foundation deltas.** The domain table needs a v2 row, and the offer ID rule must name "its own schema version's domain". Otherwise "the domain-framed canonical offer payload" becomes ambiguous once two offer domains exist. The v1 row stays, marked verification-only: no native signer signs a new offer under it after the upgrade, but retained v1 offers must still verify and their IDs must still recompute. Existing v1 offer IDs, and therefore the quote `offer_id` and the opening commitment that covers it, are unchanged. The quote, funding-intent, receipt, auth and feedback domains are unchanged, because those payloads do not carry `endpoint` or `transports`.
8. **Prefer HTTPS when both transports are declared.** It is the current, qualified path, it reveals no metadata to a relay, and it keeps existing deployments unchanged. libp2p may serve a later operation when the origin is unreachable. An already dispatched operation is never re-sent on the other transport. This choice is not listed as an author decision in the book; it is recorded here so the author can revisit it.
9. **The address filter reuses `offer_registry.rs::public_ip`.** One predicate serves both HTTP and libp2p, applied at the swarm dial boundary to every learned source the book lists, plus addresses named in AutoNAT dial-back requests. Learned DNS multiaddresses are not dialed (the swarm has no DNS transport today, and resolving would bypass the IP filter). Configured bootstrap and relay addresses are operator configuration, as the book's phrase "learned from untrusted peers" implies. The development exception matches HTTP's: literal loopback only. The bound of eight learned addresses per peer keeps today's identify bound.
10. **Reachability on every node.** The book applies the Kademlia rule to every node, because the relay runs the same `DhtService` and every node forces server mode today. Every node therefore runs AutoNAT and uses Kademlia server mode only with a confirmed public address, so NAT'd consumers, HTTPS-only providers and relays without confirmation do not fill routing tables with undialable peers. Every node also answers AutoNAT dial-back requests. Today the canonical relay is the only configured public peer, so its own confirmation can come only from the peers connected to it, which can dial out to it even from behind NAT. To stop a dial-back being used to probe private networks or amplify traffic, it goes only to the requester's observed public IP and is rate-bounded. A provider with libp2p serving holds at least one reservation even when publicly reachable, because DCUtR coordination needs it. Holding a reservation needs no offer (decision 12), so a provider started drained, such as milestone 4's daemon before its pre-publication check, can be reached. Losing reachability is reported in administration status; it does not change terms and is not turned into a withdrawal.
11. **Serving-relay mode is opt-in, and every limit is mandatory.** The serving-relay configuration block names every serving-grade limit and quota, plus reservation and circuit rate limits per peer and per IP address. A missing or zero value fails startup. For reference, libp2p's default rate limiters, for both reservations and circuits, are an allowance of 30 refilled at one per two minutes per peer and an allowance of 60 refilled at one per minute per IP address; this change does not adopt them for serving mode. Coordination-sized limits are fixed at libp2p's defaults (120 seconds, 131,072 bytes), the book's "about two minutes and 128 KiB", and a node that is not a serving relay grants nothing larger. Circuit relay v2 reports a `Limit {duration, data}` in reservation and connect replies, which is how the provider records and the consumer observes each circuit's limits. The relay counts duration from establishment and bytes in both directions on the whole relayed connection. Per-peer bandwidth is enforced across all of a peer's circuits.
12. **Serving-grade limits are decided per circuit from the destination's own `/2` manifest, with a grace that ends 24 hours after the last verified offer expires.** A reservation is never refused for lack of an offer. A qualifying offer is an unexpired v2 `libp2p` offer naming the destination, from the destination's own authenticated `/2` manifest. The relay can request that manifest back over the destination's reservation connection, or rely on its verified registry: manifest receivers already require `peer_id` to equal the responding peer, so a registry entry naming the destination came from that peer. A circuit gets serving-grade limits while the relay's wall clock is before the grace end: the signed `expires_at` of the most recent qualifying offer the relay verified for that destination, plus 24 hours (book *Relays carry ciphertext, under explicit limits* and *Author decisions* item 6; open question 3, decided). Before that `expires_at` the destination has a current qualifying offer; after it, the destination is in its grace period. Otherwise the circuit gets coordination size.
    - **Grace anchor.** The book counts the grace "from the signed `expires_at` of the most recent offer the relay itself verified for that peer", and the relay already holds that value in its evidence record. Earlier drafts counted from the relay's verification time on its monotonic clock; the book's 2026-11-16 clarification replaces that anchor. The relay cannot see a later withdrawal, and withdrawal by complete manifest, a publication pause during a chain outage and a performance-withdrawal latch involve no expiry it could observe, but none of them changes the recorded `expires_at`, so the grace covers all of them; a retrieval that finds no qualifying offer leaves the record unchanged. Only a newer verification moves the anchor, and it replaces the record's offer, so the record always describes the most recent qualifying offer the relay verified; when one manifest response holds several qualifying offers, the relay records the one with the latest `expires_at`. To keep that offer close to the provider's last valid offer, the relay refreshes evidence for a reserved destination when its recorded offer expires, at most once per 120 seconds per destination with one request in flight. The grace can therefore end earlier than 24 hours after the provider's last published offer expired, by the gap between that offer's expiry and the expiry of the last one the relay verified: about one offer lifetime for native 120-second offers, and never later.
    - **Clock.** The relay compares its own wall clock in integer Unix seconds with the signed `expires_at`, the comparison offer acceptance already makes, with no skew or other allowance: the grace end has passed once the wall clock reads `expires_at` plus 86,400 seconds, the book's 24 hours exactly. A relay clock that runs ahead can only end a grace early, the same direction as an eviction; a correctly synchronized relay clock is an operator requirement (task 2.13). Offer acceptance also bounds a recorded `expires_at` to at most 3,630 seconds after the relay's wall-clock time of verification (30 seconds of future issuance plus a 3,600-second lifetime). The relay therefore also records its wall-clock verification time and treats the grace as ended once its wall clock reads that time plus 90,030 seconds (3,630 plus 86,400). Within one process lifetime it also keeps its monotonic verification time and treats the grace as ended no later than 90,030 seconds after it on the monotonic clock, so a backward step of its wall clock cannot stretch a record beyond that bound within a run. Monotonic time does not survive a restart, so across a restart only the two wall-clock bounds apply, and a backward wall-clock step across a restart is not caught by the monotonic cap. A forward step can only end a grace early.
    - **Evidence.** One record per destination peer ID within the relay's network, holding the peer ID, the network scope, the most recently verified qualifying offer's content ID and `expires_at`, and the relay's wall-clock time of that verification (persisted) and monotonic time (in memory for the current run), and no account, consumer or request data. Records are removed once their grace end has passed and are capped by the mandatory `max_offer_evidence_records` (decision 18), an explicit operator-configured relay-wide quota of at least `max_reservations` so every reserved peer can hold one; when it is full the record whose grace end is earliest is evicted first, and among equal grace ends the oldest verification. Eviction is the only way the relay itself ends a grace before its 24 hours, apart from a forward wall-clock step and a failed store; the per-peer quotas refuse circuits during a grace without ending it. The relay's authenticated administration status reports the eviction count and the time of the last eviction, and the pre-funding disclosure says that a relay whose evidence store is full or has failed can end the grace early (decision 17). Removal or eviction can only shrink later circuits to coordination size. Records serve only this circuit-limit decision. They are not provider-availability observations: book *Author decisions* item 9's launch reputation (availability, free-period probes and the service score) belongs to `specify-provider-launch-reputation`, and nothing here defines or feeds it.
    - **Durability.** Records are durable, so a relay restart does not end a grace. They live in a protected store under the relay's data directory, scoped to its selected network, with owner-only permissions like the relay's other state (`relay_server` already scopes its state with `network.scoped_dir(data_dir)`). A new or replaced record is durably written before any serving-grade decision relies on it, removals and evictions are durably applied, and the store is reloaded on start, with the clock rule applied to each reloaded record before use. A store that is missing, unreadable, corrupt or insecure, or a failed durable write, fails closed for grace: the relay holds no reloaded records, discards its records on a failed write, keeps any record it creates until the store is sound in memory only and without a grace period, and so grants serving-grade limits only to destinations with a current qualifying offer it verifies, never invents, reconstructs or imports records, does not overwrite or delete a damaged store, and reports the condition in authenticated administration status. A missing store is replaced by a new empty one for later verifications, because the relay cannot tell a first start from a lost store. Serving mode on `relay_server` therefore adds a loopback-only, bearer-authenticated administration status like `chiral_daemon`'s operator listener. An earlier draft kept records in memory only and let a restart end the grace; that is superseded.
    - **Open circuits** keep their limits when offers lapse or the grace ends, so in-flight streaming and settlement are not cut early by an expiry, a drain or the end of the grace period.
    - **Quotas.** Grace circuits are ordinary serving-grade circuits for the per-peer reservation, circuit, bandwidth and rate limits, so the per-provider quotas of decision 21 bound them as the book requires.

    Price and serving profile play no part in the decision. The book's author decision 1 lets a free generation share publish with `serving: null`, and a relay can verify neither qualification nor payment from an offer (signature validity alone does not prove qualification), so a free unprofiled offer qualifies exactly as a priced, profiled one does. Author decision 8 makes a free launch window the default for a new share, so this matters for most desktop shares: a free share gets serving-grade circuits from its first verified offer. Auto-price then changes the price by publishing new revisions of the same deployment and peer ID. Each verified revision replaces the relay's evidence record like any other qualifying offer, so a step between free and priced terms, in either direction, changes no circuit's limits; the free allowance, like the price, plays no part. The automatic qualification run in the launch window pauses free admission at the provider while the share keeps publishing, so relays keep granting serving-grade circuits and existing accounts can still reach status and receipts. Keeping that run free of competing inference is milestone 4's provider-side admission concern, because a relay cannot tell status calls from inference. A provider that drains instead is in its grace period like any drained provider. (Before the 2026-11-16 revision of items 8–11, this paragraph described an explicit paid upgrade that drained the free share first; that upgrade is superseded.) Offer evidence is therefore not abuse resistance: publishing a valid offer costs nothing, and the per-peer quotas and rate limits of decision 11 are what bound one peer's use of a serving relay, during the grace period as at any other time. Peers that publish free offers can create evidence records at the per-IP reservation rate and so evict other records; that can end a drained provider's grace early on that relay, but never extends anyone's grace or limits.
13. **Circuit-budget check before paid dispatch.** Limits cover the whole circuit, so the consumer tracks the bytes and time each relayed connection has used, measured below Noise and yamux, and reserves budget for in-flight requests on it. A paid request is dispatched only when the circuit can still carry its head and body plus the 8 MiB response bound within the stream client's response deadline. The 8 MiB bound is used instead of a bound derived from `max_tokens` because the bytes per token are not tightly bounded: JSON escaping, SSE framing, logprobs and tool-call arguments all expand them. The 8 MiB figure is the limit the client already enforces, so it is a sound upper bound. Today's response deadline for inference is 3,600 seconds, so a serving relay whose circuit duration is shorter cannot carry paid requests, and one whose circuit byte limit is not comfortably above 8 MiB carries at most one at a time. For a relay another operator runs, those are consequences of its operator's choices, not defaults set here; the check simply refuses dispatch on a circuit that cannot carry the request. For a project relay, the author decision (open question 1, decided) makes one paid request per circuit the minimum (decision 21). A request on a free account is checked, reserved and reported exactly as a paid request (author decision 10): its known usage draws down the account's signed allowance even when a cut loses the response, and an unchecked free request on a circuit shared with a paid one could consume the budget reserved for the paid request. This also covers milestone 5's probes when its observer uses the native consumer path. The requirement keeps its name, *Paid requests are dispatched only on circuits that can carry them*, because milestone 2 cites it, and defines a paid inference request to include a free-account request. A circuit is classified as coordination-sized from its reported limits, using libp2p's default thresholds. Both the consumer and the provider refuse serving streams on such circuits, so the rule holds even against a non-conforming peer. A relay that reports no limit is disclosed as reporting none and is not blocked; if it then cuts the circuit, that is a transport failure.
14. **Discovery budget.** A serving-grade circuit must fit a full manifest exchange, so serving mode refuses a circuit byte limit below one maximum exchange on `/chiral/inference/manifest/2` plus a documented identify and Kademlia allowance. Circuit relay v2 does not tell a client a relay's per-source limits, so consumers bound their relayed fan-out per relay at libp2p's default per-source values (four concurrent circuits; a 30-circuit allowance refilled at one per 120 seconds). A stricter relay then produces refusals, and a more generous one is under-used. Either way, the result states that it is incomplete instead of silently omitting NAT-only providers. A consumer may still try a manifest exchange over a coordination-sized circuit: a cut costs nothing and only marks the result incomplete.
15. **Stream-server and stream-client bounds.** No TLS ingress fronts the stream listener, so the stream server enforces what Caddy enforces for HTTPS: a head deadline, a maximum head size (431 or reset), an idle timeout and a bounded number of requests per stream, in addition to per-peer and global stream caps. yamux's default of 512 streams per connection is not treated as a limit. The stream client keeps the HTTPS client's deadlines and 8 MiB bound. It never dials anything named in a response, and it surfaces a 3xx response as a provider error without `Location`, so the milestone 2 gateway receives nothing it could forward.
16. **The recovery boundary is "any request byte written".** Before that point, a failure, including a circuit-budget refusal, is "not sent". After it, the outcome is ambiguous: reconcile by request ID, or, when the failure came before the response headers, by the retained `Idempotency-Key` in the account's request list (request reads already expose the key). An explicit user resend reuses the key, so the provider's existing `duplicate_request` deduplication protects it. Funding and control calls keep their journaled state machine.
17. **Disclosure content.** The pre-funding disclosure adds the path; for a relayed path the relay's visibility of both peers' IP addresses and peer IDs, timing and volume, as the book states in *Product and trust model*, *Relays carry ciphertext* and A.1.6; for a direct or hole-punched path the mutual public-IP exposure the book's risk disclosure states; relay powers (delay, drop, refuse, cut); for a relayed path, that once the provider stops publishing valid offers a relay carries its service to existing accounts only until 24 hours after the last of its offers that the relay verified expires, which can be sooner than 24 hours after its last published offer expires, and which a relay whose evidence store is full, or has failed, can end earlier (decision 12); the latency caveat; and that the path can change, including an upgrade from Relayed to Hole-punched that exposes both IPs. The book's A.5.1 prepay header already reserves a `<endpoint | p2p path>` slot. Other surfaces that present network-account requests use the same native path observation: Chat network threads (milestone 1's view), whose per-request path label this change implements under task 2.11, and the milestone 2 local-server log.
18. **Configuration shapes** (names proposed for implementation):
    - Provider: `public_endpoint` becomes nullable, plus an optional `libp2p_serving {relays, max_streams, max_streams_per_peer, request_head_timeout_secs, max_header_bytes, idle_timeout_secs, max_requests_per_stream}`.
    - Consumer: an optional `p2p {allowed_relays}`.
    - Relay node: an optional `serving_relay {max_circuit_duration_secs, max_circuit_bytes, max_peer_bytes_per_sec, max_reservations, max_reservations_per_peer, max_circuits, max_circuits_per_peer, reservation_duration_secs, reservation_rate_per_peer, reservation_rate_per_ip, circuit_rate_per_source_peer, circuit_rate_per_source_ip, max_offer_evidence_records}`, where each rate is `{burst, refill_interval_secs}` and `max_offer_evidence_records`, the relay-wide quota on durable evidence records, is at least `max_reservations` (decision 12). Serving mode requires the relay's existing `data_dir`, under whose network-scoped directory the evidence store lives; it adds no separate store path, and it adds a protected administration bearer file for `relay_server`.

    All are strict (unknown fields rejected), relay lists are bounded to 32 entries like `bootstrap`, and numeric limits must be nonzero. The values are operator choices and are not fixed here. A project relay's values are implementation inputs fixed and measured within this milestone (decision 21).
19. **Operator provisioning.** Today the operator path cannot produce or preflight a libp2p-only provider: the generator always writes an HTTPS origin and requires the provider DNS name, and preflight concatenates the origin. This change makes the provider DNS name optional only when a libp2p serving object is supplied, writes a `null` origin without provider TLS ingress, and has preflight check the loopback public listener plus the administration status's libp2p observation. The relay and RPC names and the ACME email remain, because they configure those separate services. The desktop's own share path is milestone 4's. Book *Author decisions* item 7 makes desktop shares libp2p-only and sends a provider that wants an HTTPS origin to `chiral_daemon` with the provider guide and its preflight; this provisioning path, with a provider DNS name, is that route, and this change keeps it. `https` therefore stays a declared transport, and consumers keep reaching HTTPS providers.
20. **Transport stack.** TCP with Noise and yamux, as the book specifies. QUIC, WebRTC and WebTransport are out of scope.
21. **Project relays, no relay fee** (book *Author decisions* item 2, open question 1). The project operates serving-capable testnet relays, and shipped profiles may name them; a provider may also list relays that any operator runs, alongside or instead of project relays. A listed relay is explicit configuration whoever runs it, and every relay gets the same treatment: peer-ID authentication, the circuit-budget check, path disclosure and no protocol authority. Relays add no fee, payment, agreement or term. No signed object names a relay, so no protocol object changes to carry this out. Introducing a relay fee would reverse the author decision.
    - **Minimum for project relays.** A project relay runs in serving mode, and its serving-grade duration and byte limits must let a fresh circuit pass decision 13's check for one paid request: the documented setup, identify and Kademlia allowance, then the head and the public router's maximum inference request body (256 KiB today, `inference_backend.rs::MAX_REQUEST_BYTES`) plus the 8 MiB response bound with framing, within the stream client's inference response deadline (3,600 seconds today). The book phrases this as "its maximum body plus the 8 MiB response bound within the request deadline". The check is decision 13's arithmetic, not a separate formula, so a project relay that passes it is usable by every conforming consumer. Other operators' relays are not held to this minimum; a smaller relay simply fails the consumer's check.
    - **Per-provider quotas.** The relay identifies a provider only by its peer ID. The existing per-peer reservation, circuit and bandwidth limits (decision 11) count circuits for which the peer is the destination as well as the source, so for a provider they act as per-provider quotas. The per-peer circuit quota caps how many consumers a relay-only provider can serve at once through one relay. A refused circuit is a transport failure before any request byte, so the request is "not sent" (decision 16). It is a relay capacity limit, not an agreement term. Peer IDs cost nothing to create, so per-IP rate limits stay mandatory alongside these quotas.
    - **Values and deployment.** The values are implementation inputs. They are fixed in the project relay's shipped configuration within this milestone (task 2.13) and measured by the release gates for relay saturation, quotas and abuse and for relayed latency and throughput (tasks 3.5–3.7). This change deploys no relay. Running a project relay, and naming it in a shipped profile, needs its own authorized deployment with explicit cutover, backups, monitoring and rollback, as CLAUDE.md requires for live services. The relay sees the metadata that decision 17's disclosure states.
22. **The free allowance is a signed v2 offer term** (book *Wire change* and *Author decisions* item 10).
    - **Shape.** `free_allowance` is present in every v2 payload, as an object for a free offer and `null` otherwise, the same treatment `endpoint` gets (decision 4), so absent and `null` cannot both be valid and the canonical encoding stays unique. The object has exactly `tokens` and `lifetime_secs`, unsigned integer JSON numbers, canonicalized with sorted keys as `{"lifetime_secs":…,"tokens":…}`.
    - **Free means both rates zero, with zero minimum.** The book defines a free offer by "both token prices and minimum funding zero". The pending commercial terms already treat any zero-rate service as free whatever its minimum, so a zero-rate v2 offer with a nonzero minimum would be free service without an allowance. v2 therefore rejects it. Native publication never emits one ("local publication emits `"0"` for genuinely free service").
    - **Input and output count together.** The book says "a maximum token count". The provider's cost covers both prompt processing and generation, and the account's accounting usage is exactly two counters, `prompt_tokens` and `completion_tokens`, so the allowance is compared with their sum. Embeddings count input tokens only, as their reservation already has zero output budget.
    - **Bounds.** `tokens` is 1,000 to 10,000,000 and `lifetime_secs` 3,600 (1 hour) to 2,592,000 (30 days). The lower bounds keep a free account usable for at least a few small requests, such as milestone 5's probes, and a consumer time to use it. The upper bounds keep the term a real limit, far above the default. The book fixes only the default, 20,000 tokens and 24 hours, which native publication emits unless the provider configures other values. These bounds are this change's choice and can be revised before implementation without changing the design. Accepted 2026-11-16 as an implementation decision the author may revisit, together with the 402 codes `free_allowance_expired` and `free_allowance_exhausted` and the precedence of `free_allowance_expired` (decision 24).
    - **Per account.** The allowance limits each account separately, not a payer, a wallet or a provider. How many free accounts one wallet or ledger may open stays with the existing free-opening admission (fewer than eight per wallet and 10,000 per ledger), which decision 25 modifies so that ended free accounts stop counting toward the ledger limit only (open question 4, decided 2026-11-16).
    - **Retained v1.** v1 offers and quotes have no allowance. A free account opened from a v1 quote before the upgrade keeps its saved terms, unlimited as before, because retirement governs only new accounts (decision 5). v1 never shipped publicly, so this affects only private testnet accounts.
    - **Price changes.** Auto-price (milestone 4) publishes ordinary new revisions. A step between free and priced terms adds or removes the allowance in the next revision and needs no other protocol change; accepted agreements keep their terms, so an opened free account keeps its allowance and a paid account its prices. A quote issued against the previous revision keeps that revision's terms through its 300-second validity, as today.
23. **Quote schema v2 copies the allowance under `chiral-inference-quote-v2`.** The book says the agreement binds the allowance. Quotes copy every commercial term explicitly and reject unknown fields, so the quote must carry it; binding it only through `offer_id` would make each admission depend on re-parsing the retained offer, against the rule that copied terms are explicit. Following decision 4, schema and domain are bound together: a quote with `free_allowance` verifies only under `chiral-inference-quote-v2`, and one without it only under `chiral-inference-quote-v1`, which stays verification-only for retained quotes. The quote's version follows its offer's: fresh quoting of a v1 offer is already refused, so a new quote is always v2 and names a v2 offer, and no retirement rule beyond decision 5 is needed. The opening commitment hashes the quote framed under its own domain, so a retained v1 quote's commitment is unchanged; a paid v2 quote carries `free_allowance: null` and is framed under the v2 domain. The funding-intent acknowledgement names the quote by `quote_id` and the receipt carries an account snapshot, so neither changes. Feedback funding evidence does carry the signed quote, and the relay's verification (`reputation.rs`, today fixed to `chiral-inference-quote-v1`) must select the domain from the quote's schema, or payment-gated feedback on every paid v2 account would fail verification; the wire-foundation delta states this for every quote verifier.
24. **The allowance is enforced in the request reservation.** The provider records `opened_at` from its wall clock when it creates the free account and never changes it, so a replayed opening does not restart the lifetime. Inside the reservation transaction of `inference-request-accounting` it requires the clock to be before `opened_at + lifetime_secs` and reserves the worst case, `P + G` tokens, so that settled usage plus holds never exceeds `tokens`. Validated usage cannot exceed the hold (exactly `P` input, at most `G` output), and unknown usage releases the hold without counting, at the provider's expense, as for paid holds. The deadline governs admission only, so an admitted request finishes. Refusals are HTTP 402, matching `insufficient_balance` for paid accounts, because the remedy is a new (possibly paid) account: `free_allowance_expired` takes precedence over `free_allowance_exhausted`. Records, status, receipts and cancellation stay available until the account is deleted 30 days after it ended (decision 25), and there is no renewal: free accounts already cannot be topped up. The provider's own wall clock is enough: a backward step only lengthens free service at the provider's own expense, so no monotonic cap is needed, unlike the relay grace, which spends a third party's resource. The consumer shows the allowance before opening and, afterwards, the remaining tokens from the account's usage counters and an end time estimated from its own clock when it sent the opening, which is never later than the provider's end unless a clock is stepped. The account snapshot gains no field: `AccountView` is strict and signed into receipts, so exposing `opened_at` or the remaining allowance there would be a change to `inference-account-snapshot`, not needed for enforcement.

25. **Ended free accounts leave the ledger limit, not the wallet limit** (book *Wire change*, 2026-11-16; open question 4, option (b)). Retention, decided 2026-11-16 by the author: an ended free account with nothing unsettled is deleted 30 days after it ended, so stored free records stay bounded by the free-opening rate times 30 days. The pending *Authenticated opening admission preserves original acceptance* counts every account toward both free-opening limits. This change carries a MODIFIED copy of that requirement, with its full current text and only the free-opening paragraph changed, plus one scenario. An account is ended when its agreement is a v2 free quote, its allowance has ended by the same two tests the reservation uses (the provider's wall clock at or past `opened_at + lifetime_secs`, or used allowance equal to `tokens`), and it has no unsettled request or token hold. The test runs inside the creation transaction, so it competes atomically with reservations; an ended allowance admits no new request, so an ended account cannot start counting again. The per-wallet limit of eight still counts every account, so one wallet cannot cycle free accounts at one provider. Retained v1 free accounts have no allowance, never end and keep counting. The book's *Wire change* adds the deletion rule ("is deleted 30 days after it ended, after which its status and receipts are no longer available"), and the MODIFIED requirement carries it: an ended account's records, status and receipts stay available until it is deleted 30 days after it ended, after which status and receipt requests are answered as for an unknown account. The 10,000 limit bounds concurrently active accounts, and the deletion rule bounds retained ended free records. **Archive-order dependency:** unchanged (`specify-inference-commercial-terms` first); task 1.4 rebases this MODIFIED copy too. This is an implementation choice of the definition of "used" and "nothing unsettled"; the author may revisit it.
26. **A qualification pause is retryable and not admitted on the consumer side** (implementation decision, 2026-11-16; the author may revisit it). Milestone 4 owns the provider's qualification pause, which answers new inference requests and openings with HTTP 503 `qualification_in_progress` and, through milestone 2's gateway, an integer `Retry-After` of 1–3,600 seconds. This change already classifies the free-allowance 402 codes for native consumers, so it also owns this classification: desktop Chat, the Playground and the CLI treat the 503 on either transport as not admitted (no charge, no hold, not an ambiguous outcome needing reconciliation), never retry automatically, never broadcast an opening transaction without a persisted acknowledgement, and show "Provider is qualifying — try again later". `Retry-After` is only a hint. Recorded in *Free accounts are served only within their signed allowance*. The book's *Share online* step 4 also has a passing run keep serving free accounts opened before it under their allowance; the execution-compatibility rule that lets a profiled deployment serve those unprofiled agreements is milestone 4's. Nothing in this change refuses them: the allowance check depends only on the agreement's quote, relay admission ignores the serving profile (decision 12), and the path disclosure promises no speed for an agreement without one.

## Non-goals and limitations

- **Relay deployment.** The author decided relay operation on 2026-11-16 (book *Author decisions* item 2, decision 21): project-operated testnet relays named in shipped profiles, other operators' relays allowed, and no relay fee. This change specifies what a project relay must satisfy and plans its configuration and shipped relay lists (task 2.13). It does not deploy, cut over or monitor a relay, and it names no relay address or final limit value; those values are implementation inputs fixed and measured within this milestone.
- **SDK and tool access to libp2p-only providers** belongs to `specify-desktop-local-api-server` (milestone 2), which forwards funded network accounts over this transport. This change only forbids presenting an invented HTTPS base URL. The book also requires that "the local loopback gateway never passes a provider's 3xx status or `Location` header to SDK clients". That rule belongs to milestone 2, which specifies it (`desktop-local-api-server`, *Network routes forward through the native consumer path with the credential held natively*). This change makes the native stream client surface a 3xx as a provider error without `Location`, so the gateway has nothing to forward. The book also names a CLI-hosted loopback gateway, which is left to the follow-up change `specify-cli-loopback-gateway` named by milestone 2.
- **Share wizard, reachability verification before publishing, and the provider dashboard** belong to `specify-desktop-share-online` (milestone 4). This change supplies the coordination-sized reservation and the administration-status observation those features use.
- **Local-server surfaces** belong to milestone 2, and the rest of the Chat page to milestone 1. The Chat network-thread path label is implemented here, under task 2.11, from the same native path observation.
- **No mixed-version operation.** Upgraded and un-upgraded nodes do not discover each other's offers: upgraded nodes neither serve nor query `/1`, and un-upgraded nodes fail negotiation on `/2`. Private testnet nodes upgrade together (book *Author decisions* item 5; decisions 5 and 6). Saved v1 accounts are unaffected, because serving them needs no manifest.
- **Catalog-only consumers** (no `dht` node) cannot reach libp2p providers. The relay catalog does not supply address hints.
- **No consumer peer-ID unlinkability.** Relays and providers see the consumer's configured peer ID, and on direct and hole-punched paths the provider sees the consumer's public IP. Ephemeral per-session identities are not specified.
- **No relay chaining or multi-hop circuits**, and no UPnP, NAT-PMP or PCP port mapping.
- **No token-derived response bound.** The circuit-budget check uses the 8 MiB response bound, not an estimate from `max_tokens` (decision 13).
- **Backpressure.** A slow relayed reader can back-pressure the gateway's output, as a slow HTTPS client can today. This change does not alter the token clock. The release gates measure whether relayed backpressure changes recorded outcomes.
- **Identical deadlines on slow paths.** Over a slow relay, a large request body is subject to the same five-second body deadline as on HTTP, so it can be rejected before admission (no charge). The deadline is deliberately not relaxed for relayed paths.
- **Retained endpoints.** An account keeps its retained offer's HTTPS endpoint; it does not follow a new origin. It may move to libp2p for the same peer ID when the provider's current offers for that model declare it.
- **Private operator endpoints** inside one trusted provider network are unchanged and are not a NAT-traversal mechanism.
- **No free-account limit beyond the allowance and existing admission.** The allowance bounds each account; how many free accounts a payer can open is the existing free-opening admission (open question 4). New wallets cost nothing, so neither is Sybil resistance: a provider's free service is bounded by its own concurrency, rate and admission limits.
- **Not a security sandbox or attestation.** The provider still sees prompts in plaintext, and a peer ID or serving-grade relay admission proves no execution.

## Open questions

1. **Relay operation.** Decided 2026-11-16 (book *Author decisions* item 2): the project operates serving-capable testnet relays named in shipped profiles, and providers may also list relays that anyone else operates. Relays charge no fee and add no payment, agreement or term to the inference protocol. A serving-grade circuit on a project relay must at least carry one paid request (its maximum body plus the 8 MiB response bound within the request deadline), which is decision 13's circuit-budget check, and project relays enforce per-provider reservation, circuit and bandwidth quotas. The exact values are implementation inputs fixed and measured within this milestone, not an author decision. Running a relay is a deployment that needs its own authorization, cutover and monitoring; nothing here authorizes one. Recorded in decision 21 and in *Serving relays enforce explicit operator-chosen limits*. Remaining dependency: tasks 2.13 and 3.5–3.7 fix and measure the project relay's values, but their real-relay parts (naming a project relay in shipped profiles, and the release gates run against a real serving relay) need an authorized project relay deployment with explicit cutover. Tasks 2.1–2.12 implement explicit, operator-supplied limits and can be tested with test-chosen limits.
2. **Value of the v1 acceptance cutoff `T_v1`.** Decided 2026-11-16 (book *Author decisions* item 5): there is no acceptance window, so there is no cutoff to choose. v1 never shipped publicly, and v2 replaces it at once on `/chiral/inference/manifest/2`. Upgraded nodes retire `/1` and stop publishing, discovering, quoting and funding v1 offers, and private testnet nodes upgrade together. Retirement governs only new discovery, quotes and accounts: top-ups, requests and recovery of an existing account continue under its saved terms, and saved accounts and provider ledgers keep their v1 offers, quotes and receipts parseable and verifiable for the life of each account. Recorded in decisions 4–7, *Upgraded nodes serve and query only the v2 manifest protocol*, and the MODIFIED *Complete signed offer declaration*, *Offer freshness and advertised origin*, *Native quote verification binds the chosen provider and payer* and *Length-framed operation domains*. Tasks 2.1–2.3 no longer depend on a cutoff value.
3. **Relayed service for a provider without a current offer.** Decided 2026-11-16 (book *Author decisions* item 6): option (b) below, a 24-hour grace. Without it, a relay-only provider with no current valid offer, because it drained, stopped sharing, paused publication during a chain/RPC outage or latched performance withdrawal, would get only coordination-sized circuits; serving streams never ride those, so unless a DCUtR upgrade succeeded it could not serve request status, receipts, cancellation or existing accounts over a relay. That conflicted with the book's rule that existing settled credit can remain usable during temporary chain outages, and with draining's promise that in-flight work settles. The options were:
   - (a) keep the rule as written and rely on the pre-funding disclosure, the "provider can disappear" risk and direct or hole-punched paths;
   - (b) grant serving-grade circuits for a bounded grace period after the destination's last valid offer (chosen, with 24 hours);
   - (c) grant them on another signed provider statement, such as a signed "serving existing accounts" declaration in the manifest.

   A relay still cannot restrict a circuit to status or receipt routes, because it cannot read the encrypted HTTP; grace circuits carry any serving traffic, within the same per-provider quotas. The grace ends 24 hours after the signed `expires_at` of the most recent qualifying offer the relay verified for that peer (the book's 2026-11-16 anchor; earlier drafts counted from the verification time), compared on the relay's wall clock with no skew allowance and bounded by a monotonic cap, so drain, *Stop sharing* or withdrawal, a chain-outage publication pause and a performance-withdrawal latch are all covered. Evidence is one durable record per peer within the relay's network, bounded by a relay-wide quota whose evictions are reported; a relay restart keeps the grace, a failed store fails closed, and a full store can end a grace early, as disclosed. Recorded in decision 12, *Serving-grade circuit limits apply only until 24 hours after the destination's last relay-verified offer expires*, the 24-hour bullet of *The active path is disclosed before funding and during use*, and tasks 2.7, 2.11, 2.13, 3.4 and 3.5. Task 3.4's relayed-recovery gate for drained, publication-paused or performance-withdrawn providers is no longer blocked.

4. **Do used or expired free accounts keep counting toward free-opening capacity?** Decided 2026-11-16 (book *Wire change*: "An ended free account with nothing unsettled no longer counts toward the provider's ledger-wide account cap (the per-consumer cap still counts it)"): option (b), with the book's deletion rule: an ended free account with nothing unsettled is deleted 30 days after it ended, and its records, status and receipts stay available until then. Recorded in decision 25 and the MODIFIED *Authenticated opening admission preserves original acceptance*. The original question follows. The pending free-opening admission (`inference-commercial-terms`, *Authenticated opening admission preserves original acceptance*) admits a first free opening only while the payer owns fewer than eight accounts at the provider and the ledger holds fewer than 10,000, and it counts every account. With the allowance (item 10), a free account stops serving after 24 hours by default but stays in the ledger for its records. Milestone 5's observer opens free accounts from rotating identities while a provider is free, and every step back to free restarts probes, so a long-lived share's ledger approaches 10,000 accounts and then refuses every free opening, for probes and consumers alike, for good. The per-wallet limit likewise lets one wallet use at most eight free accounts, about 160,000 tokens at the defaults, at each provider, ever. Options:
   - (a) keep counting every account, so free service at a ledger ends after 10,000 free openings;
   - (b) stop counting an account toward the 10,000-account ledger limit once its allowance has ended or been used and it has no unsettled request, keep counting it toward the per-wallet limit, and bound the retained records of such closed accounts by a separate retention rule;
   - (c) as (b), and also stop counting it toward the per-wallet limit.

   This change recommended (b): free service stays available for the life of a share, while one wallet still cannot cycle free accounts at one provider. It modifies a requirement owned by `specify-inference-commercial-terms`. The retention bound was later decided as the book's 30-day deletion rule (decision 25).

The book's other author decisions, also recorded 2026-11-16, belong to other milestones. Item 3 (local chat history on by default) belongs to milestone 1 and item 4 (automatic sleep prevention while sharing) to milestone 4; neither affects this change. Item 1 (free sharing without qualification) belongs to milestone 4. It needs no new rule here, because schema v2 already allows `serving: null`. This change only makes sure nothing assumes a serving profile: relay admission ignores price and profile (decision 12), and the path disclosure and speed display promise no speed guarantee for an offer without one (*The active path is disclosed before funding and during use*; *The transport path does not change qualification or waiver terms*). Item 7 (desktop sharing libp2p-only) also belongs to milestone 4. Nothing in this change assumes a desktop HTTPS share: `https` remains a declared transport for `chiral_daemon` providers, consumers still reach HTTPS providers, and the operator provisioning path with a provider DNS name is the HTTPS route the book now points to (decision 19). Items 8 (launch window and Auto-price) and 11 (ready-to-charge and Auto-price defaults) belong to milestone 4, and item 9 (launch reputation: availability and free-period probes; still no free votes) to milestone 5 (`specify-provider-launch-reputation`); they were checked here. Their only wire consequence is item 10's free allowance, applied by decisions 22–24. An Auto-price step is an ordinary offer revision, and relay admission ignores price, free allowance and serving profile, so every revision of a share, free or priced, gets serving-grade circuits by the same rule (decision 12). Probes are ordinary free-account requests within the signed allowance, and the circuit-budget check covers them (decision 13). This change neither lets free sessions vote nor defines availability, probes or the service score: offer-evidence records serve only the circuit-limit decision (decision 12). The earlier items 8 (free by default, with charging an explicit upgrade) and 9 (uptime-only track record) that a previous revision of this change checked are superseded by items 8–11.
