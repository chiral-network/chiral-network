## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

- *Product and trust model*, line 31 (the Settlement plane): "separately operated Conflux eSpace RPC verifies native CFX funding. No blockchain transaction occurs per generated token. The application never starts a node or miner on login; Core mining payouts require an explicit Core-to-eSpace transfer before use."
- *Direction, precedence, and status*, line 17: the runtime is "settled with native CFX on Conflux eSpace testnet"; "neither mainnet nor a new mining pool is authorized"; "Historical storage/Drive/CDN/Core-Geth/in-app-mining guides are not current runtime instructions."
- *Release gates*, line 777: "Mainnet, a new mining pool and the retired product domains are not part of this release."
- *Historical context (non-normative)*, line 793: earlier versions "implemented file sharing, Drive, ChiralDrop, CDN/site publication, download payments, and bundled Core-Geth/Ethash mining"; their "old payloads, RPC assumptions, fee collection, admission, and lifecycle semantics are **not** compatibility contracts". Line 795: historical implementation details "remain available in repository history".
- *Shared signing-wallet directory*, lines 470 and 472: the network-scoped `inference/<hash>` namespace under the configured `data_dir` base, and network-scoped consumer state.
- *Native provider provisioning and operations*, line 607 ("separate native service startup") and line 644: "Native provisioning starts no service. Optional Linux Compose is deployment machinery, not container rental; it has no standalone engine service."
- *Backup, incident response, and cutover*, line 675 (a fresh ledger is no authority "to … reinterpret CHI/CHR as CFX") and line 679: the cutover "removes legacy runtime/API paths; it does **not** delete or migrate existing Drive files, chain databases, wallet exports, old CHI history, or file-transfer reputation … Existing supported private keys can be explicitly imported into native protected storage, but old balances, contracts, reputation, and data are not new-network credit. There is no automatic legacy data importer, token bridge, or claim that every historical installation has been upgraded."
- *A.5.4 Wallet*, lines 937 and 940: import "does not convert old CHI/CHR balances"; the funding section "explains … that Core and eSpace balances are separate, and that funding an eSpace wallet from Core needs an explicit transfer".
- *A.5.8 Settings*, line 963: preferences "contain no secrets or legacy runtime fields".
- `CLAUDE.md`: "No WAN tensor parallelism, home-provider NAT traversal, S3, container submission, CDN, Drive, ChiralDrop, or app-managed mining is part of this release"; "Preserve legacy wallet, chain, download, Drive, and hosting data in place. Do not automatically import old balances, convert CHI/CHR to CFX, migrate old keys, delete directories, or auto-start legacy services"; "Retiring/replacing live services requires an explicit cutover, backups, and an operational rollback plan".

Supporting, not authority: `docs/llm-serving-migration-plan.md` line 16 ("Existing miners/pools remain external, with explicit Core-to-eSpace transfer and no automatic mining/node startup on login"), line 180 (the runtime excludes "old miner installers/launchers, and their commands/events/startup recovery") and line 356 (release gate: "no old file/mining feature is reachable or auto-started; … legacy user data is preserved").

The change was prompted by item 16 of `docs/apas-worker/comparison-2026-11-18.md`: "The application never starts a node or miner on login (low). Book Part I." No specification stated the rule.

### What "on login" means

In the earlier application, "login" was the in-app wallet login. Commit `49ed4da9` ("Make mining auto-start opt-in and default it to off") shows it in `src/App.svelte:473–512`: "Auto-start Geth node once when user logs in", run when `$isAuthenticated` became true, which called `gethService.start(…)` and, with the `autoStartMining` preference (`src/lib/stores.ts`, key `chiral-settings`), `gethService.startMining(1)`. The book's sentence therefore retires a session-start behaviour first, and an operating-system login behaviour as well. The current application has no wallet login. Its session starts when a consumer profile is loaded (`configure` on the desktop, `--config` on the CLI), and it has a `logout`. Requirement 2 covers both senses: an operating-system login, and the start of an application session.

No commit in history added an operating-system start-at-login mechanism. `git log --all -S "plugin-autostart"` and `git log --all -S "LaunchAgent"` find nothing, and the legacy `src-tauri/Cargo.toml` (`49ed4da9`, line 34) had `tauri-plugin-shell` but no autostart plugin. No legacy login entry is therefore expected on an upgraded machine.

### "Node" means a chain node

Line 31 is the Settlement plane, and line 793 names the retired "bundled Core-Geth/Ethash mining". "Node" there is a blockchain node. The libp2p peer of the Discovery plane (line 29) is not that node. It starts only when the user discovers offers (`consumer.rs:926–935`), which `desktop-gui-global-rules` (*Network actions wait for an explicitly loaded profile*) already keeps from starting on its own.

## Decisions

1. **One small capability, `application-startup-boundaries`.** The rules apply to the desktop, the CLI, the headless binaries and the provisioning scripts together. Placing them in `desktop-window-lifecycle` would leave the CLI and provisioning implicit. Placing them in `provider-daemon-lifecycle` would leave the desktop implicit, and that change already declared the consumer's legacy handling "outside the provider daemon".
2. **"Never", not only "on login", for nodes and miners (requirement 1).** Line 31 names login, but line 31 also says settlement uses a "separately operated" RPC. Line 17 retires the in-app-mining guides, line 777 excludes a new mining pool, and `CLAUDE.md` excludes "app-managed mining" from the release. Together they exclude a node or miner managed by the application at any time. Login is where the earlier application started them, so requirement 2 names it separately.
3. **Requirement 2 forbids login entries for nodes, miners and legacy services, not every login entry.** The book forbids only starting a node or miner on login, and `CLAUDE.md` forbids auto-starting legacy services. The current application registers no start-at-login entry at all (coverage row 2). Whether the application may ever register one for itself is open question 1. The spec does not decide it, so a later change could add a desktop start-at-login only through its own specification, and requirement 2 would still bind it.
4. **An operator's service manager is not the application starting at login.** `chiral_daemon`, `relay_server` and `chiral_rpc_gateway` are operator processes. An operator may deliberately run them under a service manager. For example, the private zoo-6 deployment's `chiral-llm-8gb.service` is "enabled for guest boot" (`docs/zoo6-private-pilot.md:11`), and the reference Compose services use `restart: unless-stopped`. None of these is a node, a miner or a legacy service, and requirement 5 keeps native provisioning from creating them. Whether deployment machinery may restart the daemon automatically stays `provider-daemon-lifecycle` open question 5.
5. **Legacy services are not started; nothing more is specified about them (requirement 2).** `CLAUDE.md` forbids auto-starting legacy services, so requirement 2 forbids starting, restarting, enabling or scheduling one. The book says only that the cutover "removes legacy runtime/API paths" (line 679). It says nothing about the application stopping, disabling or removing a legacy service that it finds on the host. `CLAUDE.md`'s rule that "Retiring/replacing live services requires an explicit cutover, backups, and an operational rollback plan" is about operators retiring the historical deployments, not about application behaviour. The spec therefore does not forbid those actions. For a legacy node or miner, requirement 1 already keeps the application from stopping or managing it. The current application has no operation that touches a legacy service at all.
6. **Legacy data is defined by line 679's list, wherever it lies (requirement 3).** It includes legacy data under the configured `data_dir` base. For example, the earlier application kept Geth under `dirs::data_dir()/chiral-network/geth` (`49ed4da9:src-tauri/src/geth.rs:411–414`), and a profile may name that same base. The current consumer writes its state only under `<data_dir>/inference/<hash>/` (`consumer.rs:636–641`; `network.rs:83–85`). The webview preference entry of the earlier application (`chiral-settings`) is legacy data too: the current desktop reads and writes only `chiral-inference-settings` (`stores.ts:33`, `38`) and leaves the old entry in place. Requirement 3 places only the state that the book places: the wallet, account, credential, request-key and nonce-journal state (lines 470 and 472). It does not say that the application writes nothing else. The webview keeps its preference entry in the operating system's application-data directory, which the book does not name. The book does not place the version-policy cache either; the code keeps it in the same namespace (`consumer.rs:638–642`).
7. **The Core and eSpace rule is stated as what the application does not do (requirement 4).** The book requires a disclosure (line 940, owned by `desktop-gui-pages`) and an explicit transfer "before use" (line 31). It does not ask the application to perform the transfer. The current runtime makes no Core-space request at all: its chain client and RPC helper send only `eth_*` methods. An in-app transfer would need a Core network identity and key handling that `inference-wire-foundation` does not admit, and would need its own change. The spec therefore forbids only a transfer without the user's explicit action and the presentation of Core funds as eSpace funds.
8. **Native provisioning is included (requirement 5).** Line 644's first sentence had no owner. `provider-daemon-lifecycle` recorded it as out of scope and checked it by inspection. Starting a service is the same boundary as starting one at login, and the provisioning scripts are the only repository tooling that prepares a host. The scripts' helper processes (`whoami`, `icacls` and PowerShell, for access-control lists) end before the script exits, so they are allowed. The book's sentence is about *native* provisioning, so requirement 5 covers `provision-provider.py` without `--container`, and the runtime and model scripts. Container provisioning (`--container`) prepares the optional Compose deployment, which line 644 calls "deployment machinery". The book does not say whether that preparation may start a service, so the spec does not cover it. The script's docstring says it never "starts network services" in either mode (`provision-provider.py:10`). That is an implementation fact, not a requirement.
9. **Current implementation facts (not normative).** The desktop's `setup` hook only installs the tray (`desktop.rs:403–406`). The library constructs non-test processes in only one place, `engine_runtime.rs:201–202` (`command()`). That helper launches the pinned llama-server (`ManagedEngine::start`, line 301). During that start it also runs short-lived device-observer tools through `capture` (lines 387–400), each awaited within a 10-second bound: the runtime's `--list-devices`, and `nvidia-smi`, `sysctl`, `ioreg`, `vm_stat`, `sw_vers` or `vulkaninfo` (lines 410–462). Only `chiral_daemon` reaches it, through `ProviderRuntime::start` (`app.rs:282`, called at `chiral_daemon.rs:171`). The Network page states "There is no legacy-chain fallback and no background node or miner startup" (`Network.svelte:42`). The Wallet page states "Mining pools normally pay Core Space addresses. Core and eSpace balances are separate: use an explicit native Core-to-eSpace transfer to fund an eSpace wallet. Changing an address's text is not a transfer." (`Wallet.svelte:48`). `README.md:106` gives the same rule to operators. These texts are consistent with the spec; their exact wording is not a requirement here.

## Observations outside this capability

- `network::data_dir()` (`network.rs:87–91`, `dirs::data_local_dir()/chiral-network`) has no caller. It is not a fallback today, because every binary requires an explicit `data_dir`. If a later change used it as a default, the default would be the base under which the earlier application kept `geth/`. Requirement 3 would still forbid touching that data, but the explicit-configuration rule (book line 449) would be the one to check first.
- Commit `49ed4da9` also auto-published hosting offers on login (`src/App.svelte:455–470`: "Auto-publish hosting marketplace on login while enabled"). Requirement 2 covers it as a legacy service.
- `docs/macos-testing.md:3` and `docs/provider-qualification.md:22` already say that no local blockchain node or miner is part of those flows, and `README.md:11` says legacy data is "not automatically imported". No document needed an edit.

## Out of scope, each with a reason

- **Operating zoo-6's miner.** `CLAUDE.md` says "Do not restart that miner automatically". That is an operator authorization for one host, not application behaviour; the application never controls a miner (requirement 1).
- **Retiring live legacy services** (`relay-server.service`, `cdn-freshnet.service` on historical hosts). `CLAUDE.md` requires an explicit cutover with backups and a rollback plan. That is an operator procedure. Requirement 2 only keeps the application from starting or enabling such services (decision 5).
- **Signed installers and their behaviour on each operating system.** The book says supported-platform installers "remain unqualified" (line 19). Task 4.1 records inspection evidence and does not qualify an installer.
- **A desktop start-at-login, background operation after quit, or a headless desktop.** Excluded by `desktop-window-lifecycle`'s archived design and by `desktop-share-online`; whether the application may ever start itself at login is open question 1.
- **An in-app Core-to-eSpace transfer.** Decision 7.

## Open questions for the whitepaper author

1. **May the application register itself to start at login, if that starts no node, miner or legacy service?** Line 31 forbids only starting "a node or miner on login". Today nothing is registered, and every desktop change so far has left start-at-login out of scope. The options are:
   - (a) the book text: only a login start of a node, miner or legacy service is forbidden, and a desktop start-at-login (for example for the target design's sharing) would need its own specified change that keeps requirement 2;
   - (b) no start-at-login entry of any kind in this release.

   Proposed default, which is what the spec adopts: (a), the book text. Nonblocking: no task waits on the answer.

## Risks

- A user upgrading from the earlier application may still have a Geth or miner process that the old application started. The new application neither stops nor restarts it (requirements 1 and 2), so it runs until the user stops it or the machine restarts, and it may hold GPU memory that inference needs. The book asks for no detection or notice, and none is specified.
- Static evidence (configuration and source searches) shows what the repository can do. It does not show what a built installer does on each operating system. Task 4.1 covers that.
- Requirement 2's scenario on operating-system login cannot be fully automated in the shared test suite. The acceptance tasks use static checks and process observation, and task 4.1 uses a real login on each operating system.
