## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

## Decisions

1. **One capability, `client-version-policy`.** It covers the authority, the policy, its storage, its sources, its enforcement on clients and providers, and the desktop gate. The desktop-managed daemon's policy stays with `desktop-share-online`, and general GUI rules stay with `desktop-gui-global-rules`.
2. **The three statuses.** Line 846 distinguishes a *required* from a *recommended* update. The code's rule (version.rs:141–160) is the natural reading: `required` below `min_required`, `recommended` below `recommended`, otherwise `ok`. A policy with `min_required` above `recommended` still yields `required` below the minimum (`compare_to_policy_misconfigured_min_above_recommended_fails_safe`). A malformed version fails the check instead of reading as zero.
3. **Expiry limits use, not authenticity.** Line 650 keeps the watermark "across restart and expired-policy refresh". The code therefore restores an expired policy as the watermark without checking its expiry (version.rs:519–521). It rejects an expired policy only on arrival (version.rs:317–319, consumer.rs:608–610) and when it is used for a status (version.rs:141–142, 412–417).
4. **The signed policy names no network; storage provides the network scope.** Line 650 scopes "storage" to authority and network, and `CLAUDE.md` scopes "acceptance". The code stores each network's watermark under its own namespace, which is a hash of the complete network identity (network.rs:76–84). The signed fields (version.rs:253–270), however, carry no network identity, so a policy that the authority issued for one network verifies on every network that trusts the same authority. Line 63 makes the authority project-wide, so the spec reads the policy as a statement by that authority about client versions, and reads the network scope as a property of storage only. Author question 3 asks whether policies should instead be bound to a network.
5. **A required update: the settled minimum, with the rest left open.** The book shows a full-screen blocking modal for a required update (line 846) and lists what upgrades preserve (line 652). It does not say which native operations are refused or which stay open. `CLAUDE.md` requires that historical funding recovery and revocation remain reachable and that request status support ambiguous-outcome recovery. The spec therefore requires only:
   - the refusals that both native surfaces already make: opening funding, top-ups and native inference;
   - that the client's own check never refuses inspection, reconciliation or cancellation of existing state: the pending view, `funding_recovery`, `cancel_funding`, request status and cancellation, credential revocation, local views, wallet reads and export, logout and quit;
   - that nothing is erased.

   `resume`, `discover`, `quote`, credential issuance and rotation, and `feedback` are left to author question 1. Today the desktop refuses all of them and the CLI refuses none (decision 12). Under these rules neither surface differs from the book.

   A corrupt or insecure policy cache is left to the same question. Line 650 says such a cache fails closed, and the spec requires that it never falls back and that it refuses new funding and inference (requirement 6). Today `Consumer::new` refuses the whole profile (consumer.rs:462), which also makes recovery unreachable until the cache is repaired. The book does not say whether fail-closed covers recovery, and recovery becomes reachable again once the cache is repaired, so the spec neither requires nor forbids refusing the profile.
6. **A policy that cannot be checked fails closed.** An expired policy, a fetched policy that is rejected, and an unreachable `policy_url` all make the check fail. The native client then refuses the same new work as under a required update. This matches the code: `version_status` returns an error (consumer.rs:587–623) and `ensure_version_supported` propagates it (624–629). It is also the conservative reading of "corrupt/insecure caches fail closed" (line 650). The book does not address an unreachable policy URL; author question 2 asks about it.
7. **The header is checked only when present.** Line 343 says the provider middleware checks `X-Chiral-Client-Version` "when provided" and that missing-version requests are not universally rejected. Line 581 says stock clients need no custom header. The spec requires the check of a present header and forbids refusing a missing one. The codes 426 `upgrade_required` and 400 `invalid_version` are the current ones (app.rs:506–527); the consumer already maps `upgrade_required` (consumer.rs:336).
8. **"Blocking" includes the keyboard and assistive technology.** Line 846 says "full-screen blocking modal", and A.1.9 (line 816) makes the GUI accessible. A modal that only covers the screen with a pointer overlay, while Tab can still reach the controls behind it, does not block a keyboard user. The tray's Quit confirmation is an HTML `<dialog>` opened with `showModal()` (App.svelte:45), so it stays above the gate.
9. **"Copy download URL for an HTTPS URL only".** Read literally, the copy action exists only for an HTTPS URL. The spec also excludes URLs with credentials, which `openDownload` already refuses (UpdateGate.svelte:32). For any other URL, nothing invites the user to fetch it.
10. **The gate reflects the loaded profile's network.** The policy is stored per network (line 650), and A.1.8 (line 815) requires that "no data from the previous network/session remains visible" after logout or a profile load. A status derived from the previous network's policy is such data.
11. **The private key never travels on a command line, in the environment or on standard output.** Line 474 forbids private keys on command lines. `CLAUDE.md` requires protected files for operator secrets. Line 648 keeps the authority's key offline. The signer is the only program that handles the key, so these rules apply to it.
12. **Current implementation values (not normative constants).** Each may change without a spec change if the requirements still hold:
    - The policy JSON uses camelCase names: `minRequired`, `recommended`, `downloadUrl`, `message` (left out when absent), `issuedAt`, `validUntil` and `signature` (version.rs:35–61). `validUntil` 0 means no expiry.
    - The signed encoding is six fields in this order: `min_required`, `recommended`, `download_url`, `message` (empty when absent), and `issued_at` and `valid_until` as decimal strings. Each field is preceded by its byte length as a little-endian `u32` (version.rs:253–270). The signature is 64 bytes in 128 hexadecimal characters.
    - The clock-skew allowance for `issued_at` is 30 seconds (version.rs:317 and 522).
    - Versions compare as dot-separated integers after trimming whitespace and any leading `v` characters. Anything after the numeric prefix is ignored, so `1.0.0-rc1` equals `1.0.0`. Missing components count as 0, so `1.0` equals `1.0.0` (version.rs:85–137).
    - The bundled policy is `min_required` `0.0.0`, `recommended` equal to the build's `CARGO_PKG_VERSION`, `download_url` `https://github.com/chiral-network/chiral-network/releases/latest`, issued at 0, no expiry, unsigned (version.rs:67–78).
    - The placeholder authority is 32 zero bytes (policy_key_validation.rs:1–3). The build script treats a `PROFILE` of `release` as a release build (build.rs:42–46).
    - The watermark is the stored signed policy itself; no separate timestamp is kept (version.rs:425–431). It lives at `<data_dir>/inference/<namespace>/version-policy/<authority hex>/policy.json` beside `policy.lock` (consumer.rs:457–461 and 588–592; chiral_daemon.rs:41–45; relay_server.rs:176–178; version.rs:570–578). It is written to a random temporary file, synced, renamed (on Windows with `MoveFileExW` write-through) and the directory synced (version.rs:464–496 and 532–551). The cache limit is 64 KiB (version.rs:433). The daemon and relay refuse a policy file larger than 65,536 bytes (chiral_daemon.rs:47, relay_server.rs:180).
    - The effective policy is one process-wide slot (version.rs:357–374). Each acceptance takes the slot's write lock and then an exclusive file lock (version.rs:560–577).
    - The consumer fetches its policy on every `version_status` call, that is, on every `fund`, `topup` and inference call and on every desktop status refresh, with a 30-second timeout and the 8 MiB response bound (consumer.rs:296–315 and 587–629).
    - The desktop refreshes the status at startup, every hour, and after a profile load (versionStore.ts:39 and 63–69; Settings.svelte:17). Banner dismissal is stored under `chiral-update-banner-dismissed` in `sessionStorage` (UpdateGate.svelte:15–26).
    - While an update is required, the desktop's native layer refuses `discover`, `quote`, `fund`, `topup`, `resume`, `credential_issue`, `credential_rotate`, `feedback`, `infer` and `inference_stream` with "client update required before network operations" (desktop.rs:46–52, 152–154 and 219). The consumer layer, which is all the CLI uses, refuses only `fund`, `topup` and inference, with "a client upgrade is required before funding or inference" (consumer.rs:624–629, 984, 1567 and 2074).
    - The provider's messages are "Upgrade the Chiral client before using this provider" for 426 `upgrade_required` and "Invalid Chiral client version" for 400 `invalid_version` (app.rs:506–527). The status and error codes themselves are normative in requirement 10 (decision 7), because the native consumer maps them; only the messages are implementation values.
    - The provider also serves its effective policy at `GET /api/version-policy` (app.rs:447, 492–494). The book does not require this, so requirement 9 permits it but does not require it.
    - The provider evaluates its own policy in each 30-second maintenance pass (app.rs:327–342). The daemon and the relay load a policy file only when they start; a newer policy needs a restart.

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **The policy signer takes the authority's private key on the command line or from the environment, and prints a new key to standard output** (requirement 8; book lines 474 and 648; `CLAUDE.md`). `chiral-policy-sign sign` takes the private key as `--key <hex>`, or from the `CHIRAL_POLICY_SECRET` environment variable (`chiral_policy_sign.rs:42–45`), and parses it from that string (`118–125`). `keygen` prints `secret=<hex>` to standard output (`64–69`). Book line 474 says "Do not place private keys or bearer tokens on command lines", and `CLAUDE.md` says operator secrets "use protected files, not command-line arguments ... logs". A key in argv is visible to other local processes and is kept in shell history, and a key printed to a terminal ends up in scrollback and logs. Task 2.1. Fixed 2026-11-18 by task 2.1.
2. **The required-update modal does not block the keyboard or assistive technology** (requirement 13; book lines 816 and 846). The modal is a fixed `div` with `role="alertdialog"` and `aria-modal="true"` (`UpdateGate.svelte:47–52`). Nothing moves focus into it, and nothing makes the rest of the shell inert: no element in `src/` uses `inert`, and the navigation, page and Log out controls (`App.svelte:80–103`) stay in the tab order. A keyboard user can Tab past the overlay and operate the shell behind it, for example open Usage and submit a funding cancellation, while a pointer user cannot. A screen-reader user can also leave the dialog. Task 2.2.
3. **"Copy download URL" is offered for any download URL, and its fallback points the user to a non-HTTPS URL** (requirement 13; book line 846). The button is rendered for every required status (`UpdateGate.svelte:73–80`), and the recommended banner's *Update* button calls the same function (`103–109`). `openDownload` copies only an HTTPS URL without credentials (`28–38`). For any other URL it shows "Copy the displayed HTTPS download URL into your browser.", while the modal displays that non-HTTPS URL underneath (`81–83`). The user is therefore offered the action and then told to copy a URL that is not HTTPS. Task 2.3.
4. **The gate keeps showing the previous network's status after logout, and after a profile load whose status check fails** (requirement 13; book lines 650 and 815). `logout` drops the consumer but leaves the process-wide effective policy as it was (`desktop.rs:60–65`, `version.rs:357–374`). Without a consumer, `get_version_status` reports that policy, which is the previous network's (`desktop.rs:303–306`). The webview does not refresh the status on logout (`App.svelte:38–43`), and when a refresh fails it keeps the last status (`versionStore.ts:53–59`). After logging out of a network whose policy recommends an update, the banner therefore stays, and the hourly refresh brings back the same status. The same happens after a successful load of another profile whose status check then fails (`Settings.svelte:17`). Task 2.4.

No other difference from the whitepaper was found. The release-build requirement, the runtime override, authentication, the watermark and its storage, expiry, fail-closed caches, the placeholder limits, the policy sources, the header check, the native refusals that the spec requires, the provider gate and the required/recommended split of the gate all match the requirements.

## Observations that are not code differences

- **The desktop and the CLI refuse different operations under a required update** (decision 12). `chiral resume` still rebroadcasts or settles a pending opening or top-up, and `chiral discover`, `quote`, credential issuance and rotation and `feedback` still run, while the desktop refuses all of them. The book does not say which set is right (question 1).
- **A corrupt or insecure policy cache makes recovery unreachable until it is repaired.** `Consumer::new` restores the cache while it loads the profile, before the chain client and any account are opened (consumer.rs:457–463), so a corrupt cache stops the profile from loading in both the desktop and the CLI, and `funding_recovery`, `cancel_funding`, request status and credential revocation cannot run for that network. Deleting the file to repair it discards the rollback watermark; restoring it from the protected backup (line 675) keeps a watermark. Requirement 6 neither requires nor forbids this (decision 5); it falls under question 1.
- **Providers apply the header check to recovery requests too.** Owner challenges and owner-authorized requests carry the version header (consumer.rs:927 and 948), so a native client below a provider's minimum is also refused account, usage, receipt and funding-intent reads and credential revocation at that provider. Bearer request status and cancellation send no header (consumer.rs:2135–2162) and stay available. This falls under question 1.
- **An expired provider policy is reported as the client's fault.** `compare_to_policy` reports expiry as an error (version.rs:141–142), and `public_headers` turns any error into HTTP 400 `invalid_version`, "Invalid Chiral client version" (app.rs:509–523). While a provider's own policy is expired, every native request that carries the header is refused with that message, owner-authenticated recovery included. The book sets no error code for this case (question 2).
- **When `get_version_status` fails, the desktop shows neither a gate nor an error** (versionStore.ts:57–59 keeps the last status, which is `ok` at startup), while native funding and inference fail with the policy error. This falls under question 2.
- **Every `fund`, `topup` and inference call fetches the policy again** (consumer.rs:594–616). An unreachable relay therefore delays each such call by up to 30 seconds and then refuses it, with every provider, although the relay never carries inference. This falls under question 2.
- **A relay or daemon reads its policy only at start.** When a relay's policy expires, every consumer that fetches from it fails its check until the operator restarts the relay with a newer policy.
- **The signer signs any JSON that parses** (chiral_policy_sign.rs:127–139). A policy whose `valid_until` is not after its `issued_at`, whose versions are malformed, or whose download URL is not HTTPS is signed, and clients then reject it or, for the URL, offer no download. The signer's `verify` without `--pub` checks against the effective authority, including the runtime override (`verify_policy`, line 146), while its help text says "the public key compiled into this binary" (lines 51–52).
- **An absent `message` and an empty `message` sign the same bytes** (version.rs:261). Two JSON documents can therefore share one signature, and the equal-time check treats them as one policy. Nothing displays differently.
- **A daemon or relay below the minimum still starts.** The startup check propagates only errors (chiral_daemon.rs:61, relay_server.rs:194). The daemon then admits nothing (requirement 12); the relay keeps serving discovery, reputation and the policy. The book does not say that a relay must stop.
- **The DHT disconnects peers whose Identify agent version is below `min_required`** (dht.rs:502–506). The book's version section does not mention this. Peer admission belongs to the DHT and peer-to-peer specifications.

## Open questions for the whitepaper author

1. **Which operations stay available while an update is required?** Line 846 puts a full-screen blocking modal over the whole desktop, and lines 646–652 say what an upgrade must preserve. Neither says which recovery paths stay open in the meantime. `CLAUDE.md` requires that "historical funding recovery must remain reachable without abandoning accepted balances", and A.1.7 (line 814) says pending journaled funding "is surfaced and offered as *Resume*". Today:
   - the desktop's native layer refuses `discover`, `quote`, `fund`, `topup`, `resume`, credential issuance and rotation, `feedback` and inference, and keeps `funding_recovery`, `cancel_funding`, request status and cancellation, credential revocation and local views;
   - the modal covers every page, so a desktop user can reach none of those through the GUI, cannot log out to load another network's profile, and can only update or quit from the tray;
   - the CLI refuses only `fund`, `topup` and inference, so `chiral resume` still recovers pending funding;
   - a provider refuses every request whose stated version is below its minimum, including owner-authenticated account reads, funding-intent recovery and credential revocation;
   - a consumer profile whose policy cache is corrupt or insecure does not load at all, in either client, so no recovery runs for that network until the cache is repaired, and deleting the file to repair it discards the watermark.

   Proposed default: recovery-only operations stay available in both clients and at providers. These are the pending view, `funding_recovery`, `resume` of an original whose signed bytes are already journaled (rebroadcast or settle only, never sign a new payment), `cancel_funding`, account, usage, receipt and request reads, request cancellation and credential revocation. The modal offers a path to *Funding & recovery*, plus Log out and Quit. New quotes, new funding and top-ups, credential issuance and rotation, feedback and new inference are refused. A profile with a corrupt or insecure cache loads with the same recovery-only operations and refuses everything else, and never rewrites or deletes the cache. The spec adopts only the part both clients already meet (decision 5) and records the current sets as implementation values. Nonblocking: an answer would add tasks for the desktop gate, the provider middleware and A.2.
2. **What happens when no current authenticated policy can be obtained?** When `policy_url` does not answer, or answers with an expired or rejected policy, the consumer refuses `fund`, `topup` and inference with the policy error, and it fetches again on each such call. The desktop shows no gate or error. A provider whose own policy has expired admits nothing and answers 400 `invalid_version` to native requests. A relay outage therefore stops native funding and inference with every provider. Options: (a) fail closed, as today; (b) keep using the stored authenticated policy until its `valid_until` while the URL is unreachable, and fail closed only after expiry. Proposed default (what the spec adopts): (a), with recovery as in question 1. Nonblocking.
3. **Should a signed policy name its network?** The signed fields carry no network identity (decision 4). A policy issued for one network therefore verifies on any network that trusts the same authority. A relay of network B could serve network A's newer policy to B's clients, and that policy would become B's watermark. Proposed default (what the spec adopts): no; a policy is a statement by the project-wide authority (line 63), and storage keeps each network's watermark separate. If you want per-network policies, a later change would add the network identity to the signed fields, which requires a new signature format. Nonblocking.

## Risks

- All executable evidence is unit-level, in `version.rs`. No HTTP, consumer, daemon or relay startup, CLI or GUI test exercises the version policy (section 3 of `tasks.md`).
- Release gates 1 and 6 (book lines 769 and 774) require a published policy authority and verified version rollback protection on real desktops. Task 4.1 tracks them. Nothing here is release evidence.
- Restoring an older backup restores an older policy file, which lowers that network's watermark. A restored process can then accept an authentic policy that the live process had already superseded. Line 673 forbids rolling stale state onto the live network; the backup taken right before an upgrade is the one to restore.
- The answer to question 1 may change A.2 and both native gates. Task 2.2 must not make recovery harder to open up later, for example by making the whole document inert in a way the tray's Quit dialog cannot override.
- Task 2.1 changes the operator procedure for signing. The repository's operator documents use only `verify --pub`. Notes outside the documentation (`fm_agent/`) describe `sign --key $CHIRAL_POLICY_SECRET` and become outdated.
- Requirements reference capabilities from pending changes (task 4.4 sets the archive order).
