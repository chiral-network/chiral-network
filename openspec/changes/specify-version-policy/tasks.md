## 2. Close code differences

- [x] 2.1 Keep the authority's private key out of argv, the environment and standard output (requirement 8, design code difference 1). In `src-tauri/src/bin/chiral_policy_sign.rs`:
  - replace `sign --key <hex>` and `CHIRAL_POLICY_SECRET` with `sign --key-file <path>`, read through `wallet::open_secret_file` so that a symbolic link or (on Unix) a group- or world-accessible file is refused before anything is signed;
  - make `keygen --out <path>` create the private-key file with `wallet::create_secret_file`, refuse an existing path, and print only JSON `{"public_key": "<hex>", "secret_file": "<path>"}`.

  Regressions, which fail without the change: an integration test that runs the binary and shows that `keygen` writes a mode-`0600` file, prints no private key and refuses to overwrite; that `sign` refuses a `0644` key file and offers no argument or environment variable for the key itself; and that a policy it signs is accepted by `version::accept_policy` with the matching public key and rejected with another key. Done 2026-11-18: `keygen --out <path>` creates the key with `wallet::create_secret_file` before generating anything, so an existing path is refused. It writes the hex secret and prints only `{"public_key", "secret_file"}`. `sign --key-file <path>` reads the key through `wallet::open_secret_file`, which refuses a symbolic link, a non-regular file or (on Unix) a group- or world-accessible file before anything is signed. `--key` and `CHIRAL_POLICY_SECRET` are gone, and the secret is held in `Zeroizing` buffers. `verify` is unchanged. Regressions in `src-tauri/tests/policy_sign_cli_test.rs`, both of which fail on the previous binary: `keygen_writes_an_owner_only_key_file_and_prints_only_the_public_key`, and `sign_reads_the_key_only_from_a_protected_file`. The second checks that a signed policy verifies with the matching public key and not with another, that `--key` and the environment variable are refused, and that a `0644` file and a symlink are refused.
- [x] 2.2 Make the required-update modal block the keyboard and assistive technology (requirement 13, design code difference 2). In `src/lib/components/UpdateGate.svelte` and `src/App.svelte`, while the status is `required`, make the shell behind the modal inert (for example with the `inert` attribute on the skip link, navigation and `main`), move focus into the modal and keep it there. Leave the tray's Quit confirmation (`App.svelte:45`, a `showModal()` dialog) usable above the gate. Do not foreclose author question 1: keep the blocking in one place that a later answer can relax for recovery pages. Regression, which fails without the change: a component test that renders the shell with a `required` status and shows that focus starts inside the modal, that Tab from the last modal control stays inside it, and that the navigation and page controls are inert; and that the Quit dialog can still be opened and used. Done 2026-11-18: `App.svelte` derives one `shellBlocked` flag from the version status, the single place a later answer to question 1 can relax. While an update is required it marks the skip link, the navigation (through a `display: contents` wrapper, so the sticky bar is unaffected) and `main` inert. `UpdateGate.svelte` moves focus into the modal and keeps Tab and Shift+Tab inside it. The tray's Quit confirmation is a `showModal()` dialog in the top layer and stays usable. Regressions in `tests/updateGate.test.ts`: `moves focus into the modal, keeps Tab there and makes the shell inert, while Quit stays usable` fails on the previous shell; `leaves the shell usable when no update is required` guards the other case. A browser check in headless Chrome confirmed that focus starts in the modal, that `main` and the navigation cannot take focus, and that the navbar still sticks when scrolled.
- [x] 2.3 Offer "Copy download URL" only for an HTTPS URL (requirement 13, design code difference 3). In `UpdateGate.svelte`, parse `policy.downloadUrl` once. Render the copy action in the modal, the banner's *Update* action, and the URL as a download link only when the URL is HTTPS without credentials. Otherwise state, as plain text, that the policy gives no HTTPS download URL, and make no copy offer. Keep the clipboard-failure message for HTTPS URLs. Regressions in `tests/updateGate.test.ts`: `offers no copy or Update action for` `http://example.org/releases`, `https://user@example.org/releases` and an unparsable value, all of which fail on the previous component; `copies an HTTPS URL exactly from the modal and the banner` guards the HTTPS case. Screenshots checked for both cases.
- [x] 2.4 Drop the previous network's status on logout and on a failed refresh (requirement 13, design code difference 4). In `src-tauri/src/version.rs` add a way to reset the effective policy to the bundled policy with no scope, and call it from the `logout` operation in `desktop.rs`. A later profile load restores that network's watermark from disk. In `src/lib/stores/versionStore.ts`, reset the status on logout and on a profile load before the new status arrives. Regressions, which fail without the change: a desktop dispatch test in which, after a profile with a `recommended` policy and a `logout`, `get_version_status` reports the bundled policy; and a store test in which a `recommended` status disappears after logout, and after a profile load whose status refresh fails. - [ ] 2.5 Decode policy-source errors as the policy source's (requirement 9; found in the reputation round-44 review). ## 3. Acceptance evidence per requirement

Task 3.N corresponds to requirement N in the spec and to row N of the design coverage table. A task is checked only when existing passing tests prove every statement and scenario of its requirement. An unchecked task names the missing case. Tests that need a signed effective policy can run in a child process with the `CHIRAL_POLICY_PUBLIC_KEY` override, as `persisted_policy_fresh_process_rejects_older_still_valid_policy` does.

- [ ] 3.1 Release builds compile a non-placeholder policy authority. Existing evidence: `release_builds_do_not_embed_placeholder_policy_key` (only in a non-debug test run), `parses_valid_ed25519_public_key`, `rejects_malformed_nonzero_32_byte_key`, `parses_placeholder_for_debug_build_callers` and `placeholder_policy_key_detection`. Missing: evidence that a release-profile build fails without `CHIRAL_POLICY_PUBLIC_KEY`, with 64 zeros, with `42` repeated 32 times and with 63 hexadecimal characters, and embeds a valid key. For example, move the build decision into a pure function of `policy_key_validation.rs` and test it for both profiles, or add a CI step that runs the four release builds.
- [ ] 3.2 The runtime authority override is resolved once per process. Existing evidence: `persisted_policy_fresh_process_rejects_older_still_valid_policy` and `persisted_policy_concurrent_process_writers_keep_highest_watermark` (a valid override is used). Missing: child-process tests in which an override of 64 zeros, `not-a-key` and a non-point key each leaves the compiled key effective, and in which changing the variable after the first `policy_public_key()` call does not change the result.
- [ ] 3.3 Only an authentic, well-formed, current policy is accepted. Existing evidence: the 16 tests in coverage row 3. Missing: `accept_policy` tests under a real key in which a signed policy with `min_required` changed after signing is rejected, and in which signed policies that are future-dated, expired, or have `valid_until` not after `issued_at` are rejected, each leaving the effective policy unchanged.
- [ ] 3.4 The rollback watermark is durable, protected and scoped to authority and network. Existing evidence: the seven tests in coverage row 4, including `network::tests::deployment_namespaces_do_not_collide`. Missing: a test that two consumer profiles on one `data_dir` whose network identities differ only in deployment ID keep separate watermarks under `<data_dir>/inference/<namespace>/version-policy/<authority>/`, and that the daemon and relay use the same layout.
- [ ] 3.5 An expired policy keeps its watermark and blocks new work. Existing evidence: `persisted_policy_expiry_retains_watermark_but_allows_fresh_advance` and `future_and_expired_policies_are_rejected`. Missing: a consumer test in which an expired effective policy makes `fund`, `topup` and `infer` fail with the expiry error before any journal entry, provider request or account file is written. The provider side is task 3.12.
- [ ] 3.6 A corrupt or insecure policy cache fails closed. Existing evidence: `persisted_policy_corruption_never_falls_back_or_overwrites_evidence`, `persisted_policy_requires_owner_private_files_and_lock` and `persisted_policy_never_persists_unsigned_future_watermark`. Missing: tests that a consumer with a corrupt cache refuses `fund`, `topup` and inference (today `Consumer::load` already fails) and leaves the cache unchanged, that `chiral_daemon` and `relay_server` exit before binding on one, and that a stored policy larger than the size limit is refused.
- [ ] 3.7 The placeholder authority is private-development behavior only. Existing evidence: the six tests in coverage row 7. Missing: process tests in which `chiral_daemon` and `relay_server` with development mode off exit with an error before binding when they have no policy file, and when their policy does not verify under the effective authority, including any policy under the placeholder.
- [ ] 3.8 The authority's private signing key stays offline with the operator. Existing evidence: none. Missing, besides task 2.1: nothing further once the regressions of task 2.1 pass.
- [ ] 3.9 Policies come only from configured sources. Existing evidence: `network::tests::transport_boundary` (the shared endpoint rules). Missing: a relay test that `GET /api/version-policy` returns the accepted policy with its signature; consumer tests with a loopback policy server (development profile) in which an unsigned, tampered, older, expired or unanswered policy makes `version_status` fail and leaves the watermark unchanged; and a `Consumer::load` test in which a profile whose `policy_url` has credentials, a query, a fragment or non-loopback HTTP fails to load without sending a request.
- [ ] 3.10 Native clients state their version and providers refuse a stated version below the minimum. Existing evidence: none. Missing: provider router tests in which, with an effective minimum of `2.0.0`, `X-Chiral-Client-Version: 1.9.0` on `POST /v1/contracts/propose` answers 426 `upgrade_required` and stores no quote, `banana` answers 400 `invalid_version`, and an inference request without the header is not refused for version; and a consumer test with a loopback provider that records the header on a proposal, an owner challenge, an owner-authorized request and an inference request.
- [ ] 3.11 A required update refuses new funding and native inference but keeps recovery reachable. Existing evidence: none. Missing: consumer tests with a required effective policy in which `fund`, `topup`, `infer` and `stream_kind` fail with the upgrade error before anything is journaled, sent or saved; in which `funding_recovery`, `cancel_funding`, `request_status`, `cancel_request` and `credential_revoke` are not refused by the client's own check; and in which a restart under the required policy leaves account files, credentials and the journal byte-identical. Also missing: a desktop dispatch test for the same refused and allowed operations, and a test that an unanswered `policy_url` refuses `fund`, `topup` and inference while leaving recovery operations unrefused.
- [ ] 3.12 A provider whose own version policy is unhealthy admits no new work. Existing evidence: none. Missing: provider tests in which a policy that expires while running, and a policy whose `min_required` is above the provider's version, make maintenance set `accepting` and `funding_ready` to false and publish no offer revision, while accounts, balances and fee obligations stay unchanged and an already admitted request still settles.
- [ ] 3.13 The desktop blocks the shell for a required update and shows a session-dismissible banner. Existing evidence: none. Missing, besides tasks 2.2–2.4: component tests in which a `required` status shows the current and minimum versions and the message as plain text; a `recommended` status shows the banner, and after dismissal it stays hidden through a refresh and a remount within one `sessionStorage`; an `ok` status shows nothing; and a successful profile load calls `get_version_status` and shows the modal for a required policy.
- [ ] 3.14 Upgrades preserve accepted state and the policy watermark. Existing evidence: `persisted_policy_corruption_never_falls_back_or_overwrites_evidence`. Missing: a test that every policy directory used by the consumer, daemon and relay lies inside the configured `data_dir`. The upgrade drill itself is task 4.1.
