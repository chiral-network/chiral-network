## Scope and authority

This is the missing request-accounting foundation identified while inventorying opening-intent task 2.8.2's remaining inference-settlement/resource-pressure acceptance. `docs/chiral-book.md` remains read-only. Its request lifecycle, durable-accounting, performance-accounting and provider-restart chapters require these financial transitions; the author-approved non-reserving decision forbids grafting fresh quote capacity onto existing recovery.

The change covers the ledger transitions and their gateway/usage/receipt boundaries. It does not redefine funding safe/reorg policy, fee remittance, credential issuance/rotation authority, the full model/API compatibility matrix, performance qualification/withdrawal classification, hardware evidence or public-release gates. It supplies no settlement endpoint accepting user-claimed tokens. Pending commercial and owner-control contracts remain dependencies, including their known source-ownership blockers.

## Decisions

### One operation, one durable first terminal result

Persist the account-scoped client key and an opaque ledger request ID with the reservation. Public duplicates report the original ID/status with 409 rather than reconstruct output. Account scope permits the same literal key for distinct accounts. An absent key creates a fresh UUID and cannot identify a lost request. Terminal retention is financially significant: deleting a row to clear a duplicate or restore a rate allowance would permit another chargeable operation.

The terminal accounting transaction owns the only transition out of `reserved`. A valid repeat returns the first committed result even if later supplied usage differs. This preserves known-usage debits, explicit unknown-usage releases and performance remedies equally; late evidence cannot silently re-charge a request already terminally released. Live cancellation signaling is not itself that terminal transition.

### Exact holds are separate from actual charges and funding fees

Use checked integer arithmetic and the immutable quoted price. Compute one ceil-rounded combined token cost for the maximum reservation and one for actual authoritative usage, not separate input/output rounding. The whole maximum hold is removed at settlement; only the actual charge is retained as spend. Zero-price work still occupies a request identity and applicable concurrency slots.

Reserve account available credit and credential cap authority in the same transaction. Cap accounting is `spent + reserved`, not a second spendable wallet. Credential revocation/rotation prevents new unauthorized work but cannot release or transfer a running hold. An independent funding/reversal transition is the only authority for its own fields; request settlement must not rewrite funding fees or create a replacement payment.

### Unknown exposure is not measured provider work or new balance

The whitepaper explicitly distinguishes reservation-sized exposure from measured loss. `RequestView.provider_loss_wei` records the original maximum hold when usage is unknown; zero stored counters carry an unknown status rather than claiming zero-token execution. This is distinct from `AccountView.provider_loss_wei`, which participates in the separate funding-orphan compensation identity. Accumulating request exposure into that account field would manufacture credit and is not permitted.

Invalid counts reaching the ledger deliberately commit a terminal zero-charge release before returning an invalid-usage error. This is not a failed transaction and must not be tested as rollback of the intended release. Genuine persistence failure cannot acknowledge settlement; the gateway stops admission and retained state is recovered rather than masked. Restart recovers only still-reserved requests, before new admission.

### Preserve current bounded inference controls without borrowing quote clocks

The current request-record windows allow at most 120 recent credential requests over the inclusive creation-time cutoff `now - 60`, and refuse after 30 account unknown-usage records over `now - 3600`. Keep these established consumer-visible controls and their provider-selected sample, including retained future rows on time regression. Do not present them as quote/challenge effective-minute watermarks or a measured-loss budget. Exact clock-edge acceptance needs a controlled operation-time input, not sleeps or substituted signed timestamps.

### Performance is a bound accounting input, not a synthetic qualification

Reservations already retain the actual admitted report under otherwise identical serving terms. Terminal outcomes must agree with that report/policy. An eligible waiver changes the charge, not known authoritative token counts, funding fees or report identity. Unknown restart may retain a waiver classification while nominal waived cost remains zero because usage is unavailable. The full classifier, per-token timing and durable withdrawal window remain governed by the whitepaper and separate future specification work; this change must not claim that ledger tests qualify a GPU or speed class.

Native receipts retain the original account model and price alongside each request's actual admitted report digest. The consumer therefore validates a canonical lowercase SHA-256 report identity, the contracted policy, remedy and accounting invariants, not equality with the original quote's report digest. Otherwise a correctly signed receipt becomes unreadable after the explicitly permitted evidence-only renewal, including while a renewed request is still reserved.

This is provider attribution, not independent qualification verification: `UsageReceipt` carries the report digest but neither the report bytes nor its measurement timestamp. Strictly newer, otherwise-identical renewal is enforced at provider admission and bound durably before dispatch. Receipt acceptance cannot independently reconstruct that check or attest actual execution. Preserve this trust limit rather than replacing the original agreement, requiring a still-current discovery offer for historical reads, or inventing missing report metadata.

### Recovery reads remain bounded and attributable

Preserve the current 100-request pages and signed receipt snapshots, persistent per-account receipt sequences, existing account-scoped read authorization and absence of content replay. Timestamp-only `before` pagination can omit other requests sharing the boundary timestamp when a client treats the last item as an exhaustive cursor; the contract therefore makes no exhaustive-history claim. Do not silently introduce a new cursor/response shape in this specification step. Task 2.3's `timestamp_before_pages_can_omit_requests_sharing_the_boundary_timestamp` demonstrates this limit: continuing from the last item's creation time skips the boundary tie's unseen requests, and continuing one second later repeats listed ones. It is a documented limit, not a defect, and the pagination semantics are unchanged.

No fresh quote/storage/work/issuance/opening gate may refuse an existing request's settlement or authorized read. Fresh inference still passes its own model/readiness, authority, capacity and balance checks. Resource independence is not permission to dispatch against an unavailable engine or override a proven frozen funding state.

### Same-key independent-writer acceptance

`inference_owner_control_test::same_key_writers_preserve_one_reservation_and_its_original_bounds` covers shared and distinct application credentials, each with known or unknown subsequent settlement. Each race opens two independent `BillingStore` connections before spawning workers, then releases both calls at a two-party barrier. It neither shares a store mutex nor assumes a particular winner or schedule. Setup failures cannot leave one worker waiting at the barrier.

The two candidates use the same account/key but different prepared inputs: one versus 1,000 prompt tokens, both with a 512-token output bound, requiring two versus three wei at the signed prices. An unrelated account already retains that same key. The target account starts with 100 funded, one previously spent and 99 available; application concurrency/cap headroom allows both candidates if their keys differ. Post-verification credit and supplied usage are ledger prerequisites, not live-chain or private-engine evidence.

Exactly one candidate must succeed and the other must return `duplicate_request`, not a saturation, cap or generic SQL failure. Complete snapshots preserve every unrelated record and signed prerequisite while adding only the winning opaque identity, credential, original token bounds and maximum hold. Reserved and terminal duplicates from fresh competing connections, before/after reopening, cannot move the hold to the losing credential or adopt its token counts.

Known settlement retains the winner's input count plus one output token, charges one or two wei respectively and releases exactly the unused hold. Unknown settlement releases the entire hold with zero known usage/charge and the original reservation-sized exposure. Both preserve the first result against a later changed terminal call and retain the client/opaque identities after reopening.

After settlement, the same two original shapes and credentials race with distinct keys. Both must reserve concurrently, totaling exactly five held wei; this positive control rules out lack of authority, balance, cap or account capacity as the earlier refusal. Sequential explicit unknown releases return exactly those holds without changing the original winner's charge/usage. Complete final snapshots, all three retained keys and exported credentials survive fresh readers and competing duplicate retries.

This completes only 2.2.3.1. Limit-refusal and terminal-result races are covered separately below; ordinary sequential replay here does not establish those races. Public dispatch, scheduler/load certification and process-kill durability remain separate.

### Independent reservation-limit races

`inference_owner_control_test::competing_reservations_preserve_cap_and_concurrency_boundaries` adds six cases: spend cap, credential concurrency and final account slot, each followed by known or unknown settlement. Two independently opened connections start distinct-key reservations at a barrier. Either may win; exactly one succeeds and the loser returns the specific limit refusal with no partial request or hold. Complete ledger snapshots include prior spend, credentials, retained agreements/funding and an unrelated account already using one candidate key.

The signed prices require two or three wei for the respective candidates. Each first application has one wei of prior known spend. For the spend-cap case, its five-wei cap permits either candidate alone but not their combined five-wei holds plus prior spend; two credential/account slots and available credit are sufficient. For credential concurrency, both candidates share one one-slot credential with an eight-wei cap and two account slots. For account concurrency, an existing three-wei root hold consumes one of two account slots while the candidates use separate two-slot credentials with ample caps. These prerequisites distinguish the limiting checks rather than accepting any generic refusal.

While the winner remains held, repeated losing admission and winning duplicate calls preserve exact state before/after reopening. An independent positive control then fits a one-wei hold under the same spend cap, uses a different one-slot credential on the same account, or uses the unrelated free account while the target account is full, respectively. The last control establishes account independence, not paid credit or fee behavior. Explicit unknown release of the control restores all prior financial state; it does not unblock the still-constrained loser.

Known winner settlement charges one or two wei and returns only its unused hold; unknown settlement releases its whole hold without invented usage. A fresh connection then admits the exact originally refused key, credential and token bounds. In the known spend-cap case this reaches the cap exactly, demonstrating that spent-plus-held equality remains admissible. Late replay of the first terminal result cannot release the new request's hold or charge again. The admitted loser is explicitly released for unknown usage; any earlier root hold remains intact until its own exact known settlement.

Final reopened reads and duplicates retain both identities, exact cumulative usage/spend and original credential authority. All financial expectations derive from the fixed candidate bounds and supplied usage, not a selected winner schedule or a second call to the production cost calculation. Post-verification credit and supplied usage remain prerequisites, not live-chain or engine evidence.

This completes only 2.2.3.2; competing terminal results are covered separately below. Gateway admission/dispatch and physical durability remain separate.

### Competing first-terminal outcomes

`inference_owner_control_test::competing_terminal_outcomes_commit_one_complete_original_result` covers all six unordered pairs of partial known usage, full known usage, explicit unknown usage and invalid over-bound usage without a serving profile. Ten profiled cases add a known-usage inference waiver to those candidates. Two independently opened connections start settlement of the same durable request at a barrier. No winner schedule or clock ordering is assumed.

Every target holds two wei for 500 prepared input and 256 maximum output tokens. With the signed one/two-wei input/output rates per thousand tokens, partial `(500, 128)` usage charges one wei, full `(500, 256)` usage charges two, a known waiver retains partial usage and records one waived wei, and unknown/invalid usage returns the entire hold with two wei of exposure and no known usage. The invalid candidate supplies 257 output tokens: it returns the intentional error only if it commits first; a later invocation returns the already-terminal result.

Complete expected snapshots are derived from one candidate's fixed amounts, usage, status, settlement time and bound performance input. Both return values and every ledger table must agree with that same outcome: no mixed usage/cost/status/evidence, double release, extra observation or losing timestamp is accepted. Existing fees, prior spend, an unrelated account using the same client key and a three-wei root hold remain unchanged. Profiled fixtures retain an old report's withdrawal while requests bind an otherwise-identical newer report.

Reopened ledger/router reads, repeated competing calls, stale report input and duplicate reservation cannot rewrite the committed result or original authority. Each candidate then independently commits against a fresh explicitly reserved control key, demonstrating its effect even when it lost the race. These controls are ledger operations, not automatic paid inference retries. Three newer-report misses latch withdrawal only in the all-miss cases; the old latch persists. The earlier root hold still settles its own exact three-wei charge, including after withdrawal, and final fresh readers and competing replays preserve all results.

The existing performance-failure fixture's signed 1,000-wei opening/profile construction is shared without changing its assertions. Synthetic profiles, post-verification funding and supplied usage remain prerequisites, not qualification, observed engine usage or live-chain evidence. This closes 2.2.3.3 and its scoped competing-writer parent 2.2.3, not expiry, gateway, performance-classifier or physical durability work. Pairwise races do not certify every scheduler interleaving or process-kill recovery.

### Credential expiry during an admitted hold

The specification requires a credential "unexpired at the provider-selected operation-time sample", and `account-credentials` defines `expires_at` as the time from which a credential no longer authenticates. `BillingStore::reserve` and `authenticate` refuse when `expires_at <= now`; `settle_request` reads the request's own credential and checks no credential state. Code and specification agree, so no production change was needed. These library tests (`billing_store::tests`) use the public ledger operation-time arguments, never sleeps or rewritten stored timestamps.

`credential_expiry_admits_through_the_last_second_and_refuses_new_holds_from_expires_at` issues an `infer`/`read` credential at time 102 with `expires_at` E = 1,000, no cap and two slots. A 30-wei reservation at E - 1 is admitted. The same bounds under a new key at exactly E, E + 1 and E + 90 days return `forbidden`, and the bearer returns `unauthorized`; complete rows of every ledger table stay identical before and after reopening, and the key stays unused. The account's live root then admits that exact key and bounds at E, so expiry alone caused the refusal.

`expired_credential_hold_settles_once_against_its_original_accounting` runs 24 cases. These are four terminal kinds × three successors × settlement at exactly E or a day later. The kinds are known `(10, 7)` usage, explicit `cancelled_unknown_usage`, `(10, 21)` usage over the reservation and restart recovery. The successors are a new issuance, explicit revocation followed by issuance, and rotation. Credential C (50-wei cap, three wei already spent) reserves 30 wei for `expiring-key` at E - 1. The root keeps a two-wei charge and an unrelated 10-wei hold, and a free account already used the same key. Before settlement the account holds 950 available, 40 reserved and 5 spent wei with five fee wei. From E, C's new reservations, including the held key, are refused with all rows unchanged. The successor starts at zero hold/spend. Revocation or rotation only marks C revoked, and the successor's same-key reservations return `duplicate_request` before and after reopening between expiry and settlement.

Expected rows are patched from fixed literals rather than the production cost function. Known settlement charges 17 wei to C and the account: 963 available, 10 reserved, 22 spent; C spent 20. Unknown and invalid usage release 30 wei with 30 wei of request exposure: 980 available, C spent three. Invalid usage returns `usage_over_reservation` after its release commits. Restart recovery also releases the root's 10-wei hold because it releases every reserved request: 990 available, zero reserved. Account funding-loss compensation, fees, funding and the other account never change. Later changed terminal calls and repeated recovery, before and after reopening, return the first result without changing a row. Ledger request, list and receipt reads attribute the request to C, and a receipt advances only the receipt sequence. Finally the successor's own one-wei control hold is charged to it alone and released.

`expired_credential_requests_stay_readable_and_unduplicable_through_the_routers` drives the production control and public routers, which read the real clock. A new `CredentialRoutes::opened_at` constructor opens the account at logical time 1,000,000, so credential C (E = 1,001,000) has necessarily expired for every route call. `CredentialRoutes::new` still opens at the current time through the same steps, now named `paid_at` (formerly `paid_now`). C's bearer gets 401 for status, cancel, control request and receipt reads, and for chat inference with the held key or a new key; no financial row changes. The owner proof reads the reserved request and rotates C into a live successor without moving C's 30-wei hold. The successor's chat request with the held `Idempotency-Key` gets 409 `duplicate_request` naming the original request and status, with that `x-request-id`, before tokenization or any engine call. Its cancel of that key only reads the request. Its `read` scope and the owner proof each read the request attributed to C and each obtain a signed receipt binding it, advancing only the receipt sequence. After explicit known settlement at E + 5, C is charged 17 wei and the successor nothing. The same reads, the 409 (now `completed`) and C's refusals still hold.

Thus reads after expiry follow the specification's existing owner/read-bearer authorization: an expired credential is not that authority, and a live read credential or owner proof is needed without implicit rotation. Mutations each failed the intended tests and were restored: reservation `<` instead of `<=`; settlement requiring a live credential; disabled ledger duplicate check; expiry-blind authentication; disabled gateway pre-dispatch duplicate check; revocation or rotation clearing a running hold. An independent review then added the owner-proof receipt read and confirmed that these further mutations fail: authentication still live at exactly `expires_at` (both ledger tests); reservation refused from `expires_at - 1` (all three); restart recovery skipping requests whose credential has expired (only the new settlement matrix catches it; `restart_releases_unknown_holds_and_preserves_deduplication` still passes); rotation carrying the hold to its replacement; settlement leaving an expired credential's spend unchanged; the gateway duplicate check, or the public status read, limited to the caller's own credential (router test); and owner proofs refused for receipts (router test, through the added owner receipt read).

The existing `application_concurrency_rotation_and_revocation_do_not_release_running_holds`, `caps_concurrency_revocation_and_scope_are_atomic`, `credential_caps_restrict_authority_and_never_create_or_refund_money` and `an_expired_or_revoked_credential_rotates_into_a_working_replacement` are unchanged and pass. The integration revoked-root settlement in `authenticated_free_and_paid_reopening_preserves_credentials_and_funding_without_readiness` is likewise unchanged. Live gateway dispatch, cancellation and settlement of a request whose credential expires mid-generation are not exercised because the gateway has no explicit operation-time input; they remain with 3.1. Post-verification funding and supplied usage remain ledger prerequisites, not chain or engine evidence. This closes 2.2.4.

### Invalid usage and inference-budget edge acceptance

Task 2.5 fills the ledger edges recorded above with nine `billing_store::tests`. Each step passes an explicit logical time through the existing public `reserve`, `settle` and `recover_requests` operation-time arguments. No stored timestamp is rewritten and no sleep is used. No signed timestamp or quote/challenge clock stands in for the inference sample. Complete rows of every ledger table are read through an independent connection with the 2.2.4 snapshot helper. Expected rows are patched from fixed literals, not from the production cost function.

`prompt_count_mismatch_commits_one_invalid_usage_release_of_the_whole_hold` reserves 30 wei for 10 prepared input and 20 maximum output tokens. A prior two-wei charge and an unrelated 10-wei hold sit beside it. Known usage (9, 5), (11, 5) or (0, 0) changes only the input count and would cost 14, 16 or zero wei, all within the hold. Each commits one `invalid_usage_unknown_usage` release, and `usage_over_reservation` is returned only after the commit. The release records zero charge and usage, returns the whole 30 wei and records 30 wei of request exposure. Spend, cumulative usage and the account funding-loss field do not change. Later valid, over-bound, unknown and repeated calls, before and after reopening, return the first result, and the key stays occupied. A control with the exact prepared count is charged 15 wei.

`cumulative_usage_overflow_commits_an_invalid_usage_release_without_wrapping` uses a signed model that admits any `u64` token count. Two known requests bring the account's prompt and completion counters to `u64::MAX - 100`. Three later requests match their own reservations, but their usage would carry the input counter, the output counter or both past `u64::MAX`. Each commits the same whole release and changes neither counter: no wraparound and no partial update. Exactly 100 + 100 tokens bring both counters to `u64::MAX` and are charged 200 wei. One further input or output token is then released. First results survive replay and reopening. A second account with zero counters charges every released shape as known usage, so the cumulative counters alone caused the release. Credentials hold spend and hold amounts but no token counters, so the account counters are the specification's cumulative usage counters.

`credential_inference_budget_admits_the_120th_record_from_an_inclusive_60_second_cutoff` gives one credential two records created at T - 61, one at exactly T - 60 and 118 in (T - 60, T], 119 counted in all. These end as known, explicit unknown, invalid and still-reserved outcomes. One T - 61 record is settled only at T, inside the window, and still does not count, so this window also uses creation time. At T the 120th reservation is admitted and the 121st refused, with unchanged rows before and after reopening. Settling the held request and the 120th restores no allowance, and the account's root is still admitted. At T + 1 the T - 60 record leaves the window and exactly one more reservation is admitted. `credential_inference_budget_cutoff_saturates_at_time_zero` opens a free account at logical time zero; zero-price requests keep their admission accounting. It has one record at 0 and 118 at 30. #### Code difference: unknown-usage budget status match

**Fixed 2026-11-21 by task 2.5.** The specification counts `*_unknown_usage` records toward the account budget. `settle_request` releases a request as unknown exactly when its status `ends_with("unknown_usage")`. `reserve` counted `status LIKE '%unknown_usage'`, in which SQLite's `_` is a single-character wildcard. A status such as `completed_unknownxusage` also matched: the ledger accepts it and charges it as known usage, yet it consumed unknown-usage allowance. `reserve` (`billing_store.rs`) now counts `status GLOB '*unknown_usage'`, the same suffix settlement classifies as unknown.

The fix changes no status the product itself produces. The gateway's statuses are `completed`, `cancelled`, `disconnected`, `timed_out`, `failed` and `interrupted`, each with or without `_unknown_usage`. The ledger adds `restart_unknown_usage`, `funding_orphan_unknown_usage` and `invalid_usage_unknown_usage`. All are classified identically under both patterns, so retained rows keep their meaning and no money state changes.
