## Scope and authority

This is the missing request-accounting foundation identified while inventorying opening-intent task 2.8.2's remaining inference-settlement/resource-pressure acceptance. `docs/chiral-book.md` remains read-only. Its request lifecycle, durable-accounting, performance-accounting and provider-restart chapters require these financial transitions; the author-approved non-reserving decision forbids grafting fresh quote capacity onto existing recovery.

The change covers the ledger transitions and their gateway/usage/receipt boundaries. It does not redefine funding safe/reorg policy, fee remittance, credential issuance/rotation authority, the full model/API compatibility matrix, performance qualification/withdrawal classification, hardware evidence or public-release gates. It supplies no settlement endpoint accepting user-claimed tokens. Pending commercial and owner-control contracts remain dependencies, including their known source-ownership blockers.

## Decisions

### One operation, one durable first terminal result

Persist the account-scoped client key and an opaque ledger request ID with the reservation. Public duplicates report the original ID/status with 409 rather than reconstruct output. Account scope permits the same literal key for distinct accounts. An absent key creates a fresh UUID and cannot identify a lost request. Terminal retention is financially significant: deleting a row to clear a duplicate or restore a rate allowance would permit another chargeable operation.

The terminal accounting transaction owns the only transition out of `reserved`. A valid repeat returns the first committed result even if later supplied usage differs. This preserves known-usage debits, explicit unknown-usage releases and performance remedies equally; late evidence cannot silently re-charge a request already terminally released. Live cancellation signaling is not itself that terminal transition.

### Exact holds are separate from actual charges and funding fees

Use checked integer arithmetic and the immutable quoted price. Compute one ceil-rounded combined token cost for the maximum reservation and one for actual authoritative usage, not separate input/output rounding. The whole maximum hold is removed at settlement; only the actual charge is retained as spend. Zero-price work still occupies a request identity and applicable concurrency slots.

Reserve account available credit and credential cap authority in the same transaction. Cap accounting is `spent + reserved`, not a second spendable wallet. Credential revocation/rotation prevents new unauthorized work but cannot release or transfer a running hold. An independent funding/reversal transition is the only authority for its own fields; request settlement must not rewrite funding fees or create a replacement payment.

### Unknown exposure is not measured provider work or new balance

The whitepaper explicitly distinguishes reservation-sized exposure from measured loss. `RequestView.provider_loss_wei` records the original maximum hold when usage is unknown; zero stored counters carry an unknown status rather than claiming zero-token execution. This is distinct from `AccountView.provider_loss_wei`, which participates in the separate funding-orphan compensation identity. Accumulating request exposure into that account field would manufacture credit and is not permitted.

Invalid counts reaching the ledger deliberately commit a terminal zero-charge release before returning an invalid-usage error. This is not a failed transaction and must not be tested as rollback of the intended release. Genuine persistence failure cannot acknowledge settlement; the gateway stops admission and retained state is recovered rather than masked. Restart recovers only still-reserved requests, before new admission.

### Preserve current bounded inference controls without borrowing quote clocks

The current request-record windows allow at most 120 recent credential requests over the inclusive creation-time cutoff `now - 60`, and refuse after 30 account unknown-usage records over `now - 3600`. Keep these established consumer-visible controls and their provider-selected sample, including retained future rows on time regression. Do not present them as quote/challenge effective-minute watermarks or a measured-loss budget. Exact clock-edge acceptance needs a controlled operation-time input, not sleeps or substituted signed timestamps.

### Performance is a bound accounting input, not a synthetic qualification

Reservations already retain the actual admitted report under otherwise identical serving terms. Terminal outcomes must agree with that report/policy. An eligible waiver changes the charge, not known authoritative token counts, funding fees or report identity. Unknown restart may retain a waiver classification while nominal waived cost remains zero because usage is unavailable. The full classifier, per-token timing and durable withdrawal window remain governed by the whitepaper and separate future specification work; this change must not claim that ledger tests qualify a GPU or speed class.

### Recovery reads remain bounded and attributable

Preserve the current 100-request pages and signed receipt snapshots, persistent per-account receipt sequences, existing account-scoped read authorization and absence of content replay. Timestamp-only `before` pagination can omit other requests sharing the boundary timestamp when a client treats the last item as an exhaustive cursor; the contract therefore makes no exhaustive-history claim. Do not silently introduce a new cursor/response shape in this specification step.

No fresh quote/storage/work/issuance/opening gate may refuse an existing request's settlement or authorized read. Fresh inference still passes its own model/readiness, authority, capacity and balance checks. Resource independence is not permission to dispatch against an unavailable engine or override a proven frozen funding state.

### Same-key independent-writer acceptance

`inference_owner_control_test::same_key_writers_preserve_one_reservation_and_its_original_bounds` covers shared and distinct application credentials, each with known or unknown subsequent settlement. Each race opens two independent `BillingStore` connections before spawning workers, then releases both calls at a two-party barrier. It neither shares a store mutex nor assumes a particular winner or schedule. Setup failures cannot leave one worker waiting at the barrier.

The two candidates use the same account/key but different prepared inputs: one versus 1,000 prompt tokens, both with a 512-token output bound, requiring two versus three wei at the signed prices. An unrelated account already retains that same key. The target account starts with 100 funded, one previously spent and 99 available; application concurrency/cap headroom allows both candidates if their keys differ. Post-verification credit and supplied usage are ledger prerequisites, not live-chain or private-engine evidence.

Exactly one candidate must succeed and the other must return `duplicate_request`, not a saturation, cap or generic SQL failure. Complete snapshots preserve every unrelated record and signed prerequisite while adding only the winning opaque identity, credential, original token bounds and maximum hold. Reserved and terminal duplicates from fresh competing connections, before/after reopening, cannot move the hold to the losing credential or adopt its token counts.

Known settlement retains the winner's input count plus one output token, charges one or two wei respectively and releases exactly the unused hold. Unknown settlement releases the entire hold with zero known usage/charge and the original reservation-sized exposure. Both preserve the first result against a later changed terminal call and retain the client/opaque identities after reopening.

After settlement, the same two original shapes and credentials race with distinct keys. Both must reserve concurrently, totaling exactly five held wei; this positive control rules out lack of authority, balance, cap or account capacity as the earlier refusal. Sequential explicit unknown releases return exactly those holds without changing the original winner's charge/usage. Complete final snapshots, all three retained keys and exported credentials survive fresh readers and competing duplicate retries.

This completes only 2.2.3.1. Limit-refusal races are covered separately below; competing terminal outcomes remain 2.2.3.3. Ordinary sequential replay here does not complete the terminal race. Public dispatch, scheduler/load certification and process-kill durability remain separate.

### Independent reservation-limit races

`inference_owner_control_test::competing_reservations_preserve_cap_and_concurrency_boundaries` adds six cases: spend cap, credential concurrency and final account slot, each followed by known or unknown settlement. Two independently opened connections start distinct-key reservations at a barrier. Either may win; exactly one succeeds and the loser returns the specific limit refusal with no partial request or hold. Complete ledger snapshots include prior spend, credentials, retained agreements/funding and an unrelated account already using one candidate key.

The signed prices require two or three wei for the respective candidates. Each first application has one wei of prior known spend. For the spend-cap case, its five-wei cap permits either candidate alone but not their combined five-wei holds plus prior spend; two credential/account slots and available credit are sufficient. For credential concurrency, both candidates share one one-slot credential with an eight-wei cap and two account slots. For account concurrency, an existing three-wei root hold consumes one of two account slots while the candidates use separate two-slot credentials with ample caps. These prerequisites distinguish the limiting checks rather than accepting any generic refusal.

While the winner remains held, repeated losing admission and winning duplicate calls preserve exact state before/after reopening. An independent positive control then fits a one-wei hold under the same spend cap, uses a different one-slot credential on the same account, or uses the unrelated free account while the target account is full, respectively. The last control establishes account independence, not paid credit or fee behavior. Explicit unknown release of the control restores all prior financial state; it does not unblock the still-constrained loser.

Known winner settlement charges one or two wei and returns only its unused hold; unknown settlement releases its whole hold without invented usage. A fresh connection then admits the exact originally refused key, credential and token bounds. In the known spend-cap case this reaches the cap exactly, demonstrating that spent-plus-held equality remains admissible. Late replay of the first terminal result cannot release the new request's hold or charge again. The admitted loser is explicitly released for unknown usage; any earlier root hold remains intact until its own exact known settlement.

Final reopened reads and duplicates retain both identities, exact cumulative usage/spend and original credential authority. All financial expectations derive from the fixed candidate bounds and supplied usage, not a selected winner schedule or a second call to the production cost calculation. Post-verification credit and supplied usage remain prerequisites, not live-chain or engine evidence.

This completes only 2.2.3.2; competing terminal results, gateway admission/dispatch and physical durability remain separate. Existing same-key and terminal-failure regressions are unchanged.

### Reservation write-failure acceptance

`inference_owner_control_test::reservation_write_failures_roll_back_request_and_both_holds` uses candidate-scoped SQLite `AFTER` triggers with `RAISE(FAIL)` at request insertion, account hold update and credential hold update. Unlike statement-level rollback, `FAIL` leaves that statement's writes inside its transaction, requiring the production transaction to undo both the failed mutation and any earlier writes. Each fault must produce its specific injected error before and after ledger/router reopening.

Complete snapshots of every current ledger table preserve account/credential authority, signed agreements, pending quotes, funding and fee evidence, counters, receipt sequences, earlier terminal outcomes and an existing three-wei root hold. A different account already owns the same client key. The candidate application's two-wei hold must leave no request or financial mutation on either failure; original bearers remain usable. Explicit removal of the isolated trigger then admits that same key once, changing only available credit from 96 to 94 wei, account holds from three to five wei, application holds from zero to two wei and the exact new reservation record. Complete successful state and duplicate refusal survive reopening.

Paid opening uses the existing post-verification fixture; prior settlement counts are supplied ledger inputs, not engine evidence. No production code, signed prerequisite or provider clock is changed. This proves reservation statement-failure rollback, not terminal transaction failure, invalid-usage release, commit/fsync or power-loss durability, concurrent-writer isolation, daemon startup recovery or gateway non-dispatch. Those acceptance tasks remain open; verification is recorded in APAS progress.

### Unprofiled terminal write-failure acceptance

`inference_owner_control_test::terminal_write_failures_preserve_holds_until_one_outcome_commits` crosses known `(1, 1)` usage, explicit unknown usage and output over the reservation with candidate-scoped `AFTER`/`RAISE(FAIL)` faults on account, credential and request updates. Each of the nine cases must surface its injected persistence error before and after ledger/router reopening while preserving complete current-ledger snapshots. An invalid-usage call whose transaction fails must retain its reservation, unlike the committed invalid-usage error below.

Setup retains a prior one-wei debit, an independent three-wei root hold, the application's two-wei target hold, a different account's same client key and a pending signed quote. Explicit fixture repair permits one terminal result: known usage charges one wei, releases the other wei and increments known usage; unknown and invalid usage release two wei, retain zero known usage/charge and record two wei of request exposure without changing account funding-loss compensation. Invalid usage returns `usage_over_reservation` after its release commits. All other records, including agreement, fee, credential authority and counters, remain unchanged.

The original key/opaque ID and exact first result survive reopening. Later changed known usage, unknown status and excessive usage return that result rather than charging, releasing or changing its time again; the key remains unavailable for another reservation. The reservation and terminal cases share the same complete-row snapshot helper without dropping earlier assertions.

These are unprofiled ledger statement-failure tests with post-verification funding and supplied usage, not engine validation or cancellation workflow evidence. Commit refusal and bound performance observation/withdrawal failures are covered separately below. Gateway shutdown, physical fsync/power-loss durability and actual daemon recovery remain distinct. No author decision or whitepaper change is required.

### Unprofiled terminal commit-refusal acceptance

`inference_owner_control_test::terminal_commit_refusal_preserves_original_accounting_recovery` reuses the complete terminal matrix without dropping the nine statement-fault cases. For each known, unknown and invalid-usage mode, a request-update trigger inserts a fixture-only witness of the newly written account, credential and request. Its missing-parent foreign key is `DEFERRABLE INITIALLY DEFERRED`: every settlement statement may finish, but the explicit production transaction cannot commit. This case contains no statement-level `RAISE`.

Before and after reopening, the provider must return the foreign-key commit error, not a successful settlement or a committed invalid-usage error. The complete original ledger snapshot, both holds, prior spend and credential authority remain intact; neither witness nor parent row survives the rejected transaction. The request remains reserved and recoverable under its original identity.

Explicit fixture repair inserts only the matching parent and leaves the trigger active. The original reservation then settles under the same exact known/unknown/invalid expectations, and one witness must commit with the complete expected account/credential/request snapshot. That witness, the first terminal result and all unrelated records survive reopening, changed late usage/status and duplicate refusal. Invalid usage reports its intentional release error only after this successful commit.

The test observes deterministic SQLite constraint rejection and rollback, not disk-full/fsync failure, power loss, gateway shutdown or performance-latch atomicity. Fixture repair is not a production repair policy or authorization to replay inference. Production source, signed funding prerequisites and the whitepaper remain unchanged; verification is recorded in APAS progress.

### Bound performance write-failure acceptance

`inference_owner_control_test::performance_write_failures_preserve_bound_waivers_and_withdrawal_latches` covers known, explicit unknown and invalid usage at three failure points: candidate-scoped `AFTER`/`RAISE(FAIL)` observation insertion, withdrawal insertion, and a deferred foreign-key commit refusal triggered after the withdrawal write. All nine cases use the complete ledger snapshot, including signed agreements, fees, credentials, requests, observation sequence and withdrawal keys. The existing unprofiled matrices remain unchanged.

The signed synthetic profile/agreement, 1,000-wei post-verification credit and supplied usage are explicit ledger prerequisites, not enrollment, engine or hardware evidence. Three original-report misses create its old latch through real settlement; an otherwise identical newer report then records one charge and two misses. A root request holds three wei and the target application's request holds two. Before the target, the account retains five wei of funding fees, one spent, five waived, five reserved and 989 available, with six known input and 1,536 output tokens. Original agreement/prices and the old latch remain immutable while each reservation binds the newer report.

Wrong original-report or policy input must fail before reaching the injected write fault. Each definite persistence failure, repeated after reopening, must preserve the complete initial state, both holds, pending admitted evidence and credential authority. Neither a failed new observation nor a failed new latch may survive; a deferred commit witness must also roll back. The old report remains withdrawn while the new report remains eligible until the target transaction commits.

After explicit fixture repair, the same target records the seventh observation and third newer-report miss with its new latch in one transaction. Known usage preserves 1,000 input/128 output tokens with a two-wei nominal waiver; unknown/invalid usage records no known usage or nominal waived cost and retains two wei of exposure. Both release only the target hold, leaving 991 available, three reserved, one spent and unchanged funding fees. Invalid usage reports its intentional error only after this state commits. The commit-fault trigger stays active and must retain exactly one successful witness.

Reopening, late different usage/status/report, duplicate reservation and fresh inference attempts against either withdrawn report cannot rewrite the result, charge again or clear a latch. The other previously admitted request can still settle its exact three-wei charge with known usage after withdrawal; its success adds one observation without clearing either latch. Complete final snapshots retain funding/fee evidence, unrelated state and exported credentials.

This closes the scoped ledger terminal-failure matrix, not gateway shutdown (3.1), the broader performance classifier/evidence inventory (3.2), physical fsync/disk-full/power-loss durability or public qualification. Fixture repair is not automatic product repair or inference replay. Production source and the whitepaper remain unchanged.

### Full-storage request recovery acceptance

`inference_owner_control_test::request_accounting_and_receipts_recover_at_full_quote_storage` starts with one unrelated free account and an explicitly post-verification paid opening. It reserves a capped application's request before filling standalone quote storage, then reserves another request against the original root at full storage. One genuine quote plus 9,999 complete signed restored records are prerequisites, not claimed historical public issuance. A genuine fresh quote receives 429/`rate_limit` while legacy wallet/rate ceilings have headroom; every retained quote and quote counter survives that refusal.

The test expects combined-rounding holds of 2 and 3 wei against the 100-wei balance. Known `(1, 1)` usage charges one wei and releases the unused part of its hold. Reopening and explicit startup recovery release the other three-wei hold as `restart_unknown_usage`, with zero charge/known usage and three wei of request exposure; account funding-loss compensation stays unchanged. Changed late usage/status cannot rewrite either terminal result. Scope, account/application concurrency, spent-plus-held cap and duplicate refusals leave no extra request or financial mutation.

At each reserved/known/unknown stage the actual control router serves exact account, credential, request-list and individual-request representations. Owner and read-bearer receipts bind the complete expected snapshot, network/provider and increasing persisted sequences across ledger/router reopening. Missing, infer-only, foreign-account and consumed authority are refused. Full-column fingerprints preserve quote/funding/fee/agreement/credential authority, while exact record comparisons permit only the intended hold/spend/usage changes and receipt sequence. Unrelated account state and sequence remain unchanged.

Fresh-admission/funding gates are closed and qualification cleared during recovery. This is ledger/control acceptance with no engine invocation, not public inference admission, actual usage validation, native client recovery, a daemon/process-kill experiment, safe-chain execution or public quote-policy mitigation. The existing gateway/independent-budget tasks remain open. Verification results are recorded in APAS progress.


## Acceptance sequence and ownership

1. The focused ledger/read acceptance inventory above maps actual test bodies and leaves unexercised boundaries explicit. Complete the separate gateway/backend inventory in 3.1 rather than treating names or ledger inputs as workflow evidence.
2. The full-storage regression above is the first independently useful missing slice. Retain its post-verification opening/history and supplied-usage disclosures; its ledger/router reopening is not public dispatch or a process-kill experiment.
3. Cover deterministic transactional faults and competing writers where not already covered. Inject faults only into isolated owned fixtures. Keep successful retry controls and exact monetary identities; do not weaken existing tests or normalize production failures.
4. Complete the actual gateway boundary: preparation before reservation/dispatch, duplicate/ambiguous response, known/unknown cancellation, failed durable settlement and status/receipt recovery. Reuse bounded private test backends only as explicit controlled evidence, never as runtime fallback or model qualification.
5. Extend independently to committed quote issuance and pre-signing work exhaustion when those implemented boundaries and controlled clocks are independently committable. Stored-quote occupancy is not evidence of those budgets. Retain new-inference gates throughout.

Production ledger/gateway/backend/app source and their private unit tests are owner-untracked migration work. Do not absorb them, expose production-only test APIs, copy the modules or commit a knowingly failing regression alone. Worker-owned integration acceptance can proceed when its public interfaces suffice. The missing pre-signing work implementation and existing quote-clock/cutover ownership blockers remain separate; no new author decision is required.
