## Decisions

1. **One capability for the current runtime.** `inference-offer-discovery` specifies what runs today: `/chiral/inference/manifest/1`, offers with an HTTPS `endpoint`, forced Kademlia server mode and no address filtering. Milestone 3 replaces the manifest protocol and changes peer addressing. When that change is implemented it has to modify *Manifests use the bounded, paged `/chiral/inference/manifest/1` protocol* and the protocol name in *Only a complete, valid, single-snapshot manifest withdraws that peer's cached offers* (task 4.3).
2. **What makes pages one snapshot.** Line 234 says that a "complete valid authenticated manifest" may withdraw and that "Partial or invalid manifests do not authorize deletion". Pages taken from two different states of a peer's manifest form a complete manifest of neither state, so they are partial. The `/1` response carries no snapshot marker, and adding one would change the wire format, which older peers reject (`deny_unknown_fields`, dht.rs:47–58). The receiver therefore uses evidence that the current publisher already provides. The native provider signs every offer of one refresh with one revision from one counter (app.rs:348–375), and the milestone 3 commercial-terms delta keeps "one persisted revision counter". So pages in which every offer carries one revision, and in which no later page is empty, come from one refresh. One page is always one snapshot. A publisher that gives its namespaces different revisions never gets a multi-page withdrawal; its stale offers leave other caches through expiry instead. That is the safe direction, and line 234 allows it ("Remote disappearance is bounded by refreshed complete manifests and signed expiry"). One case remains: a namespace that becomes publishable between two page fetches of the same refresh can shift a page boundary. It can then withdraw an older cached revision of that namespace; its current revision is higher than the kept watermark and is accepted again by the next complete search.
3. **Stable page order by namespace.** Today pages follow offer-ID order (dht.rs:443 and 518–519), and every refresh gives every offer a new ID, so every refresh reorders the whole manifest. Under decision 2 a search that straddles a refresh no longer withdraws anything, but with ID order it would still return an arbitrary subset of the peer's offers. Ordering by namespace keeps each namespace on its page while the set of namespaces is unchanged, so such a search still returns every namespace, at one revision or the other. An honest peer's republish then adds no incompleteness beyond what line 226 accepts for bounds and adversarial peers.
4. **A full registry refuses new namespaces.** Line 226 bounds the registry at 8,192 namespace entries and does not say what happens when it is full. Evicting an entry would let a flood of validly signed offers push out revision watermarks and reopen rollback within the retention horizon. Refusing keeps every watermark for its full retention, so watermarks count toward the bound. The code refuses (offer_registry.rs:321–323), and the launch-reputation change's scenario *A full registry does not change the class* already assumes refusal. The cost is that a long-running relay registry can be filled with signed namespaces, which keeps new namespaces out of its catalog until entries reach the end of their retention. One peer is enough: it contributes at most 64 offers to one search, but signing keys and deployment IDs cost nothing, so it can answer every relay refresh with 64 new namespaces and fill 8,192 entries in 128 refreshes (about 32 minutes at the 15-second refresh), then refill entries as their 3,630-second retention ends. Providers already in the registry are not displaced, because each refresh gives them a new revision and a new retention horizon. Line 226 accepts that "Bounds and adversarial peers make discovery incomplete". See Risks.
5. **A fresh registry per consumer call is intended.** Line 232: "Consumers create a fresh verification registry for each discovery call; do not describe revision comparison as permanent cross-session consensus." The scenario *Each call starts with an empty registry*, in which a later call returns an older revision, states this directly. A long-running relay registry keeps its state between searches (line 226).
6. **Publication follows new-funding readiness.** The provider publishes only after a refresh finds it new-funding ready (app.rs:342–347). Lines 252 and 630 pair new funding with publication ("A temporary chain outage can pause new funding/publication"; "Withhold unverifiable new credit/publication"), and lines 631 and 632 withdraw published offers on drain and on a managed child failure. An offer served while new-funding readiness is closed only leads to refused quote proposals (`inference-commercial-terms`, *Bounded public quote proposal is not owner authorization*). The code's own failure path (`refresh` withdraws the published set on error, app.rs:249–252) shows the same intent; it misses the offers published earlier in the failed pass (code difference 2). New-funding readiness can also close between refreshes: a funding verification that finds the RPC unavailable clears `funding_ready` at once (contracts.rs:553–556), and every refresh clears it while it runs (app.rs:257). The offers already published stay served until that refresh ends or the next refresh withdraws them. The requirement therefore ties publication to a refresh that found the provider ready and allows that window of at most one refresh interval, during which proposals are refused, instead of requiring the manifest to follow the flag instantly. That window is not a code difference.
7. **Readiness conditions.** The requirement lists the conditions that the book names and the code implements: drain, rejected chain evidence, a failed managed engine, no probe-ready model and an unreadable ledger close `ready`; a temporary RPC outage closes only `funding_ready`. Line 252 also lists "durable performance withdrawal" among things that "can prevent admission", but does not say whether it closes `ready`. Today it does not (open question 1). The spec does not decide it.
8. **Inspection exposes `ready`.** Line 254: the native readiness summary "presently exposes `ready`, not the separate raw `funding_ready` field", and clients that need the distinction read `/readyz`. The requirement forbids presenting `ready` as new-funding readiness and leaves adding `funding_ready` open. How the desktop shows it belongs to `desktop-gui-pages`.
9. **The catalog's reputation role is routing only.** Line 246 says which source is read for reputation and feedback whatever discovery uses. Requirement 12 states that routing and the "unavailable" result without a catalog. Feedback admission and the score are comparison item 10.
10. **The peer identity is a protected secret.** The identity key authenticates the peer. Whoever holds it can answer manifest requests as the provider, including with an empty complete manifest that makes every cache withdraw the provider's live offers, and in milestone 3 it authenticates the serving stream. Line 474 requires owner-protected secret files on Unix and Windows, and the code already treats the identity as owner-only on Unix (dht.rs:178–186). Requirement 2 therefore applies the same protection as the node's other secrets, which `wallet.rs` provides (code difference 3).
11. **Current implementation values (not normative constants).** Each may change without a spec change if the requirements still hold:
    - Connection admission: 64 pending inbound and 64 pending outbound handshakes, 192 established inbound and 256 established in total, 2 per peer identity (dht.rs:32–36). The limiter is the first behaviour, so it runs before any protocol handler (dht.rs:132–135).
    - Inbound manifest requests: at most 64 concurrent streams (dht.rs:246); request rates tracked for at most 256 peers; 32 requests per peer per 30-second window, the window starting at the peer's first request (dht.rs:449, 490 and 514–516).
    - Kademlia: server mode forced on every node (dht.rs:237), query timeout 8 seconds (228), `max_provided_keys` 128 and `max_providers_per_key` 64 (233–234). Milestone 3 replaces the forced mode.
    - Every node also runs the libp2p relay server behaviour with 128 reservations, 2 per peer, 128 circuits and 4 per peer (dht.rs:252–256). Milestone 3 owns relay limits.
    - Idle connections close after 120 seconds (dht.rs:275). Identify adds at most 8 listen addresses per message (507). The command channel holds 64 commands (313). Start waits 5 seconds for a listen address (316).
    - Search deadlines and local offer expiry are checked every 200 ms (dht.rs:447 and 476–491).
    - The provider signs every offer of one refresh with one new revision (app.rs:348–375). The counter file is `offer-revision` in the deployment directory, replaced through a synced temporary file and a synced directory (app.rs:143 and 219–243).
    - The native catalog client allows 30 seconds per page (consumer.rs:888) and 8 MiB per response (consumer.rs:296–307).
    - Inspection allows 10 seconds for each of `/healthz` and `/readyz` (consumer.rs:344) and 30 seconds for the reputation read (consumer.rs:623).
    - The relay catalog answers out-of-range pages with HTTP 400 `invalid_page` or `invalid_model` (relay_server.rs:67–78). An unknown query member gets axum's plain-text 400 because `CatalogQuery` rejects unknown fields (relay_server.rs:46–52).

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **A manifest assembled from pages of different snapshots counts as complete and can withdraw a live offer** (requirements 4 and 9, book line 234; comparison item 4). A peer keeps its local offers in a `BTreeMap` keyed by offer ID (dht.rs:443 and 456–458) and serves pages in that order (518–519). The offer ID hashes the whole payload, revision and times included (protocol.rs:850–852), and the provider signs every offer with a new revision at every 30-second refresh (app.rs:348–375), so every refresh reorders the whole manifest. The receiver treats the pages as complete when a page arrives with `next` `null` and no offer of that peer was invalid (dht.rs:535), and then withdraws every cached offer of that peer in scope that this search did not receive (538–544). Nothing checks that the pages came from one snapshot. Example: a relay caches peer `P`'s 9 offers at revision 5 (`P` has at least 9 models; configuration allows 64, provider_config.rs:109–111). The relay reads page 0, which holds 8 offers at revision 5. `P` refreshes to revision 6, so every offer gets a new ID and a new place. The relay reads page 8, which holds 1 offer at revision 6 with `next` `null`. In 8 of 9 cases that offer's namespace was already on page 0, so another namespace `Y`, ninth at revision 5, was received at neither revision. The relay withdraws `Y` at revision 5 and keeps its watermark. `Y` at revision 6 is live but missing from the relay's catalog until a later search receives it. The same happens when `P` stops publishing a model between the two pages and page 8 comes back empty. A consumer, whose registry is fresh, simply misses `Y` in that result. Severity low: it needs at least 9 offers from one peer and a refresh between two page fetches. Task 2.1.
2. **A failed refresh leaves the offers it published earlier in the pass served** (requirement 11, book lines 236, 252 and 630–632). `refresh_inner` publishes model by model (app.rs:352–389). When one publication fails, `?` returns before the offer IDs of that pass reach `published` (app.rs:386 and 391–395). `refresh` then closes `funding_ready` and withdraws only the IDs in `published`, which are the previous pass's (app.rs:249–252). Those previous offers were already replaced in the DHT's local manifest by namespace (dht.rs:457), so withdrawing their IDs changes nothing (dht.rs:461; offer_registry.rs:336–343), and the new offers of the failed pass stay in the manifest until they expire 120 seconds later (dht.rs:487–489). If the failure persists, every refresh publishes them again before failing, so they are served indefinitely while `/readyz` reports `funding_ready` `false`, `GET /admin/offers` lists nothing (app.rs:578–585) and quote proposals are refused. One trigger: a model whose signed offer exceeds 16 KiB. Configuration validation bounds devices and strings (performance.rs:36; provider_config.rs:118–119) but not the signed offer's size, and `offer_size_limit_counts_the_complete_signed_envelope` shows that a valid profile reaches the bound. Verified by reading; no test exercises publication. Task 2.2.
3. **The peer identity key file is not handled as a protected secret** (requirement 2, book line 474; `CLAUDE.md`). `dht::load_identity` (dht.rs:172–212) checks only the Unix mode bits of the path it reads (`std::fs::metadata` and `std::fs::read`, 178–188), so it follows a symbolic link and does not check the owner. On Windows every check is compiled out (`#[cfg(unix)]`), so a new identity file gets the directory's inherited access list and an existing one is read without any check. The node's other secrets use `wallet::create_secret_file`, `open_secret_file` and `validate_secret_file` (wallet.rs:44–87 and 136–155), which refuse links, check the owner and, on Windows, require a current-user-only access list without inheritance (wallet_windows.rs). Verified by reading; not executed on Windows. Task 2.3.

No other difference from the whitepaper was found. The DHT scope and index keys, record timing, bootstrap bounds, connection limits, manifest framing and bounds, offset and `next` rules, search bounds, registry bound, revision, equivocation, idempotent replay, withdrawal and retention rules, expiry, the durable revision counter, the 30-second refresh and 120-second offers, consumer source precedence, the catalog page contract, the native catalog client, `/healthz`, `/readyz` and native inspection match the requirements.

Line 288 marks address filtering as new work for the target design; it belongs to `specify-p2p-provider-transport` (*Learned addresses are filtered before dialing or advertising*) and to comparison item 11.
- Every node runs Kademlia in forced server mode and the relay server behaviour (dht.rs:237 and 252–256). Milestone 3 owns both (*Every node selects its Kademlia mode from AutoNAT-confirmed reachability*, *Serving relays enforce explicit operator-chosen limits*).
- A peer whose Identify agent version is below the effective policy minimum is disconnected (dht.rs:502–506). The book's discovery section does not state this; it belongs with the version policy (pending `specify-version-policy`).
- The relay's own `/api/health` and `/api/ready` (relay_server.rs:97–130) belong to relay lifecycle (comparison item 14).
- An unknown query member on `/api/offers` gets axum's plain-text 400 instead of the JSON error used for out-of-range pages (decision 11). This resembles comparison item 6; the book does not specify catalog error bodies.
- `/readyz` reports `ready` `true` while every probe-ready model is performance-withdrawn: `accepting` requires only that some model passed its readiness probe (app.rs:335–339), and the probe checks the withdrawal latch only when the engine is busy (inference_backend.rs:1374–1377). Admission and publication still refuse such a model (app.rs:63–70 and 353). Open question 1.
- Each consumer DHT discovery starts and stops a complete DHT service with the profile's persisted identity and `listen` address (consumer.rs:857–865). Two concurrent discoveries from one profile with a fixed listen port contend for that port, and the second fails without falling back. The book's current-runtime discovery section does not address it; the existing report entry "2026-11-17 — Two processes on one consumer profile and its libp2p identity" and the target-design requirement *A consumer libp2p identity runs in one process at a time* (`specify-p2p-provider-transport`) already cover it, so no new question is raised.

## Open questions for the whitepaper author

1. **Does `/readyz` report a provider whose every probe-ready model is performance-withdrawn as ready?** Line 252 says `/readyz` reports serving readiness and that "durable performance withdrawal can prevent admission"; line 633 keeps the latch durable; line 636 says `/readyz` "reports serving readiness". The book does not say whether a provider with no admissible model is serving-ready. Today `ready` is `true` (and `funding_ready` can be `true`) when every model passes its readiness probe but is performance-withdrawn; every request and new quote for those models is then refused, and no offer is published for them. Options: (a) keep `ready` provider-wide, as today, with the withdrawal enforced at admission and publication; (b) make `ready` `false` when no configured model is admissible, counting performance withdrawal. Proposed default (what the spec adopts): (a), by not listing performance withdrawal among the conditions that close `ready`. Nonblocking: no requirement or task waits on the answer; (b) would add one condition and one task.

## Risks

- All executable evidence above is loopback or in-memory. The migration plan records earlier live discovery: "Provider/relay discovery traversed real libp2p/Kademlia. An independent second payer opened a paid account through signed discovery" (`docs/llm-serving-migration-plan.md` line 467, from the vLLM-era private run) and keeps "independently operated public deployments, adversarial/relay-outage/lifecycle matrix" open (line 494) and the multi-provider discovery, revision, withdrawal, relay-outage and catalog-limit exercise unchecked (line 507). Task 4.1 tracks current evidence.
- Task 2.1 changes which manifests withdraw. A publisher that gives its namespaces different revisions loses multi-page withdrawal and relies on expiry. Decision 2 records the remaining narrow case.
- Task 2.1 changes the order of offers within the manifest, not the wire format, so old and new peers still interoperate. Until every peer is upgraded, a new receiver still reads old peers' ID-ordered pages, but its snapshot check keeps them from withdrawing live offers.
- Decision 4: one peer, or many, can fill a relay's registry with signed namespaces and keep new providers out of that relay's catalog for as long as it keeps refilling it. Providers already listed keep updating. Consumers that use the DHT directly start each call with an empty registry and are affected only within one search's 64-peer sample.
- Task 2.3 can refuse an existing identity file that is a link or, on Windows, has an inherited access list. The operator then has to protect the file without replacing it, because line 236 says to preserve the DHT identity ("deleting them is not recovery"). The error must say so.
- Requirements reference capabilities from pending changes (`inference-commercial-terms`, `desktop-gui-pages`, `profile-path-resolution`) and name the target-design changes `specify-p2p-provider-transport` and `specify-provider-launch-reputation` by change name. Task 4.3 sets the archive order.
- The implementation values in decision 11 are not normative. Changing one needs no spec change, but this design should be updated to match.
