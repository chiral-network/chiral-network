## 2. Close code differences

- [x] 2.1 Withdraw only on a manifest whose pages come from one snapshot, and serve pages in a stable order (requirements 4 and 9, design code difference 1, comparison item 4). In `src-tauri/src/dht.rs`:
  - Serving: order the manifest by namespace `provider_wallet/deployment_id/model.id`, for example by keying `local` by namespace instead of offer ID. The `Withdraw` command, which takes an offer ID, then finds that ID's namespace. A republish must keep each namespace on its page.
  - Receiving: record, for each peer in a search, the revision of every offer received and whether any page after the first was empty. On the page whose `next` is `null`, withdraw only when no offer of that peer was invalid, every page after the first held at least one offer, and every offer received from that peer carries one revision. Otherwise insert the valid offers and withdraw nothing. A one-page manifest is unaffected.
  Regressions, which fail without the change. One way to write them is to factor the completion decision into a function of the pages received and to test the page builder directly:
  - a peer with 9 offers at revision 5, cached by the receiver, that republishes all 9 at revision 6 between the receiver's page 0 and page 8: no cached offer is withdrawn, and all 9 namespaces are listed at revision 5 or 6;
  - the same peer withdrawing one model's offer between the two pages, so that page 8 holds no offers and `next` is `null`: no cached offer is withdrawn;
  - a page builder test in which the same 9 namespaces republished at a new revision keep their pages.
  Keep `direct_signed_manifest_discovery_and_withdrawal` passing; it covers withdrawal by a complete one-page manifest.
  Done 2026-11-18: `dht.rs` keys the local manifest by namespace (`serve_local`, with the registry's `offer_registry::namespace`) and builds each page with `manifest_page`. `Withdraw` removes the entry that holds the offer ID. `receive_page` records in a per-peer `PeerManifest` the accepted IDs, every revision received, any empty page after the first and any rejection. It withdraws only when `PeerManifest::complete` holds: no rejection, and one page, or no empty later page and one revision. Regressions in `dht::tests`, each of which failed with its part of the change neutralised (the snapshot condition, or offer-ID keys for the local manifest): `manifest_straddling_a_republish_withdraws_nothing` (9 offers cached at revision 5; page 8 fetched after a republish at revision 6, both as this peer serves it and as an offer-ID-ordered peer can serve it, repeating a namespace from page 0), `manifest_that_shrank_between_pages_withdraws_nothing` and `republished_namespaces_keep_their_manifest_pages`. `complete_snapshot_manifest_withdraws_an_omitted_offer` shows that a complete two-page manifest at one revision, and a one-page manifest with mixed revisions, still withdraw an omitted offer. `direct_signed_manifest_discovery_and_withdrawal` passes.
- [x] 2.2 Withdraw every offer that a failed refresh published (requirement 11, design code difference 2).   Done 2026-11-18: `refresh_inner` adds each offer ID to `published` as soon as its publication or local registry insertion succeeds, so the failure path of `refresh` withdraws the failed pass's offers together with the earlier set. Regression `app::tests::failed_refresh_withdraws_the_offers_it_published`: a non-development provider with two embedding models, a chain fixture with a current `safe` frontier and engine fixtures that pass the readiness probe publishes both offers when it starts, and a DHT service started for the test discovers both. - [ ] 2.4 Keep remote provider records from blocking this node's own index advertisements (requirements 3, 10 and 11; found in the round-39 review). The Kademlia `MemoryStore` holds this node's own index keys and the provider records other peers store here under one bound (`max_provided_keys = 128`, `dht.rs:343–345`). Inbound ADD_PROVIDER is unfiltered and every node runs in server mode, so any peer, or a network with more than about 127 distinct model keys, can fill it. Once it is full, any refresh that must advertise a new index key fails: the first start, or any refresh after a failure withdrew everything. The provider then stays not new-funding ready until the remote records expire (600 s TTL). The book requires admission-bounded DHT resources (`CLAUDE.md`) and a provider that publishes while it can accept new funding (line 630). This needs a design choice, noted under design Risks: either bound local and remote keys separately, or refuse inbound records once a reserve for local keys is reached. Regression: fill the store with another peer's records, then a refresh still advertises and serves its offers.
