## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

- *API compatibility and model qualification* (lines 579–603), read in full:
  - 581: ordinary bearer authentication, no custom version header for stock clients, control-protocol compatibility enforced at onboarding;
  - 583–589: the implemented endpoint table;
  - 591: route existence is not capability; offers pin revisions, template digest, quantization, limits and capabilities; readiness probes exercise actual preparation and inference before publication; eight named failures surface honestly, not as fake responses;
  - 593: GGUF capability derivation; the artifact identity; tokenizer revision equals GGUF revision; no Python tokenizer or safetensors path; exact engine token IDs; usage reconciliation rejects truncation and retokenization mismatches;
  - 595: readiness verifies the actual model, template and context and probes every advertised capability, including streaming, echo/logprobs and tools/structured output when offered; model cards and downloads do not establish compatibility; engine instrumentation stays private; content is never a token counter;
  - 597: completion echo and log-probabilities; full-context stops;
  - 599: embedding dimensions;
  - 601: tools and JSON-schema output need separate qualification; out-of-scope surfaces; embeddings have zero output limit and rate, no template and no speed badge;
  - 603: SDK onboarding with an exported scoped bearer and the origin plus `/v1`; output and tool arguments are untrusted data; the provider never runs returned tools.
- Other lines: 77 (no cross-provider execution and no customer-supplied code execution), 167 (the six capability names), 337 (listing and capabilities are account and model scoped, not the marketplace), 502 (request bodies bounded), 520 (no rerouting to another provider), 530 (supported options validated before execution), 536 (output accounting covers attributable generated tokens, not visible text), 558 (timing starts after the complete bounded body), 628 (model, template, tokenization and capability probes gate readiness; a process or `/health` answer is not qualification), 656 (engine tokenization, metrics and model loading are not public API).
- Not turned into requirements: line 599's "The pinned Nomic GGUF was exercised at its native 768 dimensions" and line 601's "Historical embedding artifacts and results remain in the migration plan, not hard-coded current profiles" are evidence statements. No source file under `src-tauri/src` or `scripts` (tests aside) hard-codes a Nomic or BGE profile; the 768 in requirement 10's scenario is an example, not a constant.
- `docs/provider-qualification.md` lines 45–47 (provisioning: named templates, embedding task, no executed model code) and 417–418 (generation only for speed qualification; echo/logprobs probed on the public paid contract).
- `CLAUDE.md`: "Qualify each advertised capability with exact tokenizer/template identity and real inference/usage probes"; "Generation and embeddings have separate task/capability/limit contracts"; "Do not expose tokenization, template, metrics, slots, model management or arbitrary engine endpoints through the public gateway"; "Public inference authenticates before body buffering, bounds simultaneous body readers and bytes, and separates body-read deadlines from generation/SSE deadlines. Preserve non-queuing admission and reservation limits"; "Model output is untrusted data, never HTML or executable tool instructions".

Where the code differs, the requirement follows the whitepaper and an unchecked task records the code change. Requirements are never weakened to match the code. Values that the book does not state are recorded under decision 4 as current implementation values, not as normative constants.

Out of scope, each owned elsewhere:

- **Route scopes and credentials**: `account-credentials`.
- **Request identity and accounting**: `Idempotency-Key`, exact tokenization before reservation, bounded output and `n = 1`, authoritative usage, early truncation and retokenization mismatch, unknown usage, status, receipts and cancellation are owned by `inference-request-accounting`.
- **The signed model declaration** (revisions, template digest syntax, limits, capability syntax), the managed GGUF binding of model and tokenizer revision, separate generation and embedding tasks, and the zero embedding output price are owned by `inference-commercial-terms`.
- **Timing and instrumentation**: the private engine stream behind both public modes, the token clock, removal of `token_ids`, timings and verbose metadata from public output, overload refusal and speed qualification are owned by `inference-generation-performance`.
- **The engine process**: launch, inventories, the engine-reported revision, model identifier, slots and context, and health-only readiness refusal are owned by `managed-engine-runtime`.
- **Origins**: the private engine origin, the SDK base URL, TLS ingress and the preflight probe of private routes are owned by `outbound-http-safeguards`.
- **The version header**: owned by `client-version-policy`. **Rendering model output**: owned by `desktop-gui-global-rules`.
- **Daemon lifecycle**: `/healthz`, `/readyz`, drain, resume, refresh cadence, child failure and shutdown are comparison item 14. The point-in-time meaning of readiness and publication on refresh is in `inference-offer-discovery`.
- **Target design**: the desktop local API server (`specify-desktop-local-api-server`), free unqualified shares published after readiness probes (`specify-desktop-share-online`, book line 167) and catalog probes (`specify-provider-launch-reputation`). When implemented they build on requirements 1, 2 and 8; this change does not present them as current.

## Decisions

1. **One capability for the current runtime.** `public-inference-api` specifies the provider's public OpenAI-compatible routes that run today. The target-design local server and shares reuse it when implemented.
2. **Reference the owners, do not restate them.** Requirements name the owning requirement and add only the missing obligations. In particular, requirement 2 refers to `client-version-policy` for the missing-header rule and to `inference-generation-performance` for the private stream behind both modes, and requirement 9 refers to `inference-request-accounting` for the refusal of early truncation.
3. **Readiness covers what `managed-engine-runtime` left open.** That change verifies the engine-reported revision, model identifier, slots and context and leaves the template, tokenization and capability probes to this item (its requirement *The contract is never reduced to make a model fit*). Requirement 8 states them for every configured model, managed or external, because `probe_model` (inference_backend.rs:1370–1397) runs the same probes for both.
4. **Implementation values.** None of these is in the book or normative:
   - **Bounds** (inference_backend.rs:16–19; inference_gateway.rs:31–32): request bodies at most 256 KiB, at most 64 bodies read at once, a 5-second body deadline, engine responses at most 16 MiB, one SSE event at most 64 KiB, embedding batches of 1–32 non-empty strings, each at most the context and together at most 32 × context tokens (604–650).
   - **Request members** (`prepare`, 219–515; `validate_messages`, 149–215): a strict allowlist per route (224–265); 1–256 messages with roles `system`, `developer`, `user`, `assistant` and `tool`; at most 64 text parts; 1–32 function tools whose names are 1–64 of `[A-Za-z0-9_-]` and descriptions at most 4,096 bytes; tool-call arguments at most 32 KiB; JSON schemas at most 32 levels deep with only local `$ref`; `strict` function tools refused; `tool_choice` only `auto` with tools and only `none` without; `stop` at most four strings of at most 256 bytes; `logit_bias` at most 256 entries in −100..100; `temperature` 0–2, `top_p` 0–1, penalties −2..2, `seed` a signed 64-bit integer; chat `top_logprobs` and completion `logprobs` 0–5; `n` exactly 1; an output limit of 1 to the model's maximum, defaulting to the smaller of the model's maximum and 256; `encoding_format` `float` or `base64`; `dimensions` an integer 1–16,384; `Content-Type: application/json` (inference_gateway.rs:448–458).
   - **Members the gateway adds for the engine** (443–445 and 487–503): `add_generation_prompt`, `continue_final_message` and `chat_template_kwargs.enable_thinking=false` for chat; `n_probs`, `cache_prompt=false` and `return_tokens` for generation; `verbose` and `response_fields` for completions. Every public generation request runs as a private stream with `include_usage` (inference_gateway.rs:495–500), and `echo` is removed before dispatch and reproduced by the gateway from the request's own prompt (inference_backend.rs:484–486 and 1036–1061).
   - **Error codes** (all in the OpenAI-style envelope `{"error":{"message","type","param","code"}}`, error.rs:50–68):
     - authentication: 401 `invalid_api_key` for a missing, repeated, malformed, unknown, revoked or expired bearer (inference_gateway.rs:149–164; error.rs:28–30), and 403 `credential_scope` (165–171);
     - invalid options and missing capability: 400 `unsupported_parameter` (inference_backend.rs:57–59), 400 `invalid_json` (inference_gateway.rs:490–492), 415 `invalid_content_type` (448–458);
     - bodies: 400 or 413 `invalid_request_body` (480–486), 408 `request_timeout` (473–479);
     - model mismatch: 403 `model_scope` (inference_backend.rs:266–272); other agreements: 503 `model_unavailable` (inference_gateway.rs:501–510), 409 `model_revision_unavailable` (515–521), 503 `model_unqualified` (522–528 and 571–577);
     - credit: 402 `insufficient_balance` and 402 `credential_spend_cap` (84–95);
     - saturation: 429 `provider_saturated` (body readers and the account-window table, 223–229 and 464–470), 429 `rate_limit_exceeded` (231–237 and 102–107), 429 `model_saturated` (531–537), 429 `rate_limit` (arrival envelope, 545–548), 429 `engine_saturated` (inference_backend.rs:666–671);
     - context overflow: 400 `context_length_exceeded` (598 and 644–647);
     - engine: 503 `engine_unavailable` for a non-success health answer and 502 `engine_error` when the health request itself fails (568–585), 502 `engine_error` for any other engine failure or invalid engine response (60–62), 502 `engine_usage_mismatch` (1085–1094), 504 `tokenization_timeout` (inference_gateway.rs:557–563), 504 `engine_timeout`;
     - provider and account: 503 `provider_paused` (430–436 and 564–570), 403 `account_paused` (437–443);
     - unknown routes: 404 `not_found` and 405 `method_not_allowed` (app.rs:501–510).
     A failed stream sends `data: {"error":{…}}` followed by `data: [DONE]` (inference_gateway.rs:844–851).
   - **Listing** (`models`, inference_gateway.rs:242–259): `{"object":"list","data":[…]}` with one OpenAI model object and a `chiral` extension (`model`, `max_embedding_batch`, `max_request_bytes`, `requests_per_account_minute`, `tool_choice: "auto_only_when_qualified"`, `cancellation_billing`). The model is listed only while the provider is accepting new inference, the account's status is `active` or `free`, and `qualified_model` (app.rs:63–70: engine alive, model in the qualified set, no performance withdrawal) finds the deployment that accepts the agreement; otherwise the answer is HTTP 200 with empty `data`. The book states only that the listing is credential-scoped (lines 337 and 585), so these conditions are implementation behaviour, not part of requirement 3. `account-credentials` task 2.2 relies on that 200 answer.
   - **Streaming**: a public stream is a queue of four chunks (672) with `text/event-stream`, `cache-control` and `x-accel-buffering: no` (743–763); every response carries `x-request-id` (203–208). Usage appears in a stream only when the client sets `stream_options.include_usage` (inference_backend.rs:281–290 and 1336–1341).
   - **Readiness**: `model_health` runs on every refresh (app.rs:261), at start, every 30 seconds (427) and on operator refresh; at most four models are probed at once (inference_backend.rs:1358); a probe has the smaller of the model's request timeout and 60 seconds (1380); inference probes run only while every slot of the model is free, which `probe_model` takes (1374–1377); a model that is already ready and busy repeats only the identity, evidence and template checks (738). Probe bodies (749–794): chat "Reply with OK." and completion "A" with one output token; streamed variants with log-probabilities; a streamed completion echo of a fixed sentence (1251); embeddings of `["A","MiXeD case"]` in `float` and `base64`; a `ping` function that must be called with `{}`; a JSON schema `{}` with `strict`.
   - **Echo offsets** count Unicode scalar values of the prompt and of each token (943 and 1018–1021).
5. **Errors are named, codes are not normative.** Requirement 6 requires that each failure the book lists is reported as that condition and never as a fabricated success. The status and error codes in decision 4 are implementation values.
6. **"Client error" is what the provider can determine.** Requirement 6 forbids reporting, as an engine failure, a refusal that the provider can determine from the request and the agreement. An engine's own rejection of a request the gateway accepted stays an engine failure (observation 5).
7. **`streaming` is probed, not required for SSE.** Requirement 2 requires both modes for chat and completion models, from the endpoint table (lines 587–588). Provisioning never adds `streaming` (requirement 7), and the qualification runner accepts generation without it (`test_generation_capabilities_do_not_require_separate_streaming_flag`). Requirement 8 therefore requires only that an advertised `streaming` is exercised by a streamed probe on a generation endpoint, and that a model whose advertised `streaming` cannot be exercised is not ready (code difference 1). Open question 1 asks whether SSE should depend on the token.
8. **Dimensions are refused before execution.** Line 530 requires the gateway to validate supported options before execution, and line 591 requires invalid options to surface honestly. Requirement 10 therefore refuses unproducible dimensions before reservation (code difference 2). How the provider learns the deployment's dimension is left to task 2.2; open question 3 asks whether it should be signed.
9. **Tools on managed deployments.** A managed launch requires the configured capabilities to equal the artifact's derived capabilities (engine_runtime.rs:152), and provisioning derives only endpoint capabilities (requirement 7). So `tools` and `structured_output` cannot currently be advertised by a managed deployment, and outside development generation requires a managed runtime (provider_config.rs:114–137). Requirement 8 still specifies their probes, because the book requires them "when offered" and the code implements them. Open question 2 asks how they may be offered.
10. **The listing states scope only.** Requirement 3 requires what lines 337 and 585 state: the bearer sees its own account's model and nothing else. Hiding that model while the provider is paused, the account is paused or the model is not ready is current behaviour (decision 4), not a whitepaper rule, so it is not normative here. Requests are refused in those states by requirement 6 and by the owners it names.
11. **Readiness identity applies to every engine.** Line 595 requires readiness to verify "llama.cpp's actual model/template/context" without distinguishing managed engines. `managed-engine-runtime` verifies the source revision, slots and per-slot context only for managed engines, so requirement 8 states the model identifier, context and template check for managed and operator-owned engines alike. `qualification_probe` already performs them for both (inference_backend.rs:702–737). For an operator-owned engine the "actual model" is the engine-reported alias and context, not the GGUF bytes (observation 8).
12. **No action on a request's behalf.** Requirement 11 reads line 603 ("the provider API does not run returned tools on a consumer's behalf"), line 601 (tool execution outside this release) and line 77 (no customer-supplied code execution) as excluding any provider action for a request beyond inference on its own engine. The refusal of a remote `$ref` in tool parameters and response schemas (`schema`, inference_backend.rs:114–137) is the current implementation of "SHALL NOT cause the provider to fetch a remote resource".

3. **A failed stream whose error event cannot be queued ends like a normal stream** (requirement 6; book line 591). `stream_worker` (inference_gateway.rs:825–852) reports a failure by a `try_send` of `data: {"error":…}` and `data: [DONE]` (844–851). The public stream is a queue of four chunks (672) drained by `event_stream` (743–763). When the client has stopped reading and the response has backed up past the transport's buffers (the kernel socket buffers on HTTP/1, which absorb small streams first), the queue is full and `stream_inner` waits in `send_chunk` (812–824). A failure at that point (the generation deadline in `send_chunk`, or an engine error) makes the `try_send` fail. The error event is dropped, the sender is dropped, and the body ends cleanly after the queued output chunks, with no error event, no `[DONE]` and no finish reason. A stock OpenAI SDK iterates such a body to its end without raising. The ledger records the failure (for example `timed_out_unknown_usage`), so the client's only signal is a stream that looks unfinished. Severity low. Verified by reading; `bounded_backpressure_remains_cancellable` tests only that a blocked send can be cancelled. Task 2.3.

   Fixed 2026-11-19 by task 2.3. When `stream_worker` cannot queue its error event, it sets a flag shared with `event_stream` (inference_gateway.rs:702, 777 and 896) before dropping its sender, and the body then ends with an error after the queued chunks, so the chunked response is not terminated normally. Successful streams still end with `data: [DONE]` and a clean end. Regression: `inference_gateway::tests::a_stream_that_fails_while_the_client_is_not_reading_does_not_end_cleanly` (in-process `tower::Service`, six output events, a 1 s deadline and an unpolled body; the body ends with an error after four events), which fails without the change.

A tokenizer that adds no beginning-of-sequence token returns no tokens for an empty prompt, so the client is told its prompt exceeds the context when it is empty. The refusal happens before reservation, so no money is affected, but an invalid input is named as a different condition, which line 591 ("invalid options ... context overflow ... must surface honestly") separates. Severity low. Verified by reading; whether the pinned engine returns an empty list for the reference GGUF tokenizers is not established by any test, and `tokenized_input_must_leave_room_for_authorized_output` asserts only that an oversize prompt fails. ## Observations

1. **Readiness's non-streaming generation probes use the engine's non-streaming mode** (`probe`, inference_backend.rs:797–899, with `request.stream` false and the `read_json` path at 864–898), which no public request uses: the gateway executes every generation request as an engine stream (inference_gateway.rs:495–500). The engine stream that public non-streaming requests rely on is exercised by the streaming probes, and the collection into one response (`collect_event`) is local code with a unit test. Not a difference from line 595; task 3.8 asks for a router test of the collection.
2. **Structured output**: readiness exercises `json_schema` only (inference_backend.rs:790), while `json_object` is accepted under the same capability (422).
3. **Tools**: readiness exercises one function with `tool_choice` `auto` and no tool-result turn, while public requests may carry `tool`-role messages and assistant tool calls (184–212).
4. **Template digest at readiness**: readiness hashes the engine-reported `chat_template` with plain SHA-256 (728–730), while provisioning and launch use the normalized digest of the effective source (provision-model.py:270–274; engine_runtime.rs:117–129). They agree only if the pinned engine reports the effective (normalized) source, as the launch comment states. Otherwise a valid deployment fails closed. No test runs readiness against the pinned engine with a template that has a CRLF or a trailing LF (task 4.1).
5. **Engine rejections are engine failures**: when the engine rejects a request the gateway accepted (for example a JSON schema the engine's grammar conversion cannot handle), the answer is 502 `engine_error`. At template rendering this is before reservation (`Backend::tokenize`, 609–611; `read_json`, 902–907); at dispatch it is after reservation and settles as unknown usage (664–675). Requirement 6 covers only refusals the provider can determine from the request and the agreement (decision 6). Not verified against the pinned engine; not recorded as a difference.
6. **Busy refresh**: a model that is already ready and whose slots are all busy at a refresh repeats only the identity, evidence and template checks, not inference (inference_backend.rs:738 and 1374–1377). Open question 4.
7. **The qualification runner's echo check** (`probe_completion_echo`, qualify-provider.py:152–173) checks only that the text starts with the prompt and that log-probabilities are an object; it does not check the offsets or that only generated tokens are covered. Recorded as code difference 5 and fixed 2026-11-20 by task 3.9.
8. **External embedding deployments** outside development are not managed, so their capability derivation is not verified at launch, and readiness identifies their "actual model" only by what the engine reports: its `/v1/models` identifier, `model_alias`, `n_ctx`, slot count and build commit (inference_backend.rs:702–726). Nothing verifies the GGUF bytes, revision or tokenizer of an operator-owned engine. Whether embeddings must also be managed is the report question of comparison item 3. Code difference 1 depends on this path.
9. **The listing's empty answer** is HTTP 200 with empty `data` (decision 4). Requirement 3 states only what is listed. `account-credentials` task 2.2 relies on the 200 answer to tell a valid credential from an invalid one.
10. **Consumer side**: native `infer` refuses streaming for embeddings before any request (consumer.rs:2405; desktop.rs:224). The GUI's capability-limited endpoint choices are owned by `desktop-gui-pages`.

## Open questions for the whitepaper author

All four are nonblocking: no requirement or task waits on an answer.

1. **Does SSE on a generation route require the `streaming` capability?** Line 167 lists `streaming` as a capability, and line 595 requires it to be probed. The endpoint table (lines 587–588) says chat and completion models serve "non-streaming and SSE". Provisioning never adds `streaming`, and the gateway serves SSE without it. The options are:
   - (a) serve SSE only for models that advertise `streaming`, and have provisioning derive it for generation;
   - (b) serve SSE for every chat and completion model, with `streaming` informational, as now.

   Proposed default, which is what the spec adopts: the book text. Requirement 2 requires both modes for chat and completion models, and requirement 8 requires an advertised `streaming` to be exercised.
2. **How may `tools` or `structured_output` be offered on a managed deployment?** Line 601 requires "separate capability qualification" and forbids adding them from a model card. A managed launch requires the configured capabilities to equal the artifact's derived capabilities (engine_runtime.rs:152), and outside development generation needs a managed runtime, so neither can be offered today (decision 9). The options are:
   - (a) a separate qualification step that records tool and structured-output probe evidence and extends the signed capabilities;
   - (b) not offered in this release.

   Proposed default, which is what the spec adopts: the book text. Requirement 7 forbids automatic addition, requirement 8 requires probes when offered, and no procedure is specified.
3. **Should the native embedding dimension be signed or listed?** Line 599 says arbitrary reduction "is not advertised". `ModelSpec` has no dimension, so a consumer learns it from a response. The options are:
   - (a) add it to the signed model declaration (a wire change);
   - (b) report it in the `/v1/models` extension after readiness has measured it;
   - (c) neither, as now.

   Proposed default, which is what the spec adopts: the book text, with nothing signed. Task 2.2 needs the provider to know the dimension before dispatch, for example from its readiness probe, not from a signed term.
4. **Must readiness repeat its inference probes while a model stays busy?** Lines 591 and 628 make probes gate readiness and publication, with no cadence. Today a busy, already ready model repeats only identity checks (observation 6). The options are:
   - (a) reserve or schedule probe capacity so that inference is re-exercised within a bound;
   - (b) as now.

   Proposed default, which is what the spec adopts: the book text. Requirement 8 requires probes before a model first becomes ready and withdrawal after a failed probe, and sets no cadence.

## Risks

- **Task 2.1 can make an existing deployment not ready.** An external or development deployment that declares `streaming` without a generation endpoint will stop being ready and published. The operator removes the token; managed deployments are unaffected.
- **Task 2.2 needs the native dimension before dispatch.** If readiness learns it, a model is not ready until its embedding probe has recorded it, and a restart learns it again. It must never be learned from a client's request or response. Refusing every `dimensions` member would break stock clients that send the native value.
- **Task 2.3 changes how a failed stream ends.** An abnormal end must never be produced for a successful stream, and a successful stream must still end with `[DONE]`. A regression over real HTTP/1 with a few small output events does not reproduce the difference: hyper drains them into the kernel socket buffers, the queue is empty when the deadline fires, and the error event is delivered. The regression must leave the queue full, by holding the response body unpolled in-process or by streaming more output than the socket buffers hold.
- **Timing-sensitive fixtures.** The stream regression of task 2.3 uses a short generation deadline and a client that pauses; use generous margins so it is not flaky on a loaded host.
- **Task 2.4 must not refuse valid prompts.** An empty prompt on a tokenizer that adds a beginning-of-sequence token still prepares into one token and stays valid. Only an empty prepared input changes its refusal; a prompt longer than the context keeps its context-overflow refusal.
- **What the evidence is.** All executable evidence is unit or loopback-stub testing. The template digest, echo, tools, structured output and dimensions against the pinned llama.cpp engine need a real engine run (task 4.1). No evidence here is public-release qualification.
