## Decisions

1. **One capability for the current runtime, `payment-gated-reputation`.** Admission, storage, the Elo calculation, revalidation and the native client share one evidence model and one relay router. The target-design launch reputation is a separate observer with its own store and stays in `provider-launch-reputation`.
2. **Every malformed body is `invalid_feedback`, and an oversized one stays HTTP 413.** Line 441 says that invalid submissions return `invalid_feedback`. A body that does not decode as a `FeedbackSubmission` is an invalid submission, whether the defect is a content type, JSON syntax, trailing content after the JSON value, an unknown member, a wrong type or an out-of-range integer. Today the typed `Json<FeedbackSubmission>` extractor (rating_api.rs:94) rejects most of these before the handler, with axum 0.7.9's plain-text bodies: 415 for a missing JSON `Content-Type`, 400 for a syntax error and 422 for a data error such as an unknown member or `score` 300 (axum `src/extract/rejection.rs:9–40`, `src/json.rs:157–176`). It accepts trailing content, because `Json::from_bytes` never calls `Deserializer::end` (axum `src/json.rs:157–160`). Code difference 1, comparison item 6. A body over 64 KiB is refused by the body limit (rating_api.rs:89) before it is read as feedback; 413 is the HTTP meaning of that refusal, so it stays. Neither refusal takes a verification slot: decoding happens before the slot is acquired.
3. **Unavailable chain evidence is never a rejected payment or an ineligible vote.** Line 441 says that unavailable RPC evidence fails a snapshot with 503 rather than serving a known-stale score, and line 439 lists only invalid evidence, rejected execution and pending or non-canonical payment as reasons for ineligibility. `inference-funding-settlement` (*Chain evidence comes from signed bytes and the configured identity-checked RPC*) already classifies a configured-identity mismatch and a receipt that contradicts the signed transaction as unavailable. The rating paths reuse that classification. Code difference 4.
4. **A store fault is a catalog failure.** Line 441 maps invalid, stale and conflicting submissions to three codes. A database that cannot be written is none of these. The provider's own `ApiError::internal` rule (error.rs:32–40) says internal errors "can contain … database content and must never enter the response". Code difference 2. A capacity refusal is a refusal of that submission, not a fault; its code is an implementation value (decision 11).
5. **Native results name the catalog's code.** Line 441 defines eight outcome codes with different remedies: wait (`payment_pending`), retry later (`feedback_busy`, `chain_unavailable`, `chain_timeout`), revise (`expired_feedback`, `feedback_conflict`) or stop (`invalid_feedback`, `payment_rejected`). Line 443 forbids implying that the provider is at fault when the catalog or its RPC is down. Today the native client classifies catalog responses with the provider-error table, so every one of these becomes "Provider operation failed; inspect account and request status before retrying" (consumer.rs:308–313 and 316–340). Code difference 3.
6. **"Free" has two current tests, and the native client checks only one locally.** Line 395 defines the catalog's rule: funding positive and at least one rate nonzero. In the current runtime a free opening saves no opening payment, so the native client refuses an account without one (consumer.rs:2378–2381) and leaves a positive-funding, zero-rate quote to the catalog. The local refusal of that second case is target design (`provider-launch-reputation`); requirement 4 says so instead of requiring it now.
7. **The Elo arithmetic is normative, with its order and rounding.** Lines 421–433 state the formula exactly and say that the tie-break "matters because updates are sequential". Scenarios state results rounded to one decimal place, so they do not depend on the last bits of the `f64` arithmetic. They were checked with an independent Python evaluation of the formula: 52.4, 46.0, 50.0, 49.6 versus 50.4, and `w_amount` 1.17629 and 1.60987.
8. **Revalidation repeats every admission check except freshness.** Line 439 says the catalog "revalidates stored provider/payer signatures and the opening payments". The code re-runs `validate_submission` with the current time (rating_api.rs:57–61), whose time checks cannot newly fail for stored evidence, and does not re-run the 300-second rule (rating_api.rs:106). The spec states that.
9. **The vote key is `quote_id`, as the book states.** Line 413 says "one row per quote/account (`quote_id` primary key)". A quote's `id` is a random value chosen and signed by the provider (protocol.rs:411–413), so the provider of an agreement can sign a second quote with the same `id` for a wallet it controls, pay itself from that wallet, and vote first; the real payer's later vote then fails with `feedback_conflict` (rating_storage.rs:74–77). The spec keeps the book's key. Open question 1.
10. **Every snapshot revalidates every stored vote within one deadline, as the book states.** Line 439 requires revalidation "before returning a provider's snapshot", and line 441 sets a 30-second deadline. Each vote takes two complete observations of six RPC calls each (`eth_chainId`, `eth_syncing`, the `safe` and latest blocks, the receipt and the canonical block; chain_client.rs:561–575, 608–624, 808–855), made one vote after another (rating_api.rs:55–81). Eight of the twelve calls, the block and receipt reads, wait for a 300 ms interval that the whole chain client shares (chain_client.rs:23 and 540–548). The spec keeps the book's rule. Open question 2.
11. **Current implementation values (not normative).** Each may change without a spec change if the requirements still hold:
    - Types: `score` is `u8`, `revision` and `issued_at` are `u64` (reputation.rs:17–19); a `revision` above 2^64 − 1 cannot be represented.
    - Error body: the shared `ApiError` JSON object `{"error":{"message","type","param","code"}}` (error.rs:49–67).
    - The snapshot route refuses a non-canonical wallet with HTTP 400 `invalid_wallet` (rating_api.rs:152), before taking a slot.
    - A capacity refusal is answered HTTP 400 `feedback_conflict` with "feedback registry capacity reached" (rating_storage.rs:104–106; rating_api.rs:143).
    - Store: `<data_dir>/<network-scoped directory>/feedback.sqlite` (relay_server.rs:176 and 212–215), WAL with `synchronous=FULL` and a 5-second busy timeout (rating_storage.rs:20–22); the network identity is stored as canonical JSON in `rating_network` (22–42); a provider's votes are read 1,000 at a time, equal to the per-provider bound (113).
    - Background reconciliation sleeps 30 seconds before each page, reads the next 32 distinct provider wallets in string order after a cursor (rating_storage.rs:147), gives each refresh a 30-second deadline, and clears the cursor after an empty page (rating_api.rs:178–206).
    - The success body's `revision` is a JSON number (rating_api.rs:145); the snapshot's `base_elo` is the number `50.0` (reputation.rs:149).
    - Native timeouts: 30 seconds for the inspection read (consumer.rs:623) and 120 seconds for the submission (consumer.rs:2404).

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **Malformed submissions get axum's plain-text rejection instead of `invalid_feedback`** (requirement 2, book line 441; comparison item 6). `submit` takes `Json(submission): Json<FeedbackSubmission>` (rating_api.rs:94), so axum rejects a body that does not decode before the handler runs. axum 0.7.9 answers a missing or non-JSON `Content-Type` with 415 "Expected request with `Content-Type: application/json`", invalid JSON with 400 "Failed to parse the request body as JSON: …", and a data error (an unknown member of `Feedback` or `FeedbackSubmission`, a wrong type, `score` 300, which does not fit `u8`, or a missing `quote`) with 422 "Failed to deserialize the JSON body into the target type: …", each as `text/plain`. A client therefore cannot rely on the documented error object or code for these submissions. Conversely, a valid submission followed by trailing content (for example `{…} x` or a second JSON object) is accepted and processed. `Json::from_bytes` deserializes without `Deserializer::end` (axum `src/json.rs:157–160`); a scratch program reproducing that call with the locked `serde_json` 1.0.149 and `serde_path_to_error` 0.1.20 accepted `{"a":1} trailing garbage`, which `serde_json::from_slice` refuses as a syntax error. Mapping `JsonRejection` alone therefore does not close this difference; the body must be decoded so that trailing content fails. The body limit (rating_api.rs:89) already answers 413, which stays. Task 2.1. Fixed 2026-11-18 by task 2.1.
2. **Store faults are reported as `feedback_conflict` with database text** (requirement 7, book line 441). `submit` maps every `RatingStore::upsert` error to HTTP 400 `feedback_conflict` with the error string as its message (rating_api.rs:140–143). `upsert` returns SQLite errors as `e.to_string()` when it opens its transaction, reads the previous row, counts rows or commits (rating_storage.rs:61–64, 65–72, 94–103, 109), "corrupt feedback revision" (78–80), and, for any failed insert, "payment already voted or storage failure: {e}" (107). A locked or unwritable database is therefore reported to the submitter as a conflict, which invites a new revision instead of a retry, and the response carries SQLite text such as "UNIQUE constraint failed: feedback.tx_hash". The genuine conflicts (changed evidence, a stale or equivocal revision, a reused payment) and the capacity refusal remain refusals. Task 2.2. Fixed 2026-11-18 by task 2.2.
3. **The native client reports every catalog answer as a provider failure** (requirements 11 and 12, book lines 441 and 443). `Consumer::feedback` and the reputation read in `Consumer::provider_info` decode catalog responses with `response_bytes` (consumer.rs:624 and 2408), which classifies an error status with the provider table `safe_error` (consumer.rs:308–313 and 316–340; the fallback is line 338). None of the catalog's codes is in that table, so `invalid_feedback`, `expired_feedback`, `feedback_conflict`, `feedback_busy`, `payment_pending`, `payment_rejected`, `chain_unavailable` and `chain_timeout` all become "provider_error: Provider operation failed; inspect account and request status before retrying (HTTP n)". Inspection then shows this text as the reason reputation is unavailable (Marketplace.svelte:241), which attributes a catalog or RPC outage to the provider, and the feedback form loses the difference between "wait", "retry", "revise" and "stop". Task 2.3. Fixed 2026-11-18 by task 2.3.
4. **Untrustworthy chain evidence is treated as a rejected payment in the rating paths** (requirements 5 and 9, book lines 439 and 441). `ChainClient::identity_check` returns `Rejected` for a chain-ID or genesis mismatch (chain_client.rs:561–575), and `execution_receipt_fields` returns `Rejected` for a receipt whose hash, sender, recipient, type or gas contradicts the signed transaction (chain_client.rs:658–683). At submission, `submit` maps `Rejected` to HTTP 400 `payment_rejected` (rating_api.rs:130–133). At revalidation, `refresh` sets every such vote ineligible and persists it (rating_api.rs:68 and 78–80), and the snapshot is then served, possibly as the neutral baseline, instead of 503 `chain_unavailable`. Eligibility returns at the next healthy revalidation, so no evidence is lost, but a wrong-network RPC serves a score that was never checked. This is the rating-path counterpart of `specify-funding-settlement` code difference 4 (its task 2.4). Task 2.4.

## Observations outside this capability

- Rating verification runs the two RPC observations before it compares the feedback's `tx_hash` with the hash of the signed bytes (rating_api.rs:36–50). A submission with a mismatched hash is still rejected, but only after about twelve RPC calls. This is efficiency, not a whitepaper rule.
- The native client signs with the loaded wallet's address (consumer.rs:2385) rather than the saved quote's `consumer_wallet`. With a different wallet loaded, the catalog refuses the vote as `invalid_feedback`. No wrong vote can result.
- A required update refuses native `feedback` (desktop.rs:151). Which operations stay available is `specify-version-policy`'s open question 1.
- The relay also mounts the unauthenticated `/api/chain/rpc` route on the same listener (relay_server.rs:232). That is `specify-chain-rpc-gateway`'s open question 1. It shares the relay's one `ChainClient` with rating verification (relay_server.rs:195–198, 210–216 and 232), and its block and receipt reads pass through the same 300 ms read pacing (chain_client.rs:918–930 and 540–548). The proxy admits 32 concurrent reads and 64 per second (chain_rpc_api.rs:328–335), far more than the one paced read per 300 ms that the client serves in FIFO order. Unauthenticated proxy callers can therefore delay each rating verification past its 30-second deadline, so submissions and snapshots answer 503 `chain_timeout`. Open question 2 records the effect on snapshots.
- `desktop-gui-pages` design row 8 cites the feedback form at `Usage.svelte:338–352`; it is now at 356–369. Line drift only.

## Open questions for the whitepaper author

1. **Can a provider pre-empt its consumer's vote by reusing the quote ID?** Line 413 keys a vote by `quote_id`. A quote's `id` is random and chosen by the provider (protocol.rs:411–413). The provider of an agreement can sign a second quote with the same `id` for a wallet it controls, pay itself a 1-wei opening from that wallet, and submit a vote for it as soon as that payment is safe. When the real payer later votes, the stored row has another payment hash, and the vote is refused as `feedback_conflict` (rating_storage.rs:74–77). Unlike the Sybil limits line 365 discloses, this removes a real payer's vote, at the cost of gas. Options: (a) keep `quote_id` as the key, as today, and disclose the limitation; (b) key a vote by the quote commitment `Keccak256(P_quote)` that the opening calldata binds, or by `(quote_id, consumer_wallet)`, so that only the funded agreement's own payer occupies its row; (c) another rule. Proposed default (what the spec adopts): (a), because it is the book's text. Nonblocking; (b) would add one task with a store migration.
2. **Must every snapshot revalidate every stored vote within 30 seconds?** Line 439 revalidates before each snapshot and line 441 sets a 30-second deadline. Each vote takes twelve sequential RPC calls, eight of which wait for the chain client's shared 300 ms read interval (decision 10). One vote therefore takes at least about 2.1 seconds even against an instant RPC, and a snapshot can revalidate at most 12 votes with canonical payments within the deadline: the 13th vote's last paced read falls at about 30.9 seconds. A provider with 13 or more such votes, of the 1,000 the store allows, can then never be read: every snapshot answers 503 `chain_timeout`, and the background pass restarts from the first vote on each attempt, so its later votes are never revalidated. Concurrent verifications and callers of the relay's `/api/chain/rpc` proxy share the same pacing and lower this ceiling further (observations). Each read is unauthenticated and holds one of the four shared slots for up to 30 seconds, so four concurrent reads also make submissions answer 429. Options: (a) as today; (b) serve a snapshot from the votes' most recent revalidation when every one of them was revalidated successfully within a stated bound (for example by a background pass that revalidates vote by vote and keeps its progress), and answer 503 only when one is older than the bound or was unavailable, which keeps "never known-stale" as a stated bound; (c) another rule. Proposed default (what the spec adopts): (a), because it is the book's text. Nonblocking; (b) would add one task.

## Risks

- All executable evidence above is synthetic: SQLite and loopback RPC fixtures, and handler calls without HTTP. The migration plan records only that free embedding sessions "could not submit payment-backed feedback" (`docs/llm-serving-migration-plan.md` line 473). Feedback eligibility, reputation updates and relay outage across independently operated relays, providers and consumers remain open release gates (book lines 771 and 773; plan lines 504 and 507). Task 4.1 tracks them.
- Tasks 2.1, 2.2 and 2.3 change client-visible error responses. The native client is the only known client, and task 2.3 updates it in the same step.
- Task 2.4 should share the classification that `specify-funding-settlement` task 2.4 introduces for the funding path, for example a distinct contradictory outcome in `ChainClient`, so that the two paths cannot diverge. If that task changes `ChainClient` first, the rating paths need only their mapping.
- Requirements reference capabilities from pending changes (`inference-funding-settlement`, `inference-commercial-terms`, `inference-offer-discovery` and `desktop-gui-pages`). Task 4.3 sets the archive order.
- The implementation values in decision 11 are not normative. Changing one needs no spec change, but this design should be updated to match.
