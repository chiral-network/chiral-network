## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

- *Configuration and state*, line 449: "Paths in consumer/provider configurations are resolved relative to their configuration file. Select a profile deliberately in native desktop Settings or use `chiral --config consumer.json`." Lines 459, 461 and 464 name the consumer's path-valued fields: `network.rpc_bearer_file`, `data_dir` and the DHT `identity_file`.
- *Shared signing-wallet directory*, line 470: every process spending the same signing wallet on a network "must use the **same configured `data_dir` base** and coordinated journal", and `ChainClient` appends `inference/<hash-of-full-network-identity>/wallet-journal/transactions.sqlite3` itself.
- Line 472: consumer accounts, credentials, request keys and wallet state are network-scoped; the DHT identity is preserved with the rest of the state; "Changing paths or restoring an older layout without deliberate state preservation is not an upgrade strategy."
- *Version policy*, line 650: the policy rollback watermark persists under protected storage; it lives under the consumer's `data_dir`.
- Line 652: "Upgrades must preserve accepted ledgers, acknowledgements, identity, shared nonce journals, credentials and evidence."
- *Backup, incident response, and cutover*, line 673: before upgrades, take a consistent protected backup of the ledger, the shared wallet journal, consumer account and credential state, keys and configuration.
- *A.5.8 Settings*, line 960: the desktop loads a consumer profile by file path through `configure {path}`; "on success the session becomes configured".
- `CLAUDE.md`: "Processes using the **same signing wallet must share the same base `data_dir`/nonce journal**" and "CLI stdout is machine-readable JSON or explicit streaming events. Diagnostics belong on stderr."

The relay and RPC-gateway configurations are not named on line 449. Including them extends the same rule to the other two configuration files, matches their current code (`relay_server.rs:150–170`, `chiral_rpc_gateway.rs:74–83`) and matches the operator guide (`docs/provider-qualification.md` line 173: "their supported relative paths resolve against their own config file's parent directory").

The change was prompted by item 2 of `docs/apas-worker/comparison-2026-11-18.md`: `Consumer::load` decoded the profile and passed it to `Consumer::new` unchanged, so relative paths were taken from the process working directory, and `chiral wallet create` run from another directory created state there.

## Decisions

1. **One small capability, `profile-path-resolution`.** The rule applies to four configuration files and to the nonce journal, wallet and policy watermark at once. Putting it into `inference-funding-settlement` would cover only the journal; putting it into a consumer-only capability would leave the provider, relay and gateway rules implicit.
2. **Resolution is lexical and identical to the provider's.** `Consumer::load` reuses `provider_config::resolve_path` (now `pub(crate)`): a relative path is joined to `path.parent()`, an absolute path is unchanged, and nothing is canonicalized or created. A profile path without a directory component (`--config consumer.json`) has an empty parent, so its paths stay relative to the working directory, which is then the profile's directory. Symbolic links are followed by the file system when the paths are used, exactly as for providers.
3. **Command-line path arguments are not configuration paths.** `wallet import FILE`, `wallet export FILE`, offer, quote and options documents, `--version-policy`, and the gateway's `--journal-dir` and `--bearer-file` keep following the working directory, as any command-line tool does and as `docs/provider-qualification.md` line 173 already tells operators. Only paths written inside a configuration file change meaning with the file's location.
4. **Old state is detected at exactly two places per field, and only refused.** For `data_dir`, the check compares the network-scoped directory `<data_dir>/inference/<hash>` at the old working-directory interpretation and at the resolved location, and then the consumer wallet key `<data_dir>/inference/<hash>/consumer/wallet.key` at both; for the two file fields, the files themselves. The wallet-key comparison is needed because every load, even a read-only `network show` or a failing `wallet address`, creates the network-scoped directory, an empty journal and the policy directory at the resolved location. Without it, one command run from another working directory would leave a scaffold that made a later `wallet create` from the old working directory silently start a second wallet beside the old one (found in review and reproduced: two different addresses). Detection needs one `symlink_metadata` call per candidate path (at most eight per load), so it is cheap and never scans. Existence decides, not path comparison, so two spellings of one location (`data` and `./data`) can never be refused: the same location is either present at both or absent at both. The check runs before `Consumer::new` creates any directory.
5. **The refusal never moves state.** Moving a wallet directory while another process (for example a provider sharing the journal) uses it, or merging two journals, could split nonce ownership (book line 470). The client therefore refuses and names both deliberate remedies: an absolute `data_dir` pointing at the existing state, or a move performed by the user after stopping every process that uses it.
6. **Any state of this network at the old location counts, not only a consumer wallet.** The network-scoped directory also holds the shared wallet journal, which a provider may have created. Refusing in that case is conservative: under the old behaviour this profile would have used that journal, and silently starting a separate one could split a wallet's nonce coordination if the consumer and provider share a key. The message offers the absolute path, so an operator who intends separate state can say so explicitly.
7. **When both locations hold state, the profile's own location wins.** "Both" means both network-scoped directories exist and, if the working-directory location has a consumer wallet key, the resolved location has one too (decision 4). The resolved location is what the profile now means, and the user has either moved state there or created it deliberately. The working-directory copy is left untouched. Whether the client should also warn is open question 1.
8. **The bearer file is checked too.** A missing bearer at the resolved location would fail on first RPC use anyway, but with a generic message. Checking it at load names both paths. It is one more metadata call.
9. **Current implementation values (not normative).** The refusal is a single-line error string beginning `consumer profile <absolute profile path>: relative <field> "<value>" now resolves against the profile's directory to …`; absolute paths are produced with `std::path::absolute`, which does not collapse `..`. The CLI prints it as `chiral: <error>` and exits with status 1 (`bin/chiral.rs:194`). The desktop returns it from `consumer_command("configure")` (`desktop.rs:74`, in `consumer_operation`, which the command calls) before the current consumer is replaced, and Settings shows it in an error callout (`Settings.svelte:24`).

## Code differences

1. **`Consumer::load` did not resolve relative profile paths** (requirements 1 to 4, book lines 449 and 470). It decoded the profile and called `Consumer::new(config)` directly, so `data_dir`, `network.rpc_bearer_file` and `dht.identity_file` named places in the process working directory. The same profile loaded from two directories used two wallets, two agreement stores, two policy watermarks and two nonce journals, and a consumer and a provider in one folder naming `"data"` shared a journal only when the consumer happened to run from that folder. Reproduced: `chiral wallet create` run from another directory created state there. Task 2.1. Fixed 2026-11-18 by task 2.1.

No other difference was found. `ProviderConfig::load`, `relay_server` and `chiral_rpc_gateway` already resolve their configuration paths against the configuration file.

## Observations outside this capability

- Task 3.5 moved the body of the desktop's `consumer_command` unchanged into `consumer_operation(&DesktopState, …)`, which the command calls, so that a test drives the real dispatch without a Tauri application (`tauri::State` has no public constructor). Behaviour is unchanged. Two source-inspection tests in `application_startup_boundaries_test.rs` read the operation dispatch from the body of `consumer_command`; they now read it from `consumer_operation` after asserting that `consumer_command` is exactly that one delegating call, so the enumerated desktop surface is unchanged.
- `relay_server.rs` and `chiral_rpc_gateway.rs` repeat the resolution inline because binaries cannot use the crate-private helper. The behaviour is identical; a shared public helper would be a refactor, not a fix.
- `docs/provider-qualification.md` line 173 says that "raw provider/relay configs" resolve relative paths against their own file. It is still correct, and now also true of consumer profiles; it was not edited.
- The desktop launched from a file manager usually has `/` as its working directory, so a relative `data_dir` previously pointed under `/`, where an unprivileged process normally cannot create a directory. Desktop users are therefore unlikely to have stranded state; CLI and SDK users are the affected group.

## Open questions for the whitepaper author

1. **Should a client warn when the old working-directory location also holds state?** When both locations hold this network's state, the spec uses the profile's location and leaves the other untouched without a message (decision 7). Proposed default (what the spec adopts): no warning, because the user has already acted deliberately and a warning on every load from that directory would be noise. Nonblocking: no task waits on the answer.
2. **Should line 449 name the relay and RPC-gateway configurations and the command-line exception?** Proposed wording: "Paths inside consumer, provider, relay and RPC-gateway configuration files are resolved relative to that file; paths given as command-line arguments follow the working directory." Nonblocking: the spec adopts this reading (decision 3).

## Risks

- A user who ran an older client from a directory other than the profile's now gets a refusal instead of their wallet until they set an absolute `data_dir` or move the directory. This is intended (book line 472), and the message names both remedies, but it is a visible behaviour change that release notes should mention.
- Decision 6 can refuse a profile whose working-directory location holds only another process's journal for this network. The absolute-path remedy resolves it without moving anything.
- Detection covers only state of the profile's own network. State of other networks at the old location is not this profile's state and is not examined.
- Detection sees only the current working directory. State that an older client left in some other working directory cannot be found without scanning, so a run from a third directory loads the profile's own location. The wallet-key comparison (decision 4) keeps such a run from hiding the old wallet when the user later runs from the old directory.
- Once the resolved location holds the scaffold of an earlier load, a working-directory location that holds this network's journal or policy watermark but no consumer wallet key is no longer refused. Without a wallet key that location holds no consumer funds, agreements or credentials; its watermark only protects against policy rollback and is replaced by the resolved location's own.
- All evidence is local and synthetic: temporary directories, a never-contacted loopback RPC and offline wallet commands. No live chain is involved, and none is needed for this rule.
