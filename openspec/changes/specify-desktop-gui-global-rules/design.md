## Decisions

1. **Scope.** This capability covers the Appendix A introduction, A.1.1–A.1.9 and A.6. A.1.10 is already the normative `desktop-window-lifecycle` capability. A.5 page details are specified only where an A.1 rule depends on them (for example the A.5.3 reveal and the A.5.1 and A.5.3 funding surfaces).
2. **Reference instead of restating.** Where another capability already states part of an A.1 rule, the requirement names that capability and requirement and adds nothing to it: the A.1.6 reorganization, registration-risk and libp2p items, the funding and cancellation parts of A.1.7, the A.1.1 local server bearer, and the A.7 scoping of A.1.3 and A.1.8.
3. **What counts as a network action.** Book line 810 disables "network actions" until a profile is loaded, and line 873 repeats it for every page. Requirement 4 counts every native operation that needs the loaded consumer profile, including reads of the profile's local account journal and diagnostics, because the native layer refuses all of them without a profile (`desktop.rs:74–77`) and they act on the selected network's state. Starting such an operation automatically when a page opens counts as starting a network action. The native refusal is a backstop; the GUI must still disable the controls.
4. **Lifetime of a revealed API key.** Line 808 allows the key into the webview only to be shown in a masked field, cleared on hide or account change; line 815 also clears displayed credentials on logout and profile change. Requirement 2 therefore clears the key on Hide, on a change of account or credential, on leaving the page, on logout and on a profile change. This matches the bearer rules of `desktop-local-api-server` and today's code (`Usage.svelte:24`, `75`, `247`, `262`, and unmounting on navigation). Switching between the Usage tabs is not leaving the page: the key stays in component state, undisplayed, until one of those events, and returns when the API keys tab is reopened. Neither the book nor the bearer rules name a section change, so this capability does not add one.
5. **Acceptance wording.** A.1.6 requires the user to see and actively accept every item. The book's own A.5.1 sample labels the checkbox with a short summary ("I accept this provider-specific non-refundable prepayment and residual reorg risk", line 887). Requirement 7 therefore does not require the label to list every item. It requires the complete disclosure on the same surface, before the funding control, with an acceptance control that is not pre-selected, is reset when a different offer, quote or account is selected, and gates funding. One control may also cover the items owned by the referenced capabilities.
6. **Every opening, including a free one.** A.1.6 says "before any opening or top-up". The current Marketplace uses one flow for paid and free offers, so the disclosure and acceptance apply to every opening. The fee rate and gas items are still stated when the amounts are zero.
7. **The fee rate is shown exactly.** The fee rate is integer basis points, not a money amount. Requirement 7 requires it to be shown exactly (50 basis points as 0.5%). The current `fee_bps / 100` expression is exact for integer basis points, because JavaScript prints the shortest decimal that round-trips the correctly rounded quotient.
8. **Money syntax.** The wei format and range come from `inference-wire-foundation`. The GUI's CFX parser also rejects leading zeros (`01`), which the native human syntax accepts. Refusing is not rounding, so this is not a difference from A.1.4.
9. **Roles for notifications.** A failure notification uses `role="alert"`; success and information notifications use `role="status"`. The only warning notification today reports a failed copy of the download URL (`UpdateGate.svelte:36`), so warnings that report a failed action are failures.
10. **Reduced motion means both preferences.** Line 816 says the reduced-motion preference is honored, and line 961 adds an in-app switch. Requirement 10 honors either. It covers script-driven motion as well as CSS motion, because the CSS rules (`app.css:89–94`) do not reach Web Animations or programmatic smooth scrolling.
11. **A failed profile load is not a profile change.** The native layer loads and validates the new profile before it replaces the session or cancels streams (`desktop.rs:66–73`), and Settings changes the session only on success (`Settings.svelte:13–19`). Requirement 9 states this so that a mistyped path does not cancel a running stream.
12. **Where errors appear.** Book line 873 puts each page's native errors in an error callout on that page. Shell actions are not on a page: A.2 (line 843) and `desktop-window-lifecycle` (*A close request never silently quits*; *Quitting is an explicit, confirmed action*) report a failed minimize or quit in an error notification, and the current logout does the same (`App.svelte:41`). Requirement 1 therefore requires a callout for page actions and a notification for shell actions, both carrying the full native text. Background polling that no page or user action starts (the hourly version-policy refresh, `versionStore.ts:49–68`) is outside this rule.
13. **Failures before a request ID.** Book line 913 distinguishes a stream error ("Failed — inspect request status before retrying") from a dispatch error ("Failed — inspect Usage before retrying"), and `desktop-local-chat` (*Network threads keep every consumer rule*) applies the same split to a request whose dispatch fails before a stream opens. A.5.3 (line 931) lists the local request keys, including ambiguous dispatches, in Usage. Requirement 8 therefore requires the request ID with a status action when one was received, and otherwise a pointer to Usage. It does not require a page to show a local request key that the native error does not name: a stream dispatch timeout today reports "stream dispatch timed out; inspect usage before retrying" without the key (`consumer.rs:2168`).
14. **Endpoints after a profile loads.** Requirement 4 requires every RPC, catalog, relay and provider inference endpoint to come from the loaded profile or a natively verified offer. The Provider page's operator endpoint is typed by the user, defaulting to the literal-loopback `http://127.0.0.1:9421` (book line 944), so it is an explicit choice, not an implicit selection.

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **The Usage top-up card omits four A.1.6 items** (requirement 7, book lines 813 and 929). `Usage.svelte:217` says "Non-refundable. Only provider `<wallet>` can serve this credit. Use a small balance; gas is extra. Chain reorganizations can freeze or reverse credit." It does not name the endpoint, does not say that the provider sees prompts in plaintext or that signed metadata does not prove model execution, and does not state the platform fee rate. The data the card receives cannot supply two of these: the webview `Account` type (`native.ts:21`) mirrors `AccountView` (`protocol.rs:567–586`), which has neither the agreed `fee_bps` nor the offer endpoint. The saved agreement holds both (the signed quote and the signed offer that `consumer.rs:2031` already reads). `AccountView` is also the decoding target of the provider's account response and refuses unknown fields (`protocol.rs:588–592`), so the fields cannot simply be added to it. The Marketplace funding panel (`Marketplace.svelte:175`) states all items. Task 2.1.
2. **Profile-dependent actions are enabled, and some start automatically, before a profile is loaded** (requirement 4, book lines 810 and 873). With no profile:
   - Usage runs `accounts` and `pending_accounts` when it opens (`Usage.svelte:82`), so the page shows the native refusal as an error together with "No accounts in this network's local journal" (`Usage.svelte:165`), a statement about a network that is not selected. Its Refresh button (`149`), *Resume journaled funding* and *Inspect wallet recovery history* (`301–302`, enabled once an ID is typed) and *Submit or resume cancellation* (`312`, enabled after its acceptance) are not disabled.
   - Playground runs `accounts` when it opens (`Playground.svelte:87`), and its Refresh accounts button (`116`) is enabled.
   - Diagnostics enables *Collect native diagnostics* whenever the native runtime exists (`Diagnostics.svelte:20`).
   The native layer refuses each of these (`desktop.rs:74–77`), so nothing reaches the network; the difference is in the GUI. The other pages already disable their actions (`Marketplace.svelte:90`, `Account.svelte:18`, `Network.svelte:22`, `Provider.svelte:55`, `Wallet.svelte:40`, `142`, `150`). Task 2.2.
3. **A new payment is offered while another journaled payment is unresolved** (A.1.7, book line 814; the rule is `inference-funding-settlement` *Funding ambiguity is disclosed and recovered on native surfaces*, "SHALL NOT prompt for or prepare a second payment while one is unresolved"). The Marketplace reads `pending_accounts` only after its own `fund` or `resume` (`Marketplace.svelte:22–28`, `50`, `55`), and its pending state is component state (`19`). After the page is left and reopened, or after a restart, an unresolved opening is not shown there, and *Request signed quote* (`216`) and *Register intent, fund, and open account* (`233`) are offered for a new agreement. Usage disables the top-up form only for the selected account's own pending top-up (`Usage.svelte:28`, `70`), so another account's form stays enabled while an operation is unresolved; only the header notice (`167`) mentions it. The native wallet journal refuses a new original while any record is unresolved ("wallet already has an unresolved transaction; reconcile, resume, or explicitly cancel its operation", `chain_client.rs:1590–1597`), so no second payment is prepared. The GUI still prompts for one, and the refused attempt leaves a misleading *Funding stage: unresolved* notice for the new quote. Task 2.3. Fixed 2026-11-18 by task 2.3.
4. **The feedback score input has no associated label** (requirement 10). In `Usage.svelte:324–328` one `<label>` wraps an `aria-hidden` range input followed by the number input. A label without `for` labels its first labelable descendant, the range input, so the number input has no label. A jsdom check with the same markup reports `labels.length` 1 for the range input and 0 for the number input. Task 2.4.
5. **Notification and status roles** (requirement 10).
   - `Toast.svelte:80` gives every notification `role="alert"`, including success and information notifications such as "Provider account opened" (`Marketplace.svelte:49`) and the logout notice (`App.svelte:40`).
   - These status messages have no `role="status"`: the "No network selected yet" banner that appears when logout ends the session (`App.svelte:96`; the preview banner at `92` has one); the Usage pending-funding notice (`Usage.svelte:167`) and *Funding unresolved* notice (`226`) that appear after a top-up attempt; and the Wallet copy confirmation, which only swaps the button's icon (`Wallet.svelte:86–88`).
   Task 2.5.
6. **Reduced motion is not honored for script-driven motion** (requirement 10). `Toast.svelte:77` slides each notification in and out with `transition:fly`. Svelte 5.49.1 runs transitions through `element.animate()` (`node_modules/svelte/src/internal/client/dom/elements/transitions.js:440`), which the CSS rules at `app.css:89–94` do not affect. `Marketplace.svelte:37` scrolls to the funding panel with `scrollIntoView({ behavior: 'smooth' })` regardless of either preference. Task 2.6.
7. **The stream-cancel helper does not explain the preview** (requirement 3). `command` and `stream` refuse outside the native runtime with an explanatory error (`native.ts:24`, `28`), but `cancelStream` (`native.ts:33–35`) calls `invoke` directly, which outside Tauri throws a `TypeError` while reading `window.__TAURI_INTERNALS__` (`@tauri-apps/api` 2.9.1, `core.js:201–203`). No current page can reach it in the preview, because a stream ID exists only after `stream` succeeded. Task 2.7.
8. **The webview references Google Fonts** (requirement 1, book line 804). `index.html:7–9`, copied unchanged into the built `dist/index.html`, has `<link rel="preconnect">` hints for `https://fonts.googleapis.com` and `https://fonts.gstatic.com` and a stylesheet link to `https://fonts.googleapis.com/css2?family=Roboto…`, while `tailwind.config.js:25` names Roboto first. The production CSP (`tauri.conf.json:24`: `style-src 'self' 'unsafe-inline'`, `font-src 'self'`) blocks the stylesheet and fonts, so Roboto never loads from there and the UI falls back to system fonts. Preconnect hints are not governed by CSP in every engine, so whether a platform webview opens a connection to Google's servers on each launch is unverified (task 4.1). Either way, the page asks for remote resources that the thin-view rule excludes. Task 2.8.
9. **Non-canonical wei is displayed as a number** (requirement 5, book line 811; the syntax is `inference-wire-foundation` *Exact monetary representation and CFX conversion*). `formatCfx` (`native.ts:39–44`) accepts any string of digits: `"00"` displays as `0`, `"01"` as `0.000000000000000001` and `"340282366920938463463374607431768211456"` (2^128) as a number. The requirement shows a non-canonical value as unavailable, never as zero. `native.test.ts` › `does not silently display invalid monetary data as zero` covers only a non-numeric string and `-1`. `Marketplace.svelte:60` applies the same `/^\d+$/` filter to prices. Task 2.9.
10. **A stream that fails before a request ID is labeled as a stream error** (requirement 8, book lines 913 and 931, design decision 13). `inference_stream` returns its stream ID at once and reports a failed dispatch as a later `error` event (`desktop.rs:249–254`, `284`), for example "stream dispatch timed out; inspect usage before retrying" (`consumer.rs:2168`) or "inference dispatch interrupted; inspect request `<key>` before creating another request" (`consumer.rs:2104`). `Playground.svelte:50` gives every `error` event the label "Failed — inspect request status before retrying". When no `started` event arrived, `requestId` is empty, so no request ID or *Reconcile* action is shown (`203–208`) and nothing points to Usage, where the local request keys are listed (`Usage.svelte:291`). The "Failed — inspect Usage before retrying" label is used only when `stream` or `infer` itself rejects (`77`). Task 2.10.
