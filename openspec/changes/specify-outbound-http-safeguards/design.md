## Authority and scope

`docs/chiral-book.md` is the authority and stays read-only. Its SHA-256 was `eda22ce01020e0f2c6d8cc51c8081b7d9d9113b5c611441cb769f225af7d3933` when this change was written. The requirements come from these lines:

- *HTTP origins and trust boundaries* (lines 262–279), all of it: remote provider and catalog origins and the development exception (264); origins versus `/v1` and `/api/offers` (266); `safe_http_client` (268); the public address predicate and its scope (270); administration, the private engine and TLS ingress (272–276).
- *Configuration and state*: line 462 (`catalog_url` is the relay origin, not `/api/offers`) and line 463 (`development` defaults to false and enables loopback-only HTTP development). Lines 458 and 460 only to separate the chain RPC, faucet, explorer and policy endpoints from this boundary (decision 2).
- *Shared signing-wallet directory*, line 474: signing, administration, engine and RPC credentials are separate protected files.
- *Listener and secret boundaries*, line 656 (reference topology; administration and engine private; an engine may be a literal private IP for a protected trusted network but never a public paid-service bypass; firewall exposure checked independently of ingress) and line 658 (admin requests use a separate protected bearer and are local-only).
- *Transport and identity*, line 288, only to note that filtering libp2p addresses is target-design work.
- `CLAUDE.md`: "Public providers require HTTPS and public reachability … Resolve and pin untrusted offer endpoints; reject private/metadata addresses, redirects, and proxy bypasses"; "Operator routes require their protected bearer and reject browser `Origin` requests. No signing-key, engine-management, or tokenization route belongs on the public listener"; "llama.cpp runs privately, with a protected API-key file and no wallet key."

Where the code differs, the requirement follows the whitepaper and an unchecked task records the code change. Requirements are never weakened to match the code. Values that the book does not state are recorded under decision 10 as current implementation values, not as normative constants.

Out of scope, each owned elsewhere or deliberately different:

- **The chain RPC endpoint.** Line 458 gives `network.rpc_url` its own rule: "HTTPS remotely, literal-loopback HTTP only for local operation". `network::validate_endpoint` (network.rs:110–131) implements exactly that: it refuses credentials, queries and fragments, and allows HTTP only for a literal loopback IP, but it allows any HTTPS host, port and path, because an operator-qualified RPC node may sit on a private network or behind a gateway path such as `/api/chain/rpc`. `rpc_client` (rpc_client.rs:11–19) refuses redirects but is not DNS-pinned and honours environment proxies. Line 264 names only provider and catalog origins, so these are not code differences. Chain RPC transport (including redirect refusal) belongs to `inference-funding-settlement` (*Chain RPC transport is bounded*), and the standalone gateway's inbound side to `chain-rpc-gateway`. The proxy behaviour is open question 1.
- **Faucet and explorer URLs.** Line 460 calls them optional operator-supplied endpoints. They are validated at profile load by `network::validate_endpoint` (network.rs:66–72) and only displayed (`network_profile`, consumer.rs:655–659; `src/pages/Wallet.svelte:43–44`). No native code requests them, so no outbound client applies.
- **The version-policy source.** The pending `client-version-policy` (`specify-version-policy`, *Policies come only from configured sources*) owns the `policy_url` rule: it follows "the profile's endpoint rules: HTTPS for a remote host, literal-loopback HTTP only for explicit development, and no credentials, query or fragment" (book line 460). The code also fetches it through the pinned client of its origin (consumer.rs:775–788), which is stricter than that rule. This capability adds nothing for the policy source. Open question 2.
- **Credential storage and secret files** (comparison item 12), the public API and its admission (item 13), and daemon lifecycle (item 14). This capability names the administration token and engine key only as separate protected credentials.
- **libp2p addresses and the target-design transports.** Line 270 says this boundary "is not a claim that all libp2p addresses obey the HTTP-origin policy". The local listeners of the target design (`specify-desktop-local-api-server`, `specify-cli-loopback-gateway`) are loopback servers with their own specifications.

## Decisions

1. **One capability for the current runtime.** `outbound-http-safeguards` specifies what runs today: providers serve inference only at an advertised HTTPS origin. When `specify-p2p-provider-transport` is implemented, it has to modify *TLS ingress fronts only the public listener, and public HTTPS reachability remains required* (task 4.3).
2. **Reference the origin spelling rules, do not restate them.** `validate_endpoint` is the single validator for offer admission, the provider's `public_endpoint` and the pinned client (`specify-inference-commercial-terms` design, "Advertised-origin implementation"). Requirement 1 therefore points at *Offer freshness and advertised origin* for the rule and adds its scope: the catalog, the provider's own endpoint, and every request, checked before resolution.
3. **The `localhost` exception requires loopback answers.** Line 264 allows HTTP and non-443 ports only for literal loopback or exact `localhost`, and "does not authorize … remote cleartext HTTP"; line 268 rejects "any disallowed result". A literal loopback origin resolves to itself, but `localhost` is resolved by the system resolver, which a hosts file, a resolver that forwards `localhost` queries upstream, or search-domain expansion can make answer with a non-loopback address. A public answer is "allowed" by the public predicate but is exactly the remote traffic the exception excludes, so requirement 2 refuses any non-loopback answer to a `localhost` origin (code difference 1).
4. **When validation happens.** Requirement 1 requires validation before any request, not at profile load. `Consumer::new` checks `catalog_url` only for syntax (consumer.rs:633–635), and the full rule runs in `transport` before each catalog request, so a non-conforming catalog loads and is refused at its first use without a connection. Line 462 says the catalog URL is an origin, not `/api/offers`, but not when it is checked, so requirement 3 requires the path, query, fragment and credential refusal only before any catalog request. The syntax check at load (consumer.rs:633–635) refuses them earlier, which conforms.
5. **The SDK `base_url` is an outbound boundary.** An SDK uses its own HTTP stack, which applies none of requirement 4: it resolves without the answer rule, may honour proxies and may follow redirects with the bearer. Credential export is therefore the last native point at which the origin rule can apply (line 266: "adds `/v1` after validating the provider origin"). Export validates; loading does not. `load_account` must keep accepting a saved account whose origin no longer validates, because historical funding recovery must stay reachable (`CLAUDE.md`), and the commercial-terms historical-authenticity tests require that a refusal "preserves the invalid bytes for recovery rather than silently repairing/deleting them". Refusing the export neither rotates nor revokes the credential. Every native operation on such an account (inference, request status, receipts) already fails in `transport`, so the export refusal makes the SDK path consistent with them (code difference 2).
6. **A redirect is the sending origin's answer.** With redirects disabled, a 3xx reaches the caller as a non-success response, and each calling path classifies it as that source's failure (provider, catalog or policy source). Requirement 4 states the security property only: the target is never contacted and receives nothing.
7. **The predicate's ranges are normative.** Line 270 makes `offer_registry::public_ip` the exact predicate, so requirement 5 lists its ranges as implemented (offer_registry.rs:124–152). Changing the function, including adding a range, needs a spec change. The requirement keeps the book's warning that it is not a classification of every future IANA allocation.
8. **Administration.** The book states a distinct nonzero loopback-only listener, a protected bearer, no `/admin/*` on the public router, and that an account bearer or wallet challenge is not an admin token (line 274), and that admin requests are local-only (line 658); `CLAUDE.md` adds the `Origin` refusal. For the native client, "local-only" means a loopback address on the local host and no environment proxy, since a proxy would carry the bearer off the host. The book gives no refusal status code, and it does not say that the client must require a literal IP or check the endpoint before reading the token. The code does all three (401, `Consumer::provider_admin` refusing `localhost` and any non-literal host before `private_read`), and decision 10 records them as implementation values. The native client also refuses redirects (consumer.rs:2521–2523), but the book does not require it: a redirect could only come from whatever listens on the loopback port, which already receives the bearer. The 32-character minimum and the constant-time comparison are implementation values (decision 10); the length rule belongs to credential storage (comparison item 12).
9. **Engine origin.** An IPv4-mapped IPv6 literal such as `::ffff:10.0.0.1` is refused: line 275 admits only IPv6 loopback or unique-local, and the code refuses it (provider_config.rs:306–311). The book admits exact `localhost` for the engine and states DNS pinning only for `safe_http_client`; requirement 7 adds no pinning for the engine client (see Observations). A redirect from the engine is an engine failure (`read_json` refuses every non-success status, inference_backend.rs:902–907; the streaming dispatch and `ready` refuse it too, 576 and 664). The book requires the engine origin rule, not where it is checked. Requirement 7 therefore requires that configuration validation refuses a non-conforming origin and that no engine request reaches it. The second check in `Backend::new` (inference_backend.rs:525–534), which also covers paths that build a backend without `ProviderConfig::validate`, is how the code meets the second statement. It is not a separate normative check.
10. **Current implementation values (not normative constants).** Each may change without a spec change if the requirements still hold:
    - `validate_endpoint` refuses an endpoint string longer than 2,048 bytes (offer_registry.rs:155–157).
    - Consumer request deadlines: catalog page, reputation read and policy fetch 30 seconds (consumer.rs:965, 699 and 784), inspection 10 seconds per probe (`observe_provider`), feedback and administration 120 seconds (2481 and 2529). Consumer responses are bounded at 8 MiB (`bounded_body`, 296–309).
    - Private engine client: 5-second connect timeout, the model's `request_timeout_secs` as request timeout, an idle pool of `max_concurrency` (inference_backend.rs:544–551). Managed health probe: 2 seconds per attempt (engine_runtime.rs:322).
    - Administration token: at least 32 characters (app.rs:126–129; `chiral_daemon --check`, chiral_daemon.rs:96–99), compared in constant time (app.rs:557–559); a refused administration request gets HTTP 401 (`ApiError::unauthorized`, app.rs:560); administration responses carry `Cache-Control: no-store` (562–566). The native client requires a literal loopback IP (`localhost` is refused), checks it before reading the token file, and refuses redirects (consumer.rs:2493–2527).
    - Consumer checks earlier than the requirements demand: `Consumer::new` refuses a `catalog_url` with credentials, path, query or fragment at profile load (consumer.rs:633–635); `fund` builds the pinned client of the provider origin before it saves the account or prepares any payment (consumer.rs:1169–1170); `ProviderConfig::validate` runs at `ProviderConfig::load`, before the daemon binds (chiral_daemon.rs:71, 115–116).
    - Private engine: `Backend::new` repeats the engine-origin check (inference_backend.rs:525–534).
    - Reference deployment: public `127.0.0.1:9419`, administration `127.0.0.1:9421`, engine `http://127.0.0.1:8000` (provision-provider.py:256–257; provider-preflight.py:141). The reference Caddyfile forwards the provider domain's `/v1/*`, `/healthz`, `/readyz` and `/api/version-policy` to `127.0.0.1:9419`, answers anything else 404, and turns the Caddy admin API off (provision-provider.py:279). Preflight accepts 401, 403, 404 or 405 for the private routes it probes (provider-preflight.py:170–172) and treats ports 8000, 9419, 9421, 8547 and 8081 as private (39).
    - `relay_server` also refuses a non-loopback bind in development (relay_server.rs:172–174). The relay is not a provider; its lifecycle is comparison item 14.

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **A development `localhost` origin accepts non-loopback answers** (requirement 2; book lines 264 and 268). `safe_http_client` refuses an answer only when it is not public and not the loopback answer that the exception permits: `!public_ip(a.ip()) && !(development && loopback_origin && a.ip().is_loopback())` (offer_registry.rs:216–217). A public answer to `localhost` therefore passes and is pinned with the loopback answers (226). Example: in development mode with origin `http://localhost:9419`, a resolver that answers `127.0.0.1` and `93.184.216.34` yields a client pinned to both. When nothing listens on loopback port 9419, the connector moves on to the public address and sends the request there in cleartext: an account bearer, an owner-signed control request or a prompt. Line 264 says the exception "does not authorize … remote cleartext HTTP". A literal loopback origin is not affected, because its only answer is itself. A private non-loopback answer (`10.0.0.5`) is already refused. Severity low: development mode only, and only with a resolver that answers `localhost` with a public address. Verified by reading; no test injects resolver answers. Task 2.1.
2. **Credential export derives the SDK `base_url` without the origin validator** (requirement 3; book line 266). `credential_export` builds `base_url` with `endpoint_url(&saved.offer.payload.endpoint, &["v1"], development)` (consumer.rs:2222–2226). `endpoint_url` checks only the scheme (HTTPS, or HTTP for loopback or `localhost` in development), credentials, query, fragment and path (252–290); it does not apply the port, public-address, `localhost`-alias or single-label rules of `validate_endpoint`. `load_account` checks the saved offer only through the same `endpoint_url` (`verify_quote`, 1042). Funding validates the origin fully before saving (1170), so the gap needs a saved origin that no longer validates under the current mode: an account saved by an earlier release before the validator was tightened (for example `https://intranet./` before `specify-inference-commercial-terms` task 2.7, or `https://localhost./` before task 2.1.4), or an account saved in development mode with `https://localhost:8443` or `https://127.0.0.1:9419` and exported after development is switched off. In each case export returns the API secret with `base_url` `https://intranet./v1` or `https://localhost:8443/v1`, while every native request for the same account fails in `transport`. The SDK then sends the bearer to that host through its own HTTP stack, without the answer rule, pinning, or proxy and redirect refusal. Severity low: it needs such a saved account and an explicit export. Verified by reading. Task 2.2.

No other difference from the whitepaper was found. The origin rule, the other development cases, the 33-answer inspection and 32-answer bound, the 5-second resolution deadline, pinning, proxy and redirect refusal, the 10-second connect timeout, per-origin clients, normal TLS verification, the public address predicate, the administration listener and bearer, the engine origin rule and engine clients, and the reference ingress and preflight checks match the requirements.

## Observations outside this capability

- `rpc_client` honours environment proxy variables (rpc_client.rs:11–19 has no `no_proxy`). The pinned reqwest 0.11 has no built-in loopback bypass, so with a literal-loopback `http://` RPC URL and `HTTP_PROXY` set, every JSON-RPC request, including the `Authorization` bearer from `rpc_bearer_file`, goes to the proxy in cleartext unless `NO_PROXY` excludes the address. With an HTTPS RPC URL the proxy sees only the `CONNECT` host. The chain RPC is a separate boundary (Authority and scope). Open question 1.
- `scripts/provider-admin.py` disables proxies but follows redirects with urllib's default handler (provider-admin.py:29), which copies the `Authorization` header to the redirect target (CPython `HTTPRedirectHandler.redirect_request`). It only contacts `http://127.0.0.1:<port>`, and whatever listens there already receives the bearer, so following a redirect adds no exposure beyond that listener. Line 658 requires local-only use and no bearer in argv, which the helper meets. Refusing redirects, as `qualify-provider.OPENER` does, would be cheap hardening; it is not required.
- `Consumer::new` checks `catalog_url` only for syntax (decision 4). A catalog on port 8443 or a private address loads and is refused with the origin error at its first use, without a connection.
- The private engine client resolves `localhost` through the system resolver at each connection, without pinning (inference_backend.rs:544–553). The book accepts exact `localhost` for the engine and does not require pinning there (decision 9). An operator who wants no resolver involvement can use `127.0.0.1` or `::1`; the managed engine already requires a literal loopback IP.
- `scripts/provision-runtime.py` downloads the pinned llama.cpp archive with `urllib.request.urlopen`, which honours environment proxies and follows redirects, refusing only a final non-HTTPS URL (provision-runtime.py:308–309). It sends no credential, and `install_archive` verifies the archive's pinned SHA-256 before use. It is operator provisioning of an official release asset, not a provider or catalog origin, so it is outside this capability. The qualification runner and preflight use `qualify-provider.OPENER` (no proxies, no redirects; qualify-provider.py:58–62).
- `reqwest` clients across `src-tauri/src`: `safe_http_client` (offer_registry.rs:222–228); the private engine client (inference_backend.rs:544–552) and managed health probe (engine_runtime.rs:322); the native administration client (consumer.rs:2521–2525); and the chain RPC client (rpc_client.rs:11–19). No other production client exists. The `reqwest::Client::new()` calls in billing_store_tests.rs and chain_client_tests.rs are test callers. The desktop frontend makes no `fetch`, so every provider and catalog request goes through `transport`.
- The DHT uses `public_ip` to decide which of its own listen addresses to announce (dht.rs:634–640). Line 270 says this boundary does not govern libp2p addresses; libp2p filtering belongs to `specify-p2p-provider-transport`.
- Book line 278 cites `provider_config.rs:91–103,143–160,190–211`, `app.rs:440–470,540–562` and `inference_backend.rs:527–549`. The code has moved slightly since; this design cites current lines. No book change is proposed for that.

## Open questions for the whitepaper author

1. **Should the chain RPC client ignore environment proxies?** Line 268 disables environment proxies for provider and catalog origins and line 275 for the private engine, but line 458 states only the scheme rule for `rpc_url`. Today `rpc_client` honours them, so a literal-loopback HTTP RPC URL sends its bearer to an `HTTP_PROXY` in cleartext. Options: (a) keep honouring proxies, since an operator may need one to reach a remote HTTPS node; (b) ignore environment proxies for all chain RPC, as for provider and catalog origins; (c) ignore them at least for literal-loopback HTTP RPC. Proposed default (what this change does): the capability does not cover the chain RPC client and leaves it unchanged until answered; if (b) or (c) is chosen, it belongs to `inference-funding-settlement` *Chain RPC transport is bounded*. Nonblocking: no requirement or task waits on the answer.
2. **Does the provider/catalog origin rule also govern the version-policy source?** Line 460 calls `policy_url` an optional operator-supplied endpoint, and line 264 names only provider and catalog origins. The code fetches the policy through the pinned client of its origin (consumer.rs:775–788), so a policy source must be public HTTPS on port 443 (or loopback in development), while profile load accepts any HTTPS URL with a path (network.rs:66–72). The source rule belongs to `client-version-policy` (`specify-version-policy`, *Policies come only from configured sources*), which states only the profile's endpoint rules. Options: (a) make the provider/catalog origin rule and the pinned client normative for the policy source, as a modification of that requirement (not of this capability); (b) leave it as current behaviour without a requirement. Proposed default (what the spec adopts): (b). Nonblocking.

## Risks

- Task 2.1 refuses a development setup whose resolver answers `localhost` with a non-loopback address. The refusal must say that a development `localhost` origin must resolve only to loopback, and suggest `127.0.0.1` or `::1`.
- Task 2.2 makes credential export fail for a saved account whose origin no longer validates. The account, its balance, its signed terms and its credentials stay stored and recoverable; every native operation on that account already fails today. The error must name the origin rule, not the secret.
- The tests of row 4 need DNS answers that a test controls. Any seam (for example a pure function that checks an answer set, or a resolver parameter) must not create a production path that skips validation. Environment-variable tests are process-wide; run them in a separate process (an integration-test binary that sets the variables before building the client) so they cannot race other tests.
- All executable evidence above is pure or loopback. No DNS, proxy, TLS ingress or Windows run is involved. The migration plan's private-run probe (line 480) predates this specification and "is not a complete SSRF, firewall or public-ingress audit". Task 4.1 tracks current deployment evidence; it never counts as public-release approval.
- Requirements reference capabilities from pending changes (`inference-commercial-terms`, `managed-engine-runtime`) and name `specify-p2p-provider-transport` by change name. Task 4.3 sets the archive order.
- The implementation values in decision 10 are not normative. Changing one needs no spec change, but this design should be updated to match.
