## Scope and authority

The read-only book's authorization matrix, funding order, settlement/recovery risks and durable accounting sections require payer authority, original top-up evidence, the existing immutable agreement, healthy-safe verification and exact once-only credit. The approved non-reserving decision forbids new quote/admission gates on this recovery. Pending owner-control/opening changes and the wire foundation supply related contracts but do not define `TopupRequest`'s complete schema.

This step supplies that missing specification before implementation. It does not redefine accounting-response schemas, introduce another paid-admission handshake, or complete the parent changes' full chain/expiry/resource qualification. No author policy answer is required; exact request syntax and ordering are implementation-level decisions consistent with the book.

## Decisions

1. **One required string in one object.** Preserve the object emitted by the native writer and reject positional projections. Missing/null is not optional payment: top-up is never free opening. Keep empty strings as strings for the existing business/payment gates, rather than adding normalization or treating them as absence. Unknown and duplicate members remain errors.
2. **Preserve owner-first ordering.** The actual top-up route validates the account identifier and invokes `authorize_owner` before matching/decoding its operation body. That authenticates and consumes the exact proof, then resolves account ownership. Keep missing/wrong-owner refusals before decoding; correctly authenticated malformed bodies consume their proof. Do not copy opening's different parse-before-owner ordering or move all control parsing in an unrelated refactor.
3. **Bind the path and raw bytes, not a reconstructed operation.** The account is the literal route ID. The body supplies only signed payment evidence, not the selected amount or another account. Native serialization is unchanged; the same bytes are hashed, signed and sent. Route syntax accepts either case of hexadecimal digits, while lookup and proof binding retain the literal spelling; that does not create aliases for canonical stored account IDs.
4. **Keep verification and credit separate.** Active-paid status precedes chain verification and is checked again transactionally. The chain verifier checks signed payment identity/terms and canonical safe evidence; the ledger requires positive value, uses the original payee/fees and atomically deduplicates by transaction hash. Top-ups need not equal the opening amount. Do not introduce an opening-style registered-raw-string equality rule where no top-up acknowledgement exists: native recovery preserves its exact journal original, and provider credit deduplicates the verified transaction identity.
5. **Recovery is not fresh funding admission.** Closed serving/new-funding readiness, withdrawn offers and full quote/opening resources do not erase the accepted agreement or prevent otherwise-valid top-up settlement. They also do not excuse a frozen account or unavailable safe evidence. A repeated accepted top-up still traverses verification; unlike existing-account opening replay, it is not an offline ledger-only fast path. Unavailable evidence is not a reorg.
6. **Retain useful existing acceptance.** Extend the shared production-router fixture and direct object visitor rather than adding another server, payment simulator or decoder convention. Account/credential/fee snapshots distinguish forbidden mutations from legitimately consumed challenges and bounded verification-attempt records. Synthetic chain and restored account/storage prerequisites must remain explicitly disclosed.

## Typed decoder observation — 2026-11-15

A temporary Rust example used the actual `TopupRequest` type with `serde_json::from_str`, printing accepted values through its real serializer. It accepted `{"raw_transaction":"probe"}`, preserved `{"raw_transaction":""}`, and accepted `["probe"]`, serializing the latter as the object form. Missing, null, numeric, unknown and duplicate payment members, and a scalar root string, were rejected. The example was removed before project checks.

This is executable schema evidence only: `probe` is deliberately not a signed transaction, no owner proof was sent, and no payment or ledger mutation occurred. Positional decoding is a shape gap to fix under this new requirement, not evidence of an authorization bypass, successful top-up or signature forgery.

## Object-only implementation and authority acceptance — 2026-11-15

`TopupRequest` now uses the existing direct object visitor and a local strict field decoder. The required `String` is moved into the unchanged public field; serialization and native callers are unchanged. No intermediate `Value`, nullable-payment alias, compatibility shim or storage conversion is added. The route still validates the identifier, authenticates/consumes the exact owner proof and resolves account ownership before decoding the top-up body.

`topup_request_schema_refuses_invalid_shapes_after_consuming_owner_authority` covers sixteen malformed/root/member cases for both free and existing paid accounts, including the previously observed complete positional projection. Each request carries genuine authority bound to its exact bytes. Full fourteen-table snapshots must differ only by removal of that request's nonce; an unrelated pending read proof remains usable. Consumed-proof replay fails, existing credentials remain valid, and the observed RPC/engine endpoint receives no request.

The real `TopupRequest` serializer supplies each object control. Free accounts reach their eligibility refusal without RPC. Matching signed paid top-ups reach an intentionally unavailable loopback RPC and retain only the original unavailable funding attempt, without credit, fee or credential mutation. This proves decoding and verification entry, not safe credit; paid opening credit remains a disclosed post-verification fixture prerequisite. Existing safe-credit and native top-up regressions remain separate controls.

`topup_authority_precedes_schema_and_binds_exact_body_and_target` covers missing/bearer authority on malformed bodies, wrong-owner and absent-account precedence, and invalid route syntax before proof consumption. Both directions of compact/whitespace-equivalent JSON substitution, another same-owner account's path and an added query must fail binding with the complete ledger/proof and RPC count unchanged. The exact original compact or spaced object remains usable, reaches the proper eligibility/verification boundary, then cannot reuse its consumed proof. No new authentication or financial policy is introduced; remaining eligibility/resource correspondence stays in tasks 2.3–2.4.
