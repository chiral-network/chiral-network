## Relationship to existing and pending specifications

It references the following capabilities and does not restate them.

## Decisions

1. **One capability, `inference-fee-remittance`.** The fee formula, credit, balance identity and orphan accounting stay with `inference-funding-settlement` and `inference-account-topup-request`, which already own them. This capability starts where a credited fee becomes an obligation.
2. **Both thresholds are inclusive.** Line 528 says "at least `10^15` wei" and "the oldest obligation reaching 86,400 seconds". A sum of exactly 10^15 wei qualifies, and an obligation exactly 86,400 seconds old qualifies. The code skips a group only when `amount < FEE_MIN_REMIT_WEI && now - oldest < FEE_MAX_AGE_SECS` (billing_store.rs:1483), which matches.
3. **Aggregation is per platform wallet, over every pending obligation of that wallet.** A transfer has one recipient, so a batch can pay only one platform wallet, and "at least 10^15 wei" is read as the amount owed to that wallet. Obligations normally share one wallet. Keeping wallets apart means a configuration change never mixes recipients. When either condition holds, every pending obligation of that wallet is sealed, so the obligations left pending are never older than the ones remitted. The code applies the thresholds per wallet but only to the 1,000 oldest pending obligations across all wallets (code difference 3). `desktop-share-online` already describes the trigger per wallet ("when a platform wallet's pending obligations reach 10^15 wei").
4. **The book's four state names are the reported states; stored names are implementation values.** The ledger stores obligation statuses `pending`, `batched`, `remitted`, `cancelled`, `orphaned_batched` and `orphaned_remitted`, and batch statuses `prepared`, `submitted`, `accepted` and `orphaned`. The reported state of an ordinary obligation is:

   | Stored obligation status | Batch status | Reported state |
   |---|---|---|
   | `pending` | none | pending |
   | `batched` | `prepared` | batched |
   | `batched` | `submitted` or `orphaned` | submitted |
   | `remitted` | `accepted` | confirmed |

   `cancelled` obligations are reported as cancelled. `orphaned_batched` and `orphaned_remitted` obligations are reported as orphaned, with the same mapping for their batch state. A batch whose confirmed remittance was proven orphaned (`orphaned`) still has its signed bytes, so its obligations are submitted, not batched. The current fee view does not apply this mapping (code difference 1).
5. **"Confirmed" means the funding settlement policy.** The book defines one chain-evidence policy, `canonical-successful-receipt-at-espace-safe-v1` (line 514), and says that safe acceptance is "an application risk policy, **not irreversible finality**". It does not define "confirmed" for remittances. The spec applies the same policy, with the same two consistent observations, and checks the remittance's own sender, recipient, value, calldata and network. The code verifies remittances through the same `ChainClient::verify_payment` path as funding (contracts.rs:744–767). Author question 1 asks the author to confirm this reading.
6. **A reorganized remittance is recovered by its original bytes only.** A remittance that monitoring no longer confirms returns to submitted, and only its original signed bytes are broadcast again. This mirrors the funding rules: re-inclusion refreshes evidence without duplicate credit, there is no automatic fee bump or replacement (`CLAUDE.md`), and a displaced payment is reconciled without an automatic replacement transfer (line 518). Because the remittance's nonce is owned by its original, a second transfer for the same batch cannot be signed.
7. **A failed remittance is reported, never replaced automatically.** The book does not say how a remittance is resolved when its execution failed canonically, for example because the platform wallet is a contract that rejects the value, or when its nonce was consumed without its receipt. The spec requires only what follows from the book and `CLAUDE.md`: its obligations stay unconfirmed in their batch, nothing is signed automatically, and every pass reports the failure. Author question 2 asks for the recovery action.
8. **Remittance continues while the provider drains.** Line 631 says that draining "is not a refund or deletion of agreements", and line 737 says that stopping sharing "does not erase existing balances or obligations". The maintenance loop runs regardless of drain (app.rs:418–431), and `desktop-share-online` decision 28 depends on that.
9. **An explicit `fees/remit` leaves nothing pending.** It is the operator's way to remit below the thresholds (line 528). If it sealed only part of the pending obligations, the operator would see a successful remittance while older-than-intended debt stayed pending. Per-call work may be bounded only per batch, not per obligation. The code used to seal at most 1,000 obligations per call (code difference 3, fixed by task 2.3).
10. **The fee view lists actual remittances.** Line 528 says obligations are "separately tracked", line 677 tells operators to "reconcile pending chain submissions and fee batches before resuming", and `CLAUDE.md` says to "track obligations and actual remittances". An operator cannot reconcile batches that no route shows. The current view has only totals (code difference 2).
11. **Fee failures never gate consumers or new funding.** Line 630 lists what gates new credit and admission: chain or RPC unavailability, drain, managed-child failure and performance withdrawal. Remittance is not on that list. Line 33 treats a provider that fails to remit as a disclosed risk, not a protocol gate. The fee is fixed when funding is accepted (requirement 1), so a remittance outcome cannot change what a consumer owes or holds. The code keeps `fee_error` apart from `funding_error`, and only `funding_error` closes `funding_ready` (contracts.rs:650–651; app.rs:322 and 342).
12. **Current implementation values (not normative constants).** Each may change without a spec change if the requirements still hold:
    - `FEE_MIN_REMIT_WEI = 1_000_000_000_000_000` and `FEE_MAX_AGE_SECS = 86_400` (billing_store.rs:17–18). They are compiled constants; the book calls them the "default", and no configuration overrides them.
    - Maintenance runs every 30 seconds (app.rs:421) through `refresh` → `contracts::reconcile` → `reconcile_fees` → `remit_inner` with `force = false` (app.rs:315, contracts.rs:651 and 692).
    - Sealing reads at most 1,000 pending obligations per call (billing_store.rs:1465). Code difference 3 changed this (task 2.3): every pending obligation of each wallet is totalled, and a qualifying wallet is sealed completely in 1,000-row chunks within one transaction.
    - At most 100 unconfirmed batches are submitted or verified per pass (billing_store.rs:1489). Confirmed batches are rechecked 100 per pass, on page `(now / 30) mod ceil(count / 100)` (billing_store.rs:1500–1516). Code difference 4 changed how that page is chosen (task 2.4): batches are now returned least-recently checked first, from a `fee-batch-checked:<id>` time in the ledger's `metadata` table that advances after every recheck outcome.
    - A failed `fees/remit` answers HTTP 500 `internal_error` with the fixed message "The provider could not complete this operation" (`ApiError::internal`, error.rs:34–40). The specific fixed category is kept as `maintenance.fee_error` in `GET /admin/status` (app.rs:624–629).
    - A batch identifier is a random 32-byte value. Its calldata is `CHRL-FEE1\0` followed by the 32 identifier bytes, 42 bytes in all (billing_store.rs:113–124). The journal operation identifier is `fee:<batch id>` (contracts.rs:718).
    - A remittance is a legacy EIP-155 transaction at the node's gas price with the node's exact gas estimate (`ChainClient::payment_once`). The balance check covers value plus gas before signing.
    - When adding an obligation would overflow `u128`, a new batch is started for the same wallet (billing_store.rs:1471–1476).
    - An unconfirmed remittance is rebroadcast with identical bytes on every pass until confirmed (`payment_once` broadcasts an existing operation whose status is not `accepted`).
    - Fee failures use the fixed categories of `contracts::chain_failure` (contracts.rs:591–602), prefixed `Fee submission:`, `Fee verification:` or `Fee evidence recheck:`.
    - The fee view's JSON field names: `amounts_wei` (keys `pending`, `batched`, `submitted`, `confirmed` since task 2.1), `cancelled_wei`, `orphaned_amounts_wei` (`batched`, `submitted`, `confirmed`), `batches` (the newest 100: `id`, `platform_wallet`, `amount_wei`, `state`, `tx_hash`, `inclusion_block_hash`, `inclusion_block_number`, `created_at`; since task 2.2), `minimum_remittance_wei`, `maximum_age_secs`, `aggregation`, `collection` and `platform_receipt` (since task 2.2).

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **The fee view does not report submitted obligations and calls confirmed ones `remitted`** (requirements 3 and 11, book line 528). `BillingStore::fee_summary` totals obligations by stored status only (billing_store.rs:1601–1625). The stored status changes only when an obligation is sealed (`batched`, 1486) and when its batch is confirmed (`remitted`, 1556). Recording the signed transaction updates only the batch record (contracts.rs:726–733). A sealed obligation whose remittance is broadcast and waiting for `safe` is therefore reported as `batched`, the same as one whose batch was never signed. Confirmed obligations are reported as `remitted`, and orphaned ones only as `orphaned_batched` or `orphaned_remitted`. Task 2.1. Fixed 2026-11-18 by task 2.1.
2. **The fee view lists no remittance transactions and omits the receipt disclaimer** (requirements 11 and 12, book lines 528 and 677, `CLAUDE.md`). `GET /admin/fees` and `POST /admin/fees/remit` return only `fee_summary` (app.rs:600–602 and 624–629). `BillingStore::fee_batches` (billing_store.rs:1492–1499) has no caller outside tests. No administration route shows a batch's identifier, platform wallet, amount, state, transaction hash or inclusion evidence. The view states `"collection":"provider-remitted-not-trustless"` but not that a recorded obligation is not proof that the platform received the fee. Task 2.2. Fixed 2026-11-18 by task 2.2.
3. **Aggregation considers only the 1,000 oldest pending obligations per pass** (requirements 4 and 6, book line 528). `prepare_fee_batches` reads `status='pending' AND batch IS NULL ORDER BY created,tx_hash LIMIT 1000` across every platform wallet (billing_store.rs:1465) and applies the thresholds to that subset only (1483). Three consequences follow:
   - The amount trigger can be missed. With 1,200 pending obligations of 900,000,000,000 wei to one wallet, all younger than 86,400 seconds, the wallet owes 1,080,000,000,000,000 wei, but the 1,000 oldest sum to 900,000,000,000,000 wei, so nothing is sealed until the oldest reaches 86,400 seconds.
   - An explicit `fees/remit` (`force = true`) seals only those 1,000 obligations and leaves the rest pending.
   - When a wallet qualifies, its pending obligations beyond the first 1,000 stay pending.

   Task 2.3. Fixed 2026-11-17 by task 2.3.
4. **Monitoring can skip some confirmed remittances indefinitely** (requirement 9, book lines 514 and 528; found in review). `BillingStore::fee_batches_to_recheck` (billing_store.rs:1500–1516) returns the accepted batches at `OFFSET ((now / 30) mod ceil(count / 100)) * 100`, `LIMIT 100`. The page depends only on the wall-clock time of the pass, not on when each batch was last checked. Maintenance ticks every 30 seconds with `MissedTickBehavior::Skip` (app.rs:421–422). When a pass takes between 30 and 60 seconds, the next one starts 60 seconds later, so `now / 30` advances by 2 each pass. Example: with 150 accepted batches there are 2 pages, every pass reads page 0, and maintenance never rechecks batches 101–150. A reorganization of their remittances is then never detected. More than 100 accepted batches is expected after about 100 days under the daily age trigger. Rechecking 100 batches is itself slow: each recheck makes two `observe_execution` calls, each with `eth_chainId`, `eth_syncing`, the `safe` and `latest` blocks, the receipt and the canonical block (chain_client.rs:561–575, 608–616 and 808–830). That is about 1,200 RPC calls per pass, so passes longer than 30 seconds are plausible. Funding monitoring instead reads the oldest-checked payments first (`funding_to_recheck`, billing_store.rs:1317–1324). Task 2.4. Fixed 2026-11-17 by task 2.4.

No other difference from the whitepaper was found. The fee arithmetic, the obligation recipient, the inclusive thresholds, batch immutability, journaled one-transaction remittance, provider-paid gas, the confirmation policy, the reorganization transitions, restart recovery and the administration boundaries match the requirements.

## Observations outside this capability

- A ledger fault while rechecking a confirmed batch, either an `update_fee_batch` refusal or an accepted batch without evidence, returns from `reconcile_fees` before `remit_inner` runs (contracts.rs:663–690). That pass then seals and submits nothing; the failure is reported as `fee_error`, and `fees/remit` still works because it calls `remit_inner` directly. A recheck changes only inclusion evidence, so only a ledger fault reaches this path. It is noted, like `specify-funding-settlement` code difference 5, but no whitepaper rule is violated.
- Only the last fee failure of a pass is kept (contracts.rs:735–737 and 764–766). While the wallet has one unresolved remittance, every further unconfirmed batch reports "canonical settlement pending", which can hide a more specific earlier failure. This is a reporting detail.
- The current desktop Provider page sends `remit` without a confirmation step. A.5.5 does not require one. The confirmation of *Remit now* on the future Share dashboard belongs to `desktop-share-online`.
- The A.1.6 consumer disclosure lists "the platform fee rate", and the Marketplace says "The provider remits a … platform fee" (Marketplace.svelte:175). ## Open questions for the whitepaper author

1. **What makes a remittance "confirmed"?** Line 528 names the confirmed state but does not say what evidence it needs. The spec applies the funding policy `canonical-successful-receipt-at-espace-safe-v1`: successful canonical execution at the healthy `safe` frontier, observed twice, checked against the batch's sender, recipient, value and calldata. It is not PoS `finalized`. Proposed default (what the spec adopts): the funding policy, as the code does. Nonblocking: no task waits on the answer.
2. **How is a failed or displaced remittance resolved?** A remittance can fail canonically, for example when the platform wallet is a contract that rejects the transfer, or its nonce can be consumed without its receipt (`nonce_conflict`). The book does not say what happens next. Today the batch's obligations stay unconfirmed forever and every pass reports a fee failure. A `nonce_conflict` also blocks every later original of that wallet, including consumer funding that shares the journal, until the receipt returns. Options: (a) an explicit operator action that, after a failure is canonical at `safe`, seals the same obligations into a new batch and sends a new transaction, paying gas again; (b) keep them as permanently unremitted debt shown in the fee view; (c) another rule. Proposed default (what the spec adopts): no automatic replacement and a failure reported on every pass; no recovery action is specified until the author answers. Nonblocking for the specification; a recovery action would need its own task.

## Risks

- All executable evidence above is synthetic: loopback JSON-RPC fixtures and ledger transitions. The migration plan records one isolated live fee remittance ("The chain confirmed the original `50000000000000` wei fee remittance, with provider-paid gas", `docs/llm-serving-migration-plan.md` line 472). Batching, remittance restart, reorganization and network-fee failures remain an open release gate (plan line 504, book line 771). Task 4.1 tracks them.
- Tasks 2.1 and 2.2 change the JSON of `GET /admin/fees`, which `provider-admin.py`, the CLI and the desktop Provider page print as raw results. No client parses it, but tests that read `amounts_wei.remitted` must be updated.
- Task 2.3 must keep per-pass work bounded while evaluating the thresholds over every pending obligation, for example by streaming totals in chunks inside one ledger transaction.
- Task 2.4 adds a per-batch check time to the ledger. It must not change a batch's immutable fields, and an unavailable recheck must also advance the check time so that one unreachable batch cannot hold the front of the queue.
- The implementation values in decision 12 are not normative. Changing one needs no spec change, but this design should be updated to match.
- Requirements reference capabilities from pending changes (task 4.3 sets the archive order).
