## Decisions

1. **One capability for the current daemon, `managed-engine-runtime`.** Launch, observation, supervision and stop are one lifecycle owned by `engine_runtime.rs` and `app.rs`. The desktop specs describe the same engine for a different host process and add desktop-only rules (fit estimates, per-load keys, eject), so they stay separate.
2. **The child environment is an exact list.** "Minimal" (line 619) is not testable. The spec states the current list: `CUDA_DEVICE_ORDER=PCI_BUS_ID` set by the launcher, and `SystemRoot`, `WINDIR`, `TEMP`, `TMP` and `TMPDIR` copied when present. Adding a variable needs a spec change. The forbidden families are named as examples, not as a denylist; the allowlist is the rule.
3. **Contract arguments are normative for the pinned engine.** The table in requirement 5 maps each contract term the book names to its `v0.9.0` option. A different engine pin needs its own runtime identity (line 615) and a spec change. Options that only disable features outside the contract are current implementation values (decision 9) and may change without a spec change; options that name a remote model, enable fitting or context shifting, open another listener or carry a secret are forbidden.
4. **The engine key is a separate credential, checked by token.** Line 474 requires separate protected files, and `CLAUDE.md` says the engine has "no wallet key". Comparing tokens rather than paths also covers a copy of the same secret in another file. The signing key is compared without `0x` and without letter case, because any spelling hands the wallet key to the engine. The rule also covers an external engine's key: the daemon presents that key as a bearer to the external endpoint. The 32-character floor of the key is normative, as for the administration token (`app.rs:125`) and the RPC gateway's bearer; the book states no length, and the code already enforces it (`engine_runtime.rs:138`). Code difference 1.
5. **The port probe must detect a wildcard listener without refusing expiring connections.** `tokio::net::TcpListener::bind` (tokio 1.49.0 `src/net/tcp/listener.rs:123–124`) calls `mio::net::TcpListener::bind`, which sets `SO_REUSEADDR` on Unix (mio 1.1.1 `src/net/tcp/listener.rs:80–81`; the setter is `src/sys/unix/tcp.rs:45–55`). On macOS a socket with that option binds `127.0.0.1:P` while another process listens on `0.0.0.0:P`. This was reproduced on this host with the same socket options (`python3 -I` probe in the scratchpad: with `SO_REUSEADDR` the bind succeeded, without it the bind failed with "Address already in use"). On Linux a listening wildcard socket blocks the bind either way. Code difference 2. Simply dropping `SO_REUSEADDR` is not the fix: the review measured on this host that a bind without it is also refused while the port holds only a `TIME_WAIT` connection whose listening side closed first, which a stopped engine's keep-alive connections can leave for up to about a minute, so a prompt restart would fail. With `SO_REUSEADDR`, a bind-only probe (no `listen`) of the family's wildcard address on the same port failed beside a wildcard listener and succeeded beside a same-address listener and beside `TIME_WAIT`, while the existing endpoint bind failed beside a same-address listener. Probing both addresses therefore meets requirement 4 on this host. The requirement states the outcome, not the socket options. The probe is released before the child binds, so a race window remains; the launcher accepts an answer only while its own child is alive, and readiness probes check the engine's alias, build and slots (`inference_backend.rs:715–726`), so a foreign process cannot become ready. The window is recorded as an observation, not a difference.
6. **"Before startup" means the headroom check.** Line 617 says fit and headroom are checked before startup and after loading. Before startup the code checks that each device has free memory of at least the reserve. It does not estimate weights, KV cache and buffers against free memory minus the reserve; with automatic fitting off, the actual load decides fit, and the post-load check confirms the headroom. The desktop target design does estimate. Open question 1.
7. **CPU runtimes carry no memory claim.** A `cpu` runtime observes no device, signs memory kind `system`, has no reserve floor and no post-load memory check. A serving profile cannot use CPU (`inference-commercial-terms`), so CPU carries no capacity tier or speed class (line 100). The configuration still accepts a CPU managed runtime outside development for an unprofiled embedding model. Open question 2.
8. **An engine failure closes the whole provider.** `inference-offer-discovery` already specifies that a failed managed engine withdraws every published offer and makes `ready` false; the code also makes `accepting` false for every model (`app.rs:198–213`, `336–340`). Line 632 asks only that admission and publication be withdrawn, so this is stricter, not different. This capability adds that nothing restarts or revives the engine.
9. **Current implementation values (not normative).**
   - Configuration bounds: at most 16 engine selectors; `startup_timeout_secs` 1–1,800; total context at most 2,147,483,647 tokens.
   - Inventory bounds: metadata files at most 4 MiB; at most 8,192 inventoried files; a selected template at most 1 MiB.
   - Additional disabling options: `--no-cache-prompt`, `--cache-reuse 0`, `--cache-ram 0`, `--no-webui`, `--no-mmproj` and `--no-prefill-assistant`. `docs/provider-qualification.md` line 229 states that prompt-cache reuse is disabled.
   - Process settings: on Unix the child starts its own process group (`process_group(0)`), which `stop` kills as a whole.
   - Timing: the health poll runs every 100 ms with a 2-second request timeout; device observers are limited to 10 seconds and 1 MiB of output; the supervisor polls every 100 ms; `stop` waits up to 5 seconds; daemon shutdown waits up to 75 seconds for in-flight requests.
   - Platform tools are looked up in `/usr/bin`, `/usr/sbin`, `/bin` and `/sbin`, or on Windows in `%SystemRoot%\System32` and `C:\Program Files\NVIDIA Corporation\NVSMI`.

## Code differences

1. **The engine key is not checked against the other credentials** (requirement 6; book line 474; `CLAUDE.md` "no wallet key"). `ProviderConfig::validate` (`provider_config.rs:91–187`) never compares `engine_api_key_file` with `signing_key_file`, `admin_token_file` or `network.rpc_bearer_file`. `validate_inventory` (`engine_runtime.rs:134–138`) accepts any single literal token of at least 32 characters, and a signing key file holds 64 hexadecimal characters, optionally prefixed with `0x` (`wallet.rs:17–24`, `155–164`). A configuration whose `engine_api_key_file` names the signing key file therefore starts. The managed engine is given the wallet key file's path through `--api-key-file` (`engine_runtime.rs:228`), and the daemon sends the wallet key as the bearer of its health probe (`engine_runtime.rs:275–276`) and of every private engine request (`inference_backend.rs:537–543`). The same holds for the administration token, and for an external engine's key. Verified by reading. Provisioning generates a distinct `secrets/engine.token` (`scripts/provision-provider.py:237`), so only a hand-written configuration is affected. Task 2.1. Fixed 2026-11-18 by task 2.1: `ProviderConfig::verify_separate_engine_keys`, called by `ProviderRuntime::start` and `chiral_daemon --check` before any engine starts.
2. **The occupied-port probe misses a wildcard listener on macOS** (requirement 4; book lines 627 and 642). `ManagedEngine::start` probes the endpoint with `tokio::net::TcpListener::bind` (`engine_runtime.rs:260–262`), which sets `SO_REUSEADDR` on Unix. On macOS such a socket binds `127.0.0.1:P` while another process listens on `0.0.0.0:P`, so the launch continues as if the port were free (reproduced on this host, decision 5). Linux refuses that bind. On Windows mio does not set the option; whether a specific-address bind there succeeds beside another process's wildcard listener was not verified (task 4.1). Removing the option instead would refuse a port held only by `TIME_WAIT` connections (decision 5). Task 2.2. Fixed 2026-11-18 by task 2.2: `wildcard_port_probe` binds the family's wildcard address without listening, before the endpoint listener; Windows remains task 4.1.
3. **A termination signal during startup orphans the engine on macOS** (requirement 11; book lines 634 and 642). `chiral_daemon` creates its `SIGTERM` and Ctrl-C handlers inside `shutdown_signal()` (`bin/chiral_daemon.rs:23–34`), which is first polled in the `select!` at lines 112–116, after `ProviderRuntime::start` returned (line 85). tokio installs a signal handler only when the stream is created (`tokio` 1.49.0 `src/signal/ctrl_c.rs:59–61`), and nothing else in the daemon installs one. `ProviderRuntime::start` spawns each managed engine, waits for its health for up to `startup_timeout_secs` (at most 1,800 s; `engine_runtime.rs:38` and `276`), observes the devices again and then runs a refresh with inference probes (`app.rs:189`). A `SIGTERM` from the service manager or a `SIGINT` from the terminal in that window ends the daemon by the default action, so no `Drop` runs. The engine runs in its own process group (`engine_runtime.rs:210`), so a terminal's `SIGINT` does not reach it either, and macOS has no parent-death mechanism (`engine_runtime.rs:211–218` is Linux only). The engine is orphaned, keeps loading and keeps the port, and the next start fails with the occupied-port error. The book allows a macOS orphan only after an abrupt `SIGKILL` (line 642). Linux (parent-death signal) and Windows (kill-on-close job) still terminate the engine. Verified by reading; not reproduced, because no runnable stub engine exists in the repository. Task 2.3. Fixed 2026-11-18 by task 2.3: the termination streams exist before `ProviderRuntime::start`, which is raced against them; the task's process test reproduced the orphan on macOS without the fix.
4. **Ambiguous device observations were accepted** (requirement 7: "unparsable or ambiguous output SHALL fail the launch"; book line 617). The engine's `--list-devices` output was searched for the first line naming each selector, so a selector listed twice was observed from whichever line came first. `nvidia-smi` rows were mapped to `CUDA<n>` by position after sorting by PCI bus ID, so two rows with the same bus ID could put either GPU at that position. Vulkan already refused two devices of one name. Found on 2026-11-20 by task 3.7's parser tests, which failed before the change. Fixed 2026-11-20 by task 3.7: `engine_devices` refuses a selector listed more than once, and `cuda_devices` refuses a bus ID listed more than once (`engine_runtime.rs`). Neither output occurs with the pinned engine and a working driver, so only corrupt output is affected; the launch now fails closed on it.

## Observations outside this capability

- **Race between probe and child bind.** The probe listener is dropped just before the child is spawned (`engine_runtime.rs:262–265`), so a process can take the port in between. Its answers cannot make the engine ready while the child is not alive, and readiness probes check the engine's alias, build and slots. Until the child's exit is observed, however, the startup health probe sends the engine key as its bearer to whatever listens on the endpoint (`engine_runtime.rs:289–290`), and the key file is reused at the next launch. Only a local process that wins the race can receive it. No task.
- **A CUDA device is always signed `dedicated`.** `observe_devices` does not test whether a CUDA device shares system memory (`engine_runtime.rs:362–376`), unlike Vulkan (412). On such hardware the launch depends on `nvidia-smi` reporting numeric memory. Not verified on such hardware; no task. The Linux and Windows CUDA paths in lines 96–97 are discrete GPUs.
- **Vulkan memory.** `vulkaninfo --summary` gives identity, type and driver but no memory, so a Vulkan device's physical memory (`engine_runtime.rs:413`, the engine's `total`) and its free memory before and after loading (359) come from the engine's own enumeration only. Requirement 7 states this. Line 99 already says that the qualification runner rejects Vulkan without trustworthy per-device memory, and `inference-generation-performance` refuses it. The launch does not refuse Vulkan.
- **Provisioning and daemon bounds differ.** `scripts/provision-provider.py:110–112` accepts `startup_timeout_secs` up to 3,600; the daemon refuses more than 1,800 (`engine_runtime.rs:38`). Such a configuration fails closed at daemon start. Provisioning also requires a 256 MiB reserve for `cpu`, which the daemon does not. A provisioning change should align the bounds.
- **The parent-death signal follows the spawning thread.** On Linux `PR_SET_PDEATHSIG` fires when the thread that spawned the child exits. The daemon spawns engines while `ProviderRuntime::start` runs in `#[tokio::main]`'s `block_on` on the main thread, which lives until exit. A future caller that launches engines from a thread that can exit (for example a `spawn_blocking` worker) would kill the child early.
- **Readiness probes are not specified here.** Model, template, tokenization and capability probes (book line 628, `inference_backend.rs:691–760`) belong to comparison item 13. Requirement 8 names only the `/props` checks that guard against a reduced contract.

## Open questions for the whitepaper author

1. **What does "before startup" require of fit?** Line 617 says "Model fit/headroom is checked after actual loading as well as before startup." Before startup the daemon checks only that each selected device has free memory of at least the reserve; with automatic fitting off, the actual load decides whether the model fits, and the post-load check confirms the headroom. Options: (a) keep the headroom check before startup, as today; (b) also estimate weights, KV cache and buffers against free memory minus the reserve, and refuse before spawning, as the desktop target design does. Proposed default (what the spec adopts): (a). Nonblocking: (b) would add one task.
2. **What headroom applies to a CPU runtime outside development?** Line 100 calls CPU a development path, and line 90 gives headroom rules only for unified and dedicated memory. The configuration accepts a CPU managed runtime outside development for an unprofiled embedding model, with no reserve and no memory observation. Options: (a) keep it, with no capacity or headroom claim, as today; (b) require a system-memory reserve, for example 4,096 MiB as for unified memory, checked before and after loading; (c) refuse CPU managed runtimes outside development. Proposed default (what the spec adopts): (a). Nonblocking. This is related to the report question of 2026-11-18 about priced, unprofiled embedding deployments on external engines, but it is separate from it.

## Risks

- Task 2.1 refuses a hand-written configuration that reused the signing key, administration token or RPC bearer as the engine key. That is the intent; the operator must issue a new engine token, and provisioning already does.
- Task 2.2 refuses to start on a macOS host where another service listens on the wildcard address of the engine port. The operator must move one of them. A fix that merely drops `SO_REUSEADDR` would also refuse a prompt restart while the previous engine's connections expire; the task's regression covers that.
- Task 2.3 changes only when the daemon reacts to a termination request. A signal during startup still fails the start; nothing is served or published.
- The executable evidence available locally is a test binary standing in for `llama-server` and fixtures for its outputs. Argument and environment tests prove what the launcher passes, not how the engine interprets it. Whether `--fit off` and `--no-context-shift` behave as required, and whether parent-death and job containment work, are real-hardware evidence (task 4.1). That evidence is never public-release approval.
