## Decisions

1. **Scope.** This capability covers A.5.1–A.5.9 and the A.4 components that those pages use. Every A.1 rule is referenced from `desktop-gui-global-rules` or `desktop-window-lifecycle`. The A.2 shell (navigation, status pill, wallet chip, log out, quit, version gate, notifications) is outside this capability: log out and notification roles are `desktop-gui-global-rules`, quit and the tray are `desktop-window-lifecycle`, and the version gate (book lines 646–652 and 846) is not restated here (observation 9). The A.3 design language is presentation. Required elements stay reachable at the widths A.2 supports (requirement 15). The A.7 target pages are out of scope; A.7 keeps today's pages under the Network and Wallet groups (`desktop-local-workbench`, *Navigation exposes the local workflow*), so these requirements still apply to them there.
2. **What a page must keep.** Line 873 lists purpose, layout, native operations and required states for each page; lines 802 and 971 make layout, wording, color and iconography presentation, and the disclosures, acceptance controls and recovery paths required. The requirements therefore cover: the native operation and arguments of each action; the states each page distinguishes; every disclosure, acceptance, confirmation and recovery path; and secret handling on the page. They do not cover layout, order, color, icons or exact wording. Quoted strings in A.5, such as "Find a model to run" and the Playground status labels, are current presentation: their meaning is required, not their wording. No other capability requires an exact A.5 string today.
3. **Opening a page only reads.** A.6 forbids an extra unconfirmed payment path (line 971), and A.1.7 forbids automatic retries (line 814). Requirement 1 therefore allows a page to read when it opens (Usage reads the accounts and the journal; the Marketplace reads the journal), and requires every operation that signs, pays, cancels a provider request or a funding transaction, issues, rotates, revokes, submits, writes a file, administers a provider or loads a profile to run only on the user's action. Stream cancellation is deliberately not in that list: the book itself cancels a stream without a cancel action at the display limit (line 914) and when a session ends (line 815). The mapping table lists the arguments each native operation reads (`desktop.rs:55–209`); an argument the operation ignores is not part of the mapping (observation 8).
4. **Read-only additions are allowed.** The book lists no `agreement` operation; `specify-desktop-gui-global-rules` task 2.1 added it so that the Usage top-up card can state the endpoint and fee rate. Requirement 1 allows a read-only operation that returns public data and no secret, as line 973 (parsed tiles plus the raw result) and the top-up disclosure need. Such an operation may not sign, pay or change state.
5. **Credential options are part of the mapping.** Line 930 lists the options (expiry, no spend cap, concurrency 1, scopes `infer` and `read`) and the lifetime range, 60 seconds to 30 days with a default of one day. The provider accepts any expiry after the current time up to 90 days (`billing_store.rs:29`, `884–893`), so a GUI that does not enforce its own range can issue a 5-second or 60-day credential. The lifetime decides how long a revealed key stays usable, so requirement 6 requires the GUI to refuse other values before any native call. Whole seconds follow from the integer `expires_at` (`billing_store.rs:46`).
6. **A revealed key must be copyable while masked.** Line 808 requires the revealed key in a masked field and says that the user reveals it "for SDK use"; line 930 names the action *Explicitly reveal SDK credential*. A key that can be neither read nor copied cannot be used, so requirement 6 requires a way to copy it while it stays masked, for example an explicit copy action. The clipboard is outside webview state, storage, URLs and logs, which line 808 governs, and the copy happens only on the user's action after an explicit reveal. Unmasking on screen is not required and not forbidden by this capability; `desktop-gui-global-rules` requires the masked field.
7. **Offer terms are shown before a quote.** Line 480 says that a quote copies the offer's model, capabilities, prices, limits, fee and network, and line 867 lists those fields on the offer card. Requirement 3 requires them to be visible before the user requests a quote, so the user can see what the quote will bind; how they are laid out is presentation. The fee rate is already in the funding disclosure (`desktop-gui-global-rules`).
8. **Playground states, not labels.** Line 913 lists the status values. Requirement 4 requires the eight distinct states and their meaning; `desktop-gui-global-rules` (*Ambiguous paid requests are reconciled, never resent*) already requires the failure split by request ID and the possibly-billed cancellation. The quoted labels are presentation.
9. **"Prompts are not persisted"** (line 915) means that the page writes prompts and responses to no webview storage, file or history; they leave the page only as the arguments of the native inference operation. Target-design chat history is a separate, explicit feature (`desktop-local-chat`, *Chat history is local, protected and under user control*).
10. **The profile load is confirmed and the indicator has text.** Line 816 requires status changes in `role="status"` regions and color never as the only signal; `desktop-gui-global-rules` (*The GUI is accessible*) specifies both for every page. Line 958 adds a green or amber dot to the Settings menu, which is presentation. Requirement 13 therefore references the global rule for the indicator instead of restating it: where Settings shows the profile state, the indicator carries it as text. It adds what is specific to A.5.8: the success message must survive the remount that `desktop-gui-global-rules` requires. A failed load is already specified there (*Logout and a profile change end the previous session's view*). Code difference 3 violates the global rule; it is recorded here because the global-rules change did not list it and A.5.8 is where the dot is described.
11. **Native rules are referenced where another capability owns them.** The literal-loopback endpoint and native token reading for `provider_admin` are `inference-fee-remittance` (*Explicit remittance is a local operator action on the loopback administration listener*). The no-overwrite rule for wallet export (line 474) is stated in requirement 9, because no other capability states it.
12. **Required elements stay reachable.** A.2 supports phone widths: below 768 px the top bar becomes a hamburger menu, and the sidebar becomes a top bar with an overlay menu (line 838). A.6 allows any layout but no missing required element (line 971). Requirement 15 therefore requires each required element in every layout and width the shell supports, reachable by pointer and keyboard, and lets a section switcher scroll or wrap. Horizontal page overflow by itself is presentation.
13. **Balances are never combined.** Line 950 says so for the Account page, and line 33 makes provider balances non-transferable between providers. Requirement 11 forbids a total across providers.
14. **Feedback revisions.** Line 933 asks for an increasing revision; line 413 adds that the catalog requires both the revision and `issued_at` to increase strictly. The page states that the revision must increase; the catalog enforces it.
15. **Offer terms are not tied to the listing.** Line 867 describes the offer card, but A.6 allows any layout (line 971). Requirement 3 therefore requires the terms to be visible before a quote for that offer is requested, in the listing or on inspection.
16. **The backup is owner-only natively.** Line 939 has the page warn that the backup file is owner-only, and line 474 requires secrets that are not group- or world-accessible and an export that refuses to overwrite. Requirement 9 therefore requires the native export to create an owner-only file as well as to refuse an existing path, so that the page's statement is true. Today `wallet::save_private_key` (`wallet.rs:166–171`) creates the file through `create_secret_file`, with `create_new`, mode `0600` and `O_NOFOLLOW` on Unix and owner-protected storage on Windows (`wallet.rs:67–87`).

## Code differences

Each difference has an unchecked task in section 2 of `tasks.md`.

1. **The credential lifetime range is not enforced** (requirement 6, book line 930, decision 5). The lifetime field declares `min="60" max="2592000"` (`Usage.svelte:265`), but it is not in a form: *Issue API credential* and *Rotate selected credential* are click handlers (`268–269`) that call `credentialAction`, which sends `expires_at: now + ttl` without any check (`81`). Constraint validation therefore never runs. In the browser check, a lifetime of 5 seconds and one of 5,184,000 seconds (60 days) both reached `credential_issue` unchanged while the field reported itself invalid. The provider accepts any expiry after the current time up to 90 days (`billing_store.rs:29`, `884–893`), so both would be issued. An empty field sends an expiry equal to the current time, which the provider refuses. Task 2.1.
2. **The revealed API key cannot be copied** (requirement 6, book line 930, decision 6). The key is shown in `<input type="password" readonly>` (`Usage.svelte:276`) with the hint "Select the password field to copy the key into your SDK's secure environment" (`278`), and the page offers no copy action. In headless Chrome 157, a trusted copy shortcut fired a `copy` event for selected text in a text field but none for selected text in a password field (reproduced in review with the DevTools protocol's `copy` editing command), so Chromium-based webviews (WebView2 on Windows) do not copy the key. WebKit is expected to behave the same; WKWebView and WebKitGTK are checked in task 4.1. The user can therefore neither read nor copy the revealed key, and the reveal cannot serve SDK use. This settles the `specify-desktop-gui-global-rules` design observation about copying, for Chromium. Task 2.2.
3. **The Settings profile indicator has no text alternative** (requirement 13 and `desktop-gui-global-rules` *The GUI is accessible*, book lines 816 and 958, decision 10). The menu's profile entry shows a green or amber dot whose state is only in a `title` attribute on an empty `span` (`Settings.svelte:56`). Chrome's accessibility tree names the entry "Network profile" with or without a loaded profile (reproduced in review with Chrome 157 on a minimal page carrying the same markup: the button's computed name excludes the span's `title`), so the state reaches assistive technology only through color. The same state appears as text in the profile section (`70–76`) and in the shell banner and status pill, but not when another Settings section is open. Task 2.3.
4. **A successful profile load is not announced** (requirement 13, book lines 816 and 960, decision 10). `configure()` sets `notice` after incrementing `sessionEpoch` (`Settings.svelte:15–18`). `App.svelte:102` keys the current page on `sessionEpoch`, so the Settings instance that set the notice is destroyed and a new one starts with an empty notice. In the browser check the success text was absent after a load (reproduced in review against the Vite dev server with a stand-in bridge), while "Profile loaded" appeared in the green box (`70–76`), which has no `role="status"`. A screen-reader user is not told that the load succeeded. This settles the `specify-desktop-gui-global-rules` design observation about the Settings notice. Task 2.4.

No other difference from the whitepaper was found. Each page invokes the operations that A.5 lists, shows the states and statements that the requirements name, and places the referenced disclosures, acceptance controls and recovery paths as required.

## Observations outside this capability

1. **Usage width at 390 px (A.2/A.3 presentation).** The twenty-second round recorded that the Usage tab strip made the page 415 px wide at a 390 px viewport. In headless Chrome 157 at 390 px the page's `scrollWidth` was 390 on every Usage section, with and without a selected account; no element outside a scroll container extended past the viewport. The tab list is its own 358 px scroll container holding 652 px of tabs, so *Funding & recovery* and *Feedback* start off-screen and are reached by scrolling the list or by keyboard focus; the pending-funding notice also opens *Funding & recovery* directly (`Usage.svelte:181`). No required control is unreachable, so this is not a code difference under requirement 15. The review repeated the measurement with a selected account and a journaled payment, in both the top bar and the sidebar layout, on every Usage section: the document's `scrollWidth` equalled the viewport's content width (375 px beside a 15 px classic scrollbar), no element outside a scroll container extended past it, and the tab list was a 328 px scroll container holding 678 px of tabs. The tab-list markup is unchanged since the twenty-second round (`c365d384`), so the earlier 415 px figure did not come from the tab list as it is now; it may come from another engine or from the remote font removed in the twenty-seventh round. Task 4.1 checks WKWebView and WebKitGTK.
2. **Stat tiles truncate long amounts.** `StatTile.svelte:13` gives the value `truncate`, with no tooltip. At 390 px the Usage *Available* tile showed "0.99487654…" for `994876543210987655` wei. The DOM text is exact and the full value is on the same page (`Usage.svelte:218`). Whether visual truncation counts as "dropping digits" is a question for `desktop-gui-global-rules` (*Money crosses the native boundary as exact wei*); it is not recorded as a difference here.
3. **Selecting the Playground placeholder** "Choose account" calls `account` with an empty contract ID (`Playground.svelte:127`, `28`) and shows the native error "missing contract_id". Usage guards the same case (`Usage.svelte:29`).
4. **The Usage pending notice counts every journal entry** (`Usage.svelte:99`, `178–183`), including entries in `cancelled`, `not_prepared` and other stages that `unresolvedPayments` treats as settled or unpaid (`funding.ts:20`), and tells the user to resume them. The wording is conservative; whether to count only unresolved entries is presentation.
5. **A local embedding input error** ("Enter 1–32 non-empty lines…") is thrown inside the dispatch `try` (`Playground.svelte:66`, `80`), so it is labeled "Failed — inspect Usage before retrying" with the note that the request may have reached the provider (`207–210`), although nothing was sent. Requirement 4 is met, because the input is refused before any native call.
6. **The cancellation acceptance is cleared only after a successful submission** (`Usage.svelte:69`, `329`). It stays checked after a failed attempt and after the contract or operation ID is changed. `inference-funding-settlement` requires a visible acceptance before `accept_gas_and_race_risk` is set, not a reset, so this is not a difference.
7. **No hint without a wallet.** With a profile but no wallet, the Marketplace disables *Request signed quote* (`Marketplace.svelte:260`) without saying that a wallet is needed.
8. **Credential actions send ignored arguments.** `credentialAction` sends one argument object to all three credential operations (`Usage.svelte:81`): `credential_issue` also receives `credential_id`, and `credential_revoke` also receives `options` with an expiry. The native layer reads neither (`desktop.rs:107–111`, `172–175`). Requirement 1 lists the arguments each operation reads, so this is not a difference; the mapping test of task 3.1 asserts the listed arguments, not exact argument equality. Task 2.1 keeps *Revoke* independent of the lifetime check.
9. **The version gate is not specified by any change.** Under a *required* update the native layer refuses `discover`, `quote`, `fund`, `topup`, `resume`, `credential_issue`, `credential_rotate`, `feedback`, `infer` and streams (`desktop.rs:46–52`, `152–154`, `219`), and the shell shows a blocking modal (book line 846). The other A.5 operations, including `cancel_funding`, `funding_recovery` and `request_status`, stay available natively. The book's version-policy section (lines 646–652) says what upgrades must preserve but not which recovery paths stay open while an update is required. A.2 is outside this capability (decision 1); a version-policy specification should settle it.
10. **Leaving the Playground cancels its stream** (`Playground.svelte:92`). The book does not say whether navigating to another page cancels a stream; closing the window does not (book line 817). After such a cancellation the request ID shown on the Playground is gone, and the request is found under Usage › Requests as a local request key. Requirement 1 does not restrict this (decision 3).
11. **A failed address copy is silent.** The Wallet copy action ignores a clipboard failure (`Wallet.svelte:32`); only success is announced (`89`). Task 2.2 requires the API-key copy action to report failure; the address copy is presentation.

## Risks

- Most acceptance evidence today is code reading and browser checks with a stand-in bridge. Only Marketplace, Usage, Playground and Diagnostics are rendered in tests. Section 3 of `tasks.md` lists the missing tests.
- jsdom cannot show layout, clipboard behavior, focus scrolling or what the platform webviews allow. Those need the native desktop on macOS, Windows and Linux (task 4.1); a browser preview is not native verification (book line 974).
- Requirements reference capabilities from pending changes; task 4.2 sets the archive order.
- The requirement that a revealed key be copyable puts the key on the system clipboard, where clipboard history tools may retain it. The book permits the reveal for SDK use, and this capability requires only that the copy be an explicit user action.
